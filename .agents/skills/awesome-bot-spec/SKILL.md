# Deep exploration of awesome_bot

Create or expand the [specifications](../../../specifications/project/README.md), describing the actual implementation in enough detail for an agent to locate a change, understand contracts, and preserve existing behavior. Write the specifications in Russian, preserving exact command, tool, and symbol names. Do not change application code, configuration, database schema, or tests.

## Exploration

Read repository rules, the index, and existing specifications; inspect the working tree. Describe current files, including uncommitted changes, and note material discrepancies with documentation. Respect the exploration scope specified by the user.

When a complete specification already exists, use its directory indexes and coverage ledger as the discovery baseline, verify them against current code, and preserve established canonical files and section anchors. A new exploration should deepen or correct the requested scope rather than recreate the tree or replace detailed contracts with summaries. For change-driven incremental synchronization, use `awesome-bot-spec-update` instead.

Maintain a coverage inventory: subsystem/entry point → implementation → tests → specification section → open questions. First locate bootstrap, routers, tool registrations, the Prisma schema, scheduler, configuration, and tests. Then trace calls through handlers, state changes, and result delivery. Comments and help text aid discovery but do not prove behavior.

Explore the following surfaces:

- **VK commands.** Build a complete catalog from routing, parsers, button/callback handlers, and dynamic registrations. Reconcile it with help text and tools for listing/executing commands. For each command, document exact syntax, aliases, parameters, defaults, an example, conversation type, prefix/mention requirements, permissions, availability conditions, responses, errors, and data changes. Explain precedence among overlapping handlers, unknown commands, and fallback to AI. Distinguish user commands, internal actions, and model-triggered calls.
- **Model tools.** Find definitions and where tools are attached to provider requests. For each tool, document its public name, purpose, argument schema and required fields, validation, result and errors, permissions, context restrictions, external calls, side effects, and implemented timeouts and retries. Distinguish main-model tools from subagent tools and declared tools from tools actually attached to requests; explain configuration conditions and provider differences. Trace execution, returning results to the model, and delivery to the user. Do not assume each file represents a separately available tool.
- **AI and context.** Describe model/provider selection, message assembly, prompts, history, summaries, memory, attachments, loop/token limits, errors, subagent lifecycle, and result delivery.
- **Data and permissions.** Reconcile Prisma models, migrations, and read/write sites. Record identifiers, relations, uniqueness, isolation by conversation/user, authorization, transactions, retention, and deletion. Highlight invariants that changes must preserve.
- **Features and jobs.** For games, media, reminders, and other discovered features, describe scenarios, states, and transitions. For each background job, document registration, schedule, time zone, selection criteria, results, errors, restart behavior, and duplicate prevention where implemented.
- **Operations.** Trace bootstrap, DI, dependencies, and shutdown. Verify configuration keys, required values, and defaults against code and compare them with the example environment; describe Docker, migrations, and validation commands. Do not include secrets or private message content.

## Documentation for agents

Expand existing documents while preserving useful content. Give each discovered entity its own specification file in the corresponding entity directory, except commands/subcommands, model tools and Prisma models, which use three separate canonical catalogs as specified below. Catalogs and overviews link to these files rather than replacing them. Do not duplicate a contract across multiple locations.

For each subsystem, record purpose, entry points, contracts, the main flow, alternatives and errors, state and side effects, permissions, configuration conditions, dependencies, and relevant tests. Add a map from change type → documents → files/symbols. Use diagrams when they clarify routing or state transitions.

Support material contracts with relative links to implementation and exact symbol names. Use tests to substantiate the scenarios they verify; do not claim coverage for unverified scenarios. Prefer file links; add line numbers only after checking them. Record the exploration date and revision when available, noting relevant working-tree changes. Separate facts, inferences, and unknowns; do not describe plans as implemented behavior.

## Specification directory layout

Store general specifications under `specifications/project/` and mirror the repository's source directories beneath it. Each service and job must have its own canonical Markdown file, even when several entities share an implementation file. Commands/subcommands, model tools and Prisma models are explicit exceptions: keep each category in its own single catalog. Do not create a specification for every local function or type: helper details belong to their owning entity unless they form an independently consumed contract.

- Model tools: keep all main-model and subagent tools in the single canonical catalog `specifications/project/src/services/ai/tools.md`. Include a table of contents, an availability matrix and a dedicated stable heading using each exact `AITool.name`, preserving underscores. Document each tool’s full contract, schemas, examples, errors, permissions and side effects in its section; do not reduce the catalog to a summary table. Distinguish contexts with subsections when the same public name has different behavior. Do not create per-tool specification files. When reorganizing existing tool documents, consolidate useful content into this catalog and update incoming links to section anchors without leaving duplicate canonical descriptions.
- Services and infrastructure modules: mirror the implementation path and replace `.ts` with `.md`, for example `src/services/settings/personalityService.ts` → `specifications/project/src/services/settings/personalityService.md`. If a module owns multiple independent services, use a directory named after the module and one file per exported service identity; record this mapping in the directory index. Shared helper modules with substantive contracts follow the same source-path convention.
- Commands: keep all VK commands, subcommands and aliases in the single canonical catalog `specifications/project/src/services/command/commands.md`. Use a table of contents and a dedicated stable heading for each canonical command, with nested sections for subcommands. Preserve the full command contract detail; one file does not mean an overview-only table. Link to command sections using anchors from service documents, indexes and the coverage ledger. Do not create separate command files or per-command directories. When reorganizing existing command specifications, consolidate their useful content into this catalog and update incoming links, avoiding duplicate canonical descriptions.
- Jobs: mirror `src/jobs/<job>.ts` as `specifications/project/src/jobs/<job>.md`; document separately registered jobs sharing a module in individual files in a module-named directory.
- Prisma models: keep all models in the single canonical catalog `specifications/project/prisma/models.md`. Include a table of contents, a model summary and a dedicated stable heading using each exact Prisma model name. In each section, document fields/types/defaults, keys, indexes, relations, ownership, readers/writers, retention and deletion, with schema and migration links. Do not create per-model specification files or reduce the catalog to a list of names. When reorganizing existing model documents, consolidate useful details into this catalog and update incoming links to section anchors without leaving duplicate canonical descriptions. Configuration modules and entry points follow the source-path convention; group individual settings in the owning configuration document rather than inventing a file for every scalar key.

Use a `README.md` index in each entity directory containing specification files, with links, short purposes, source ownership and child directories. Keep the project root index and thematic overviews for navigation, cross-cutting flows and invariants. A service document links to its commands, tools, models and jobs; those entity documents link back to the owning service and related entities. Compute source and document links relative to each document's actual nesting depth.

Every entity file must identify the entity kind, exact runtime/exported identity, source file and symbol, responsibilities, inputs/outputs, behavior and errors, permissions, side effects, dependencies, configuration, relevant tests and limitations as applicable. Small entities may have concise documents, but a source link alone is not a specification. Use the detailed contract requirements in the exploration reference. When reorganizing existing documentation, move useful details into canonical entity files and update incoming links; do not leave competing copies of the same contract.

Extend the coverage ledger to map each entity to its canonical specification path and source symbol. For commands, model tools and Prisma models, map each identity to its section anchor in commands.md, tools.md or models.md, respectively. Check that every other entity in scope has its own file, and every command, tool and Prisma model has its section, or a clearly reported pending gap; verify that directory indexes reach all entity files, and no two files claim the same canonical identity. Reuse established entity paths when present; resolve name collisions with explicit owner/context subdirectories and document the mapping.

## Completeness checks

Reconcile command, tool, and job inventories with registrations and handlers: every discovered entity must have a description or an explained exclusion. Check availability conditions, links, examples, and document consistency. If some code remains unexplored, list it and explain why; do not claim complete coverage.

Static source and link checks are sufficient for documentation work. Run existing checks only when needed, using a Node.js 22 container for Node.js commands as required by repository rules. Do not start the bot, trigger external actions, or apply migrations to the operational database for documentation. Report documents, coverage, checks, and gaps. Use [awesome-bot-spec-update](../awesome-bot-spec-update/SKILL.md) for subsequent maintenance.

## Project-specific depth and output requirements

Before exploring code, read [the project exploration map and contract requirements](references/project-exploration.md). Use its source map to guide inspection, then verify all paths and registrations against the current working tree. It defines the required detail for command, tool, persistence, configuration and job contracts.

For full-project requests, produce durable specifications in `specifications/project/`, a linked index, and a coverage ledger with discovered/documented counts and explained exclusions. Keep individual task specifications in `specifications/tasks/`. Overview prose and pointers to source alone do not satisfy a detailed-specification request: expand every discovered command/subcommand and exposed tool into a contract, explain conditional availability and observable behavior, and document supporting data and jobs. Follow the entity-per-file layout regardless of entity size, with separate single-file catalogs for commands, model tools and Prisma models; adapt the depth to the entity without omitting categories.

Inspect all final `provider.send` tool arrays and their conditions, not only tool factories. Trace direct VK delivery and the guards that suppress duplicate model replies. Reconcile command handlers, help, aliases, command-execution restrictions and callbacks; distinguish automatic capabilities such as search from model-callable tools. Record discrepancies as current implementation facts without changing application code.

Before finishing, compare the coverage ledger with the requested scope, verify cross-document links and evidence, and explicitly list anything unexamined. Report counts and linked deliverables in chat; keep the detailed technical specification in the documents. Do not describe a source inventory or an unfinished overview as a completed deep specification.
