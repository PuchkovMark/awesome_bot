# Plan a task

Find the relevant `task.md` using the [task workflow](../../../specifications/tasks/README.md), and inspect the [specifications index](../../../specifications/project/README.md), affected code and existing conventions. If the task has not been defined, first use `awesome-bot-task`; do not silently substitute an implementation plan for a task definition.

Write `plan.md` in the same task folder. Describe the sequence of changes, affected files or subsystems, interfaces and data flow where relevant, failure handling, acceptance checks and deployment or migration implications. Keep the plan actionable and proportional to the task. During planning, update its approach only according to agreed decisions. During implementation, every plan is read-only unless the user specifically instructs a plan edit, including status/progress/check-result edits; invoking a planning skill does not bypass that restriction. Preserve task documents and unrelated changes. Do not require new or modified tests unless the user explicitly asks; existing checks may be run in an isolated Node.js 22 container.

## Agree implementation decisions before handoff

Do not independently select implementation decisions that the user has not already specified, agreed to or explicitly delegated. First inspect relevant code and contracts, identify viable options and their consequences, then ask the user to choose. Provide a concrete recommendation with its rationale and tradeoffs, clearly labeled as a proposal rather than an agreed decision. Reuse decisions already made in the conversation or task; do not ask for them again.

Resolve choices about architecture and algorithms, interfaces, data representation and schema changes, snapshots/pagination, handling of missing or partial data, failure/retry/restart behavior, resource budgets, thresholds, dependencies and compatibility before handing the plan to implementation. Ask only about actual choices left open by the requirements and code; do not turn established contracts into unnecessary questions. Local coding details such as variable names and formatting do not require agreement unless they affect a contract.

Ask implementation questions strictly one at a time. Present each question in Russian through an interactive terminal choice prompt, with numbered options, the recommended option clearly labeled and the consequences of each option briefly explained. Allow a custom answer. Wait for the user's explicit answer before presenting the next question; use that answer to refine subsequent options. Do not bundle several independent decisions into one prompt.

Do not impose an answer deadline, use timed input, choose a default automatically or interpret silence as agreement. A tool polling/yield interval is not a deadline for the user's answer: keep the question pending without progressing to dependent work. Do not keep a blocking tool call open merely to wait; preserve the pending question across turns. If the environment cannot provide an interactive terminal accessible to the user, explain that limitation and use an available explicit user-input interface with the same one-question-at-a-time and no-deadline behavior; never substitute a terminal visible only to the agent or auto-submit an answer. The user may explicitly request a different interface.

Record agreed choices and their rationale in `plan.md`. Keep unanswered choices in an explicit pending-decisions section, with options, recommendation and the affected steps. Do not silently apply a recommended/default option, infer agreement from silence, or disguise an unresolved choice as “determine during implementation.” Continue independent investigation while awaiting answers, but do not finalize dependent steps or describe the plan as ready for implementation until required answers arrive.

Include a handoff rule in the resulting plan: the implementing agent follows the agreed decisions; if new evidence requires a new implementation choice or a material change to an agreed choice, it reports the issue in chat and asks the user before dependent changes, while continuing independent work where possible. During implementation, no plan may be changed without a specific user instruction, even to record progress or check results; agreement to a solution or general authorization to implement does not authorize a plan edit. Explicit user delegation may permit implementation choices within the stated bounds, but does not authorize changing plans; record those bounds during planning.

Use project directory indexes and the [coverage ledger](../../../specifications/project/coverage.md) to locate affected entity contracts and canonical command/tool/model sections. Link these contracts in the plan, identify invariants to preserve and specification updates the implementation will require. Keep proposed behavior in task documents until implemented; specification synchronization remains a separate step when requested.

Record a concise mapping in `plan.md`: acceptance criterion → current contract and source owner → intended change → verification. Use links relative to the task document, including stable section anchors for the single [command](../../../specifications/project/src/services/command/commands.md), [tool](../../../specifications/project/src/services/ai/tools.md) and [model](../../../specifications/project/prisma/models.md) catalogs. For new entities, identify their intended canonical document/section using the existing source-mirrored layout; do not invent per-command, per-tool or per-model files. Read only the affected contracts, not the entire specification tree.

Verify the current behavior in code before choosing the approach. Distinguish intentional contract changes, invariants to preserve, existing implementation limitations and stale documentation. If task requirements and the current baseline differ, explain the intended transition; resolve material ambiguity rather than silently treating either document as the answer.

Trace consequences where relevant: VK routing/help/aliases/callbacks and permission precedence; tool schemas and final provider attachment conditions; direct versus deferred result delivery; data ownership, retention and SQLite migrations; jobs, retries and restart behavior; configuration defaults and consumers. Include dependent callers and cross-cutting documents beyond the directly edited files. Consult the [test map](../../../specifications/project/test/README.md), verify actual assertions and select checks that establish the acceptance criteria. Use [operations](../../../specifications/project/operations.md) for isolated validation; do not plan live VK/provider calls or operational database migrations as routine checks.

If the active mode prohibits file writes, present the plan in chat and write it when allowed. After `plan.md`, use [awesome-bot-implementation-plan](../awesome-bot-implementation-plan/SKILL.md) to prepare `implenent.md` when detailed planning or implementation was requested. A request for implementation authorizes proceeding with `awesome-bot-implement` once all three documents are prepared and required implementation decisions are agreed or explicitly delegated. Do not add a redundant approval step after these conditions are met. A plan-only request does not authorize implementation.
