# Implement a task

Identify the task folder using the [task workflow](../../../specifications/tasks/README.md) and read `task.md`, `plan.md` and `implenent.md`, the relevant [project specifications](../../../specifications/project/README.md), and affected code. Before starting implementation, prepare missing task/planning documents through `awesome-bot-task`, `awesome-bot-plan` and [awesome-bot-implementation-plan](../awesome-bot-implementation-plan/SKILL.md) as appropriate. Once implementation has started, missing or stale documents are a reason to ask the user before dependent work, not to invoke a planning skill to rewrite them automatically. Preserve unrelated working-tree changes and follow the user's latest instructions. Do not implement when only planning was requested or when the active mode prohibits changes.

Implement the requested behavior according to the agreed plan and detailed steps in `implenent.md`, reusing existing services and conventions. Trace affected VK routing, permissions, private and group data boundaries, request ordering, external failures, and stored data where relevant. Account for existing data and add compatible Prisma migrations or configuration examples if the task requires them.

## Ask before making unagreed decisions

Do not independently choose implementation decisions that the user has not specified, agreed to or explicitly delegated. This includes architecture, algorithms, interfaces, data representation/schema, dependencies, missing/partial data, errors/retries/restarts, resource limits and compatibility. Follow established contracts and agreed choices without asking again; local names and formatting do not require agreement unless they affect behavior or a contract. Record the bounds of any explicit delegation and stay within them.

If implementation reveals a new choice, a necessary deviation or a conflict between task documents and current code, report the evidence, affected steps and viable options with consequences and a clearly labeled recommendation in chat. Ask one question at a time, in Russian, using an available user-input interface with numbered options and a custom-answer option. If no such interface is available, ask in chat. Wait for an explicit answer before dependent edits; do not select defaults, impose answer deadlines or interpret silence as agreement. Continue independent authorized work where possible. Keep the answer in the conversation; edit a plan only if the user specifically instructs it. Agreement to a solution does not itself authorize a plan edit.

## Keep all plans read-only during implementation

During implementation, do not create, rewrite, extend, rename or delete any plan without a specific user instruction to change it. This includes `plan.md`, `implenent.md` and any other planning document, including its checkboxes, status, progress, remaining work and verification results. A general request to implement the task, permission to choose implementation details or agreement to a proposed solution is not such an instruction. Do not bypass this restriction by invoking another skill or creating a replacement plan. When specifically instructed to edit a plan, change only the authorized content; all other plans remain read-only. Report progress, deviations and check results in chat unless the user specifically asks to record them elsewhere. Ask about any necessary departure before dependent code edits.

Locate relevant entity contracts through project directory indexes and the [coverage ledger](../../../specifications/project/coverage.md); follow links to canonical command/tool/model sections and related jobs. Verify specification claims against current code and the [test map](../../../specifications/project/test/README.md) against actual assertions. When the task intentionally changes a contract, implement the agreed task requirements and report the affected specification paths/sections for subsequent synchronization; do not treat the previous behavior as a prohibition on the requested change.

Use the plan's acceptance criterion → contract/source → change → verification mapping and the detailed steps in `implenent.md` as the handoff. Recheck the current working tree before editing; distinguish pre-existing changes from task changes, including untracked files. If a plan is stale, verify its approach and mapping against current code and ask about any new or changed decision before dependent work. Leave plans unchanged unless specifically instructed otherwise. Read an existing `review.md` when continuing reviewed work, verify whether findings still apply and address authorized fixes without overwriting review history.

For affected commands, tools and models use their single canonical [command](../../../specifications/project/src/services/command/commands.md), [tool](../../../specifications/project/src/services/ai/tools.md) and [model](../../../specifications/project/prisma/models.md) catalogs. Preserve related routing/help/aliases, provider attachment conditions, direct/deferred delivery, jobs and ownership invariants unless the task changes them. Reuse source-mirrored entity paths for any requested documentation synchronization; do not create duplicate canonical descriptions.

Before reporting completion, map each acceptance criterion to implementation evidence and an executed check or an explicit verification limitation. Report actual progress, agreed deviations, remaining work and check results in chat; do not write them to plans without a specific user instruction. Do not mark unverified behavior as tested or incomplete criteria as complete. Identify the source files and working-tree/commit scope to review and affected specification sections, including relevant coverage/test-map entries. A plan status or prior review does not prove the current code passes checks.

For now, do not add or modify tests unless the user explicitly requests them. Run appropriate existing checks using a suitable Node.js 22 container and isolated data; do not apply migrations to the running bot's database for validation. Report completed work, actual checks and limitations. Review and specification synchronization are separate optional steps: use `awesome-bot-review` or `awesome-bot-spec-update` when requested.

Follow [operations](../../../specifications/project/operations.md) for validation. Do not start the live bot or send VK/provider requests merely to verify a change. Use `systematic-debugging` for unexpected failures and `sql-database-assistant` for SQL/migration work when applicable. If the user already requested review or specification synchronization as part of the task, continue to those steps without asking for permission again; otherwise report the handoff without invoking them automatically.
