# Implement a task

Identify the task folder using the [task workflow](../../../specifications/tasks/README.md) and read `task.md` and `plan.md`, the relevant [project specifications](../../../specifications/project/README.md), and affected code. If the task or plan is missing, use `awesome-bot-task` or `awesome-bot-plan` first as appropriate. Preserve unrelated working-tree changes and follow the user's latest instructions. Do not implement when only planning was requested or when the active mode prohibits changes.

Implement the requested behavior according to the plan, reusing existing services and conventions. Trace affected VK routing, permissions, private and group data boundaries, request ordering, external failures, and stored data where relevant. Account for existing data and add compatible Prisma migrations or configuration examples if the task requires them. If the implementation reveals a necessary change in approach, update the plan and continue within the authorized scope; resolve consequential ambiguities before dependent work.

Locate relevant entity contracts through project directory indexes and the [coverage ledger](../../../specifications/project/coverage.md); follow links to canonical command/tool/model sections and related jobs. Verify specification claims against current code and the [test map](../../../specifications/project/test/README.md) against actual assertions. When the task intentionally changes a contract, implement the agreed task requirements and report the affected specification paths/sections for subsequent synchronization; do not treat the previous behavior as a prohibition on the requested change.

Use the plan's acceptance criterion → contract/source → change → verification mapping as the handoff. Recheck the current working tree before editing; distinguish pre-existing changes from task changes, including untracked files. If the plan is stale, update its approach and mapping within the agreed task scope rather than implementing assumptions from an older snapshot. Read an existing `review.md` when continuing reviewed work, verify whether findings still apply and address authorized fixes without overwriting review history.

For affected commands, tools and models use their single canonical [command](../../../specifications/project/src/services/command/commands.md), [tool](../../../specifications/project/src/services/ai/tools.md) and [model](../../../specifications/project/prisma/models.md) catalogs. Preserve related routing/help/aliases, provider attachment conditions, direct/deferred delivery, jobs and ownership invariants unless the task changes them. Reuse source-mirrored entity paths for any requested documentation synchronization; do not create duplicate canonical descriptions.

Before reporting completion, map each acceptance criterion to implementation evidence and an executed check or an explicit verification limitation. Update `plan.md` with actual progress, material deviations, remaining work and check results so a later review can establish what was implemented. Do not mark unverified behavior as tested or incomplete criteria as complete. Identify the source files and working-tree/commit scope to review and affected specification sections, including relevant coverage/test-map entries. A plan status or prior review does not prove the current code passes checks.

For now, do not add or modify tests unless the user explicitly requests them. Run appropriate existing checks using a suitable Node.js 22 container and isolated data; do not apply migrations to the running bot's database for validation. Report completed work, actual checks and limitations. Review and specification synchronization are separate optional steps: use `awesome-bot-review` or `awesome-bot-spec-update` when requested.

Follow [operations](../../../specifications/project/operations.md) for validation. Do not start the live bot or send VK/provider requests merely to verify a change. Use `systematic-debugging` for unexpected failures and `sql-database-assistant` for SQL/migration work when applicable. If the user already requested review or specification synchronization as part of the task, continue to those steps without asking for permission again; otherwise report the handoff without invoking them automatically.
