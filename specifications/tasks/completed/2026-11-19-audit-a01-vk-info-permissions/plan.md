## Текущий контракт и затронутые области

`createChatInfoTool` разрешает ряд действий обычному участнику, но `VkService` после `onInfoReturned` запрещает любой групповой результат без глобальной роли. Факт проверен в обработчике tools и финальной доставке; это несогласованность двух проверок.

Проверенные особенности исходного кода:

- `ChatInfoContext.onInfoReturned` сейчас не принимает аргументов.
  Callback вызывают успешные ветки `overview` группы, `members`, `member`,
  `birthdays` группы/ЛС и `membership`. `overview` ЛС возвращает только
  идентификаторы своего диалога без callback; эту особенность не менять.
- Перед выполнением tool `checkToolAccess` проверяет актуальные настройки,
  maintenance и глобальную роль. Ошибка проверки закрывает доступ.
  Ветка `membership` отдельно требует `access.isAdmin`; администратор
  беседы не заменяет эту роль.
- В `VkService` callback выставляет `vkInfoReturned`. Этот флаг также
  запрещает последующее конфликтующее действие через `getActionError`
  и исключает сохранение финального assistant-текста в историю.
  Он не должен исчезнуть вместе с ошибочным административным запретом.
- Перед финальной отправкой перечитываются роль, настройки беседы
  и maintenance. Текущий запрет `vkInfoReturned && context.isChat && !latestIsAdmin`
  отклоняет также разрешённые обычные сведения; именно его требуется заменить.
- В `member` числовой ID/reply не требует членства цели до чтения профиля;
  текстовое имя ищется по составу беседы. Поздний `findMember` добавляет
  метаданные участника. Q01-D1 не означает добавление глобального поиска
  людей по имени или изменения пагинации/кэшей внутри A01.

## Принятые ограничения

ЛС ограничены своим пользователем; `membership` не раскрывает персональные события; active/quiet/maintenance и запрет последующих конфликтующих действий сохраняются.
Запрос пользователя относится к согласованию плана. Приняты только явно выбранные ниже решения. Не менять соседние функции, бюджеты, публичные schemas и сохранённые данные без отдельного решения.

## Согласованная зависимость Q01

**Q01-D1 — принято пользователем 20.11.2026, вариант 2:** при запросе из
групповой беседы `get_chat_info.member` может выдавать любой профиль,
доступный через VK API, включая пользователей вне беседы. Членство цели
не является обязательным условием доступа. Это выбор круга профилей,
а не матрицы ролей запрашивающего: A01-D1 и A01-D2 согласованы ниже.
Ограничение ЛС своим пользователем сохраняется. Решение не распространяется
на адресатов напоминаний и не разрешает реализацию приложения.
Основание: явный ответ пользователя «2» на вопрос Q01-D1 в ходе согласования A01.

## Согласованная матрица ролей

**A01-D1 — принято пользователем 20.11.2026, вариант 1:** сохранить
разделение доступа по действию. В группе `overview`, `members`, `member`
и `birthdays` доступны обычным участникам, администраторам беседы,
администраторам бота и создателю. `membership` доступен только
администраторам бота и создателю; роль администратора беседы сама по себе
этого права не даёт. Матрица применяется и перед получением данных,
и перед выдачей результата; общий административный запрет для обычных
сведений должен быть устранён.

| Действие в группе | Участник | Администратор беседы | Администратор бота | Создатель |
| --- | --- | --- | --- | --- |
| overview / members / member / birthdays | Да | Да | Да | Да |
| membership | Нет | Нет | Да | Да |

В ЛС для всех ролей сохраняется ограничение своим пользователем;
`members` и `membership` к ЛС неприменимы, `overview` описывает свой диалог,
`member` и `birthdays` ограничены автором. Принятый Q01-D1 разрешает
внешние профили только при групповом запросе. Правила active/quiet/maintenance
и запрет конфликтующих действий сохраняются. Выбор сохраняет доступ
к обычным сведениям без расширения доступа к статистике membership.

## Согласованная передача требований доступа

**A01-D2 — принято пользователем 20.11.2026, вариант 1:** инструмент
передаёт через внутренний callback закрытую категорию доступа:
обычные сведения либо сведения, требующие администратора бота/создателя.
Обработчик объединяет требования всех успешно полученных результатов
в пределах одного ответа и перед отправкой проверяет актуальные права.
Матрица соответствия action и категории остаётся в инструменте.
Категорию задаёт код, а не модель; публичная schema инструмента не меняется.

Успешный `membership` сохраняет требование глобальной роли до конца ответа:
последующий обычный action не снимает это требование. Отзыв роли до отправки
блокирует весь ответ, содержащий такие данные; выделение и отправка отдельных
фрагментов не вводятся. Если получены только обычные сведения, отсутствие
глобальной роли само по себе не блокирует ответ. Проверки области ЛС,
active/quiet/maintenance и запрет конфликтующих действий сохраняются.
Требования живут в памяти обработки текущего ответа, без нового хранилища.

## Последовательность реализации

снять состояние рабочего дерева и отделить уже существующие изменения
других задач. Подготовить `implenent.md` по принятому контракту.
Статусы исходного `task.md` о несогласованных решениях исторические:
фактическое последующее согласование записано в данном плане и разговоре.
Не переоткрывать принятые варианты только из-за старого статуса задания.

Область A01 — авторизация tool и выдачи результата. Не переносить сюда
изменения напоминаний Q01-D2/Q02, глобальный поиск профилей по имени,
новые проверки членства цели, пересмотр TTL, публичной схемы или бюджета API.
Сохранить действующие формы ID/reply/name, их неоднозначность и ограничения.
Если выбранный Q01-D1 потребует дополнительного изменения алгоритма
разрешения цели, описать конкретное пересечение и согласовать его отдельно
до зависимых правок; не подменять этот выбор требованием членства.

### S1. Классификация результатов и входные права

В [chatInfoTool.ts](../../../../src/services/ai/tools/chatInfoTool.ts) расширить
внутренний callback категорией доступа по D2. Закрытый набор категорий
различает обычные сведения и сведения только для администратора бота/создателя;
имена типов и значений уточняются локально при детализации. Значение определяет
код успешной ветки, а не аргументы модели. Сопоставление с action находится
в tool: `membership` требует глобальную роль, остальные action — обычный доступ.

Сохранить общий `checkAccess`, отдельный входной отказ `membership`
неадминистратору до вызова сервиса статистики/VK и ограничения ЛС.
Не ужесточать `member` до запрета внешнего ID в группе. Обновить все
существующие вызовы callback: обычные результаты передают обычную категорию,
`membership` — административную. Ошибки, неприменимые и отклонённые запросы
не должны регистрироваться как успешно полученные данные. Успешное чтение
из кэша имеет ту же категорию, что чтение через VK API.

Не изменять JSON Schema, имена action, формат публичного результата,
лимиты разделов, профилей, страниц и дней. Проверить совместимость
существующих callers и callback-заглушек без обязательного изменения
репозиторных тестов. Критерии: AC-1, AC-2.

### S2. Объединение требований и проверка перед выдачей

В [vkService.ts](../../../../src/services/vk/vkService.ts), рядом с состоянием
текущего ответа и callback `createChatInfoTool`, собирать требования
всех успешно возвращённых сведений. Требование глобальной роли монотонно:
после `membership` обычные результаты не могут его снять. Одновременно
сохранять факт получения любых сведений для прежних guards.

Использовать существующее повторное чтение `latestIsAdmin`, настроек
и maintenance перед финальной отправкой. Вместо общего запрета для любых
сведений группы проверять наличие административного требования и актуальную
глобальную роль. Только обычные сведения не требуют этой роли; `membership`
требует её и при получении, и при выдаче. Повышение роли после отказа
на входе не запускает ранее отклонённый запрос автоматически.

При отзыве необходимой роли не отправлять составленный моделью ответ
целиком, поскольку он может смешивать результаты нескольких action.
Сохранить существующую форму короткого отказа без цитирования полученных данных;
не пытаться выделять разрешённые абзацы, повторно вызывать VK или генерировать
новый ответ. При сбое повторной проверки прав данные также не выдаются.
Критерии: AC-2, AC-3.

### S3. Сохранение ограничений маршрута и истории

В [vkService.ts](../../../../src/services/vk/vkService.ts) проследить путь
от регистрации callback через model-tool loop до `deliverAssistantMessage`
и записи истории, включая ранние return и внешний catch.
`getActionError` должен по-прежнему запрещать конфликтующее действие после
получения сведений VK. Исключение административного запрета не разрешает
обход maintenance, quiet или отрицательного решения active mode.

Сохранить `commandResultDelivered`/`messageDeliveryGuard.hasAttempted`,
условие отсутствия записи assistant-ответа с VK-данными в историю и существующие
правила доставки/неопределённого исхода send. Не добавлять новую доставку
через tool, fallback с данными, автоматические повторы или запись сырых
профилей в логи. Критерий: AC-4.

## Проверки и имеющиеся свидетельства

Восемь сценариев [chatInfoTool.test.ts](../../../../test/chatInfoTool.test.ts)
проверяют страницы участников, дни рождения группы/себя в ЛС, общий входной
отказ, административный membership, отказ участнику, неприменимость в ЛС
и предел периода. Callback в них подменён заглушкой без проверки категории.
Полная матрица финальной выдачи и отзыв роли этими assertions не подтверждаются.
Существующие относящиеся файлы: [chatInfoTool.test.ts](../../../../test/chatInfoTool.test.ts), [vkMessageDeliveryIntegration.test.ts](../../../../test/vkMessageDeliveryIntegration.test.ts).
При исполнении использовать существующие проверки `npm run check` и при необходимости `npm run build` внутри изолированного Node.js 22 согласно [operations](../../../project/operations.md). Проверки специфичных сценариев из таблицы выполнить с подменёнными внешними вызовами/синтетическими данными; БД-гонки проверять на отдельной временной SQLite, а не на рабочем файле.
Новые и изменённые репозиторные тесты не требуются без явного запроса пользователя: недостающие сценарии допускается проверить временно вне `test/`. Наличие старого теста не подтверждает непроверенную ветвь. Во время текущего планирования runtime-проверки не выполнялись.

Для недостающих проверок подготовить временный стенд вне репозитория:
подменить VK/provider, роль и настройки, управляемо менять их между успешным
результатом tool и финальной отправкой. Фиксировать число обращений к API,
категории callback, фактически отправленный текст и вызовы записи истории.
У сценариев смешанного ответа проверить оба порядка вызовов, чтобы обнаружить
ошибочную замену накопленного требования последним результатом.
Проверять реальные production callback/guard, а не их копию в стенде.

Изолированная копия не должна содержать рабочую `.env`, базы и логи.
Перед Node.js-командами проверить конфигурацию container CLI; использовать
Node.js 22.13+ и синтетические данные, без сети VK/AI и запуска бота.
Фокус существующих проверок: `node --import tsx --test test/chatInfoTool.test.ts`
и `node --import tsx --test test/vkMessageDeliveryIntegration.test.ts`,
затем `npm run check` и `npm run build` по необходимости.
В предыдущем ревью другой задачи интеграционный файл падал на установке mock
для `prisma.apiUsage.create`; это историческое ограничение, которое нужно
проверить на актуальном снимке и отделить от результатов A01, а не молча
исправлять посторонний сценарий или объявлять общий check успешным.
