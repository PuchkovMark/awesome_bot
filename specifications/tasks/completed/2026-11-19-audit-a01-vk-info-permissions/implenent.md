## Принятые решения и границы

Принятые ответы пользователя последовательно записаны в [plan.md](plan.md):

- **Q01-D1=2:** в группе разрешён любой профиль, доступный через VK API,
  включая внешние профили. Членство цели не является обязательным условием.
  ЛС остаются ограничены автором. Это не выбор политики адресатов напоминаний.
- **A01-D1=1:** обычные сведения доступны всем четырём ролям;
  `membership` — только администратору бота и создателю.
  Администратор беседы без глобальной роли не получает `membership`.
- **A01-D2=1:** tool передаёт внутреннюю категорию доступа;
  VK-обработчик объединяет требования успешных результатов и проверяет
  актуальную роль перед отправкой. Один успешный административный результат
  делает весь смешанный ответ требующим этой роли. Последующий обычный
  результат не снимает ограничение. Фрагменты ответа отдельно не выделяются.

Исторические формулировки `task.md` о непринятых D* не переоткрывают эти
решения: они приняты позднее и зафиксированы в общем плане.
AC-3 задания применяется с согласованным D2: для ответа только с обычными
сведениями глобальная роль не нужна; при смешанном ответе после отзыва
необходимой роли блокируется весь текст модели.

| Область / action | Участник | Администратор беседы | Администратор бота | Создатель |
| --- | --- | --- | --- | --- |
| Группа: overview / members / member / birthdays | Да | Да | Да | Да |
| Группа: membership | Нет | Нет | Да | Да |
| ЛС: overview своего диалога | Да | Да | Да | Да |
| ЛС: member / birthdays автора | Да | Да | Да | Да |
| ЛС: members / membership | Неприменимо | Неприменимо | Неприменимо | Неприменимо |
| ЛС: чужой профиль | Нет | Нет | Нет | Нет |

Матрица действует при сохранении остальных условий: maintenance,
quiet, решение active mode, текущая беседа и запрет конфликтующих действий.
`settingsService.isAdmin` уже включает создателя через `getRole`;
проверку администратора беседы вместо него не добавлять.

Сохранять публичный JSON и schema `get_chat_info`, имена action,
пагинацию, лимиты полей/разделов/дней, TTL и ключи кэшей.
Новых команд, tools, сервисов, зависимостей, таблиц, миграций и настроек нет.
Реализация ограничена двумя исходными файлами ниже; постоянные тесты
без отдельного запроса не добавлять и не менять.

## Текущий поток и необходимые изменения

### Инструмент

В [chatInfoTool.ts](../../../../src/services/ai/tools/chatInfoTool.ts)
`ChatInfoContext.onInfoReturned` имеет тип `() => void`.
`execute` валидирует аргументы, вызывает `requireAccess`, проверяет область,
отдельно запрещает `membership` при `!access.isAdmin`, получает данные
и возвращает JSON. Успешные VK-ветки сообщают результат callback:
`birthdays` ЛС, `membership`, `overview` группы, `members`, `birthdays`
группы и `member`. `overview` ЛС не читает VK и не вызывает callback.

Профили/страницы могут возвращаться из существующих кэшей; это не отменяет
авторизацию на входе `execute` и категорию успешного результата.
`getVkUserInfo` может вернуть общий `result` при успехе части разделов;
такой публичный результат также должен учитываться callback.

### VK-обработчик

В [vkService.ts](../../../../src/services/vk/vkService.ts) локальный
`vkInfoReturned` выставляется callback и выполняет три разных функции:

1. `getActionError` запрещает последующее изменяющее действие или прямую
   отправку через `send_vk_message` после получения VK-данных.
2. Финальный guard требует глобальную роль для любых сведений группы.
   Это ошибочная часть, которую требуется заменить.
3. `if (!vkInfoReturned)` исключает assistant-текст с VK-данными из истории.

`checkToolAccess` читает актуальные роль, настройки и maintenance,
а при ошибке возвращает отказ. Callback обёрнут отдельными условиями
active-решения и запрета чтения после действия. После завершения provider
финальная ветка повторно читает `latestChatSettings`, `latestIsAdmin`
и `latestMaintenance`, проверяет доступ, затем вызывает
`deliverAssistantMessage` и условно сохраняет историю.

`sendChatCompletion` исполняет tool calls последовательно, в том числе
несколько вызовов в одном ответе. Требования поэтому должны сохраняться
между вызовами одного ответа, но не между сообщениями пользователя.

## Шаги реализации

### I0. Входная сверка

Зависимости: разрешение пользователя на реализацию и текущие документы.
Перед правками проверить `git status`, относящийся diff и перечисленные
символы: рабочее дерево содержит изменения других задач.
Не откатывать и не форматировать посторонние изменения.

Перечитать callback, все его вызовы, guards и provider arrays.
В основном/active запросе должен остаться тот же `get_chat_info`;
в `questionnaireOnly` и субагенте его не добавлять.
Прочитать актуальные тестовые фикстуры прежде чем использовать их в стенде.
Если другой задачей уже заменён внутренний контракт доступа/доставки,
согласовать конкретное пересечение до зависимых правок.

### I1. Добавить категорию во внутренний callback

Зависимости: I0, A01-D1/D2.  
Изменяемый файл: [chatInfoTool.ts](../../../../src/services/ai/tools/chatInfoTool.ts).  
Символы: `ChatInfoContext`, `createChatInfoTool`, успешные ветки `execute`.

1. Рядом с `ToolAccess` объявить закрытый union, например
   `type ChatInfoAccessRequirement = 'public' | 'bot_admin'`.
   Названия — локальная детализация принятых двух категорий.
2. Изменить поле контекста на
   `onInfoReturned: (requirement: ChatInfoAccessRequirement) => void`.
   Не включать категорию в JSON Schema, аргументы `execute` или публичный JSON.
   Отдельного файла и публичного helper API для двух значений не требуется.
3. В успешной ветке `membership` передавать `'bot_admin'`; в пяти остальных
   существующих местах callback — `'public'`. Связь action/категории остаётся
   в tool. Callback не вычисляет требования по сгенерированному моделью тексту.
4. Оставить текущий порядок проверки `access.isAdmin` перед
   `getMembershipStats`/`membershipService.getStats`; отказ не вызывает
   ни сервис, ни VK и не регистрирует успешный административный результат.
   Аналогично не добавлять callback к `not_applicable`, `not_executed`
   и общему `error`.
5. Не добавлять callback для `overview` ЛС: он возвращает только идентификаторы
   авторского диалога и не меняет прежний жизненный цикл VK-данных.
   Частично успешный `member` с общим `status='result'` учитывается как обычный
   успешный результат, как и полностью успешный.

Существующие callback-заглушки тестов без аргументов совместимы с новым
типом функции; не менять их только ради принятия неиспользуемого параметра.
Сходное поле старого `VkInfoContext` в
[vkInfoTool.ts](../../../../src/services/ai/tools/vkInfoTool.ts) относится
к другому контракту: не расширять его автоматически.

Критерии: AC-1, входная часть AC-2. Проверка: unit-набор tool и временная
фиксация последовательности категорий успешных/отклонённых вызовов.

### I2. Накопить требования ответа и заменить финальный guard

Зависимости: I1.  
Изменяемый файл: [vkService.ts](../../../../src/services/vk/vkService.ts).  
Символы: локальные `vkInfoReturned`, `createChatInfoTool` callback,
финальная проверка перед `deliverAssistantMessage`.

1. Рядом с `let vkInfoReturned = false` добавить локальный флаг
   `let vkInfoRequiresAdmin = false`. Оба принадлежат текущему `handleMessage`
   и не живут на экземпляре сервиса, в кэше или БД.
2. В callback `onInfoReturned(requirement)` сохранять
   `vkInfoReturned = true`, а административный флаг обновлять монотонно:
   `vkInfoRequiresAdmin ||= requirement === 'bot_admin'`.
   Не присваивать ему категорию последнего вызова и не сбрасывать при ошибке
   следующего tool. Отказавший `membership` не должен выставлять этот флаг.
3. Удалить условие общего административного отказа
   `vkInfoReturned && context.isChat && !latestIsAdmin`.
   Вместо него использовать
   `vkInfoRequiresAdmin && !latestIsAdmin` с существующим повторным чтением роли.
   Административный callback достижим только для группового `membership`;
   обычные сведения ЛС/группы сами по себе глобальную роль не требуют.
4. Сохранить существующий короткий отказ без данных VK и последующий `return`
   при несоответствии административному требованию. Не отправлять смешанный
   `resp.content`, не фильтровать абзацы, не запрашивать данные/ответ повторно.
   Успешный обычный action после `membership` не понижает защиту.
5. Не подменять `latestIsAdmin` исходным снимком `access.isAdmin` и не
   использовать роль администратора беседы. При ошибке повторного чтения
   Promise отклоняется в существующий внешний catch; он не отправляет
   `resp.content`, поэтому данные остаются закрыты. Новый retry не вводится.

`checkToolAccess` не переводить в глобальный admin-only режим:
этот общий helper используется и другими tools. Глобальная роль требуется
только там, где указано принятой матрицей, при сохранении общих режимов.

Критерии: выходная часть AC-2, AC-3. Проверить обе перестановки mixed tools,
несколько обычных результатов, отзыв роли и ошибку повторного чтения.

### I3. Проверить сохранность маршрута, истории и границ целей

Зависимости: I1–I2. Новых исходных файлов не добавлять.

- В `getActionError` сохранить `vkInfoReturned`, а не заменить его
  административным флагом. После любого VK-результата прямой
  `send_vk_message`, `beginAction` и остальные конфликтующие действия
  должны сохранять прежний отказ. Это закрывает обход финального guard
  прямой tool-доставкой.
- Не менять `commandResultDelivered`, `messageDeliveryGuard.hasAttempted`,
  active decision и `questionnaireOnly` early returns. Сохранить проверки
  актуальных maintenance/quiet/смены active после получения обычных данных.
- Не менять `if (!vkInfoReturned)` вокруг `memoryService.addMessage`
  для assistant-ответа. Не добавлять хранение категорий/сырого результата
  в историю, память или логи. Существующая автоматическая обработка
  исходного сообщения пользователя не расширяется данными VK.
- Не менять `deliverAssistantMessage`, озвучку, reply/anchor, разбиение,
  uncertain guard и существующий короткий текст предупреждения.
  После неясного исхода не повторять содержательный ответ.
- Сохранить серверные `senderId`/`peerId` и ограничение чужого профиля в ЛС.
  Внешний числовой ID/reply в группе не получает нового запрета членства.
  Текстовое имя продолжает разрешаться существующим `findMember`;
  нет нового users.search, выбора первого совпадения или внешней адресации.
  Наличие/отсутствие `participant` в ответе не является новой авторизацией.

Не превращать A01 в переработку Q01. Текущий поздний `findMember` может
завершить запрос ошибкой при недоступном составе; изменение его обработки
ошибок не согласовано в A01. Если входная сверка покажет необходимость
менять этот алгоритм ради отдельного сценария Q01, согласовать пересечение,
не вводя молча новую политику данных или fallback.

Критерий: AC-4. Спецификации, описывающие прежний общий запрет, не являются
основанием сохранить его вопреки принятому A01-D1.

по [operations](../../../project/operations.md). Перед выбором launcher получить
актуальную конфигурацию container CLI. Точный локальный image зависит
от среды; `docker compose up --build` не использовать как проверку,
поскольку он запускает бот и миграции рабочей БД.
В изолированной копии запланированы команды:

```sh
npm ci
npm run prisma:generate
node --import tsx --test test/chatInfoTool.test.ts
node --import tsx --test test/vkMessageDeliveryIntegration.test.ts
node --import tsx --test .a01-validation/chatInfoPermissions.test.ts
npm run check
npm run build
```

Это будущие команды, а не свидетельство выполнения. Установку/генерацию
проводить только в копии; необходимые ограничения сети/образа сообщить отдельно.
Если временной БД действительно нужны миграции, перед стендом выполнить
`npx prisma migrate deploy` с `DATABASE_URL`, указывающим на новый файл
этой изолированной копии. Никаких migrations на operational DB.
Результаты существующего unit-набора, integration, временного стенда,
общего check и build сообщать раздельно, с количеством сценариев и
ограничениями. Посторонний сбой integration не исправлять молча,
не скрывать и не считать успешным check по одному успешному build.

без новых схем, политики ролей или алгоритма разрешения целей.

После реализации отдельным разрешённым этапом через
`awesome-bot-spec-update` синхронизировать:

  проверить согласованность описания, не приписывая ему новый role guard;
- [карту тестов](../../../project/test/README.md) и
  [реестр покрытия](../../../project/coverage.md): только фактически изменившиеся
  контракты и assertions; временный стенд не объявлять репозиторным набором.

Задача завершена после I1–I3, выполнения проверок всех AC
с сообщёнными результатами/ограничениями и необходимой синхронизации
канонических контрактов. Подготовленный документ и старые успешные
проверки не доказывают выполнение этих условий.

Исполнитель следует [task.md](task.md), [plan.md](plan.md) и этому документу.
При новом выборе, устаревании плана или необходимости изменить согласованное
решение сначала описать проблему в чате и задать пользователю один вопрос,
затем ждать ответа до зависимых правок, продолжая независимую работу.
Во время реализации любые планы доступны только для чтения: без специального
указания пользователя нельзя менять статусы, прогресс и результаты проверок.
Согласие с решением или общее поручение реализовать задачу не разрешает
редактировать планы. Прогресс и результаты сообщаются в чате.
Текущий запрос разрешает создание этого документа и не начинает реализацию.
