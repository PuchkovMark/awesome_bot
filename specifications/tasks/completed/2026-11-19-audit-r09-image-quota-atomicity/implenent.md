## Конкретный протокол данных

### Схема

В [schema.prisma](../../../../prisma/schema.prisma) добавить две модели:

| Модель | Поля и ограничения |
| --- | --- |
| ImageDailyQuota | vkUserId String; utcDay String (YYYY-MM-DD); used Int default 0; legacyUsed Int default 0; createdAt DateTime default now; updatedAt DateTime updatedAt; составной PK vkUserId+utcDay; обратная relation attempts. |
| ImageQuotaAttempt | operationId String PK; vkUserId String; utcDay String; feature String; status String default reserved; createdAt DateTime default now; updatedAt DateTime updatedAt; составной FK vkUserId+utcDay к дневной модели с onDelete Restrict; индекс vkUserId+utcDay. |

В сервисе feature ограничен union `image_generate | image_edit`,
status — `reserved | consumed | uncertain | released`.
SQLite enum не вводить. Не хранить prompt, картинку, стоимость или беседу;
не связывать VK ID с внутренним User.id.

Инвариант: used = legacyUsed + количество попыток дня со status != released.
Не обрезать legacyUsed при превышении лимита. Видимая после commit дневная запись
служит признаком завершённого seed. Автоочистки, TTL-release и фоновых retries нет.

### Внутренний API и транзакции

Новый [imageQuotaService.ts](../../../../src/services/image/imageQuotaService.ts):
класс ImageQuotaService, default экземпляр с
[общим Prisma client](../../../../src/db/client.ts).
В тестах передаются отдельный клиент и управляемые часы; конструктор без I/O.

`reserve({ operationId, vkUserId, feature })` возвращает один из результатов:

- `{ status: 'reserved', operationId, utcDay, reservedAt }`;
- `{ status: 'limit_reached' }`;
- `{ status: 'already_processed' }`.

Время Date берётся один раз при входе; из него вычисляются utcDay и границы
[dayStart, dayEnd). reservedAt используется затем для image-specific ApiUsage.
OperationId создаётся через randomUUID один раз на invocation.
Это не дедупликация доставки событий VK.

Одна короткая Prisma interactive transaction:

1. Первое SQL-действие — параметризованный INSERT OR IGNORE дневной строки
   с нулевыми счётчиками и явными timestamps. Не начинать с SELECT/count.
   Использовать Prisma tagged template, фиксированные имена таблиц и Date bindings.
   Число вставленных строк определяет, нужна ли инициализация.
2. Если строка создана, tx.apiUsage.count считает только заданного автора,
   две image features и createdAt >= dayStart AND < dayEnd. Полученное значение
   записывается в used и legacyUsed внутри той же транзакции.
   Для существующего счётчика usage больше не пересчитывается.
3. Найденный operationId возвращает already_processed без нового допуска.
   Несовпадение автора/feature — ошибка. Даже reserved после рестарта
   не разрешает повторный запуск генератора.
4. Условный updateMany user+day+used < limit увеличивает used на 1.
   Ноль изменённых строк — limit_reached; созданный счётчик можно сохранить.
5. После успешного increment создать reserved попытку. Ошибка создания
   откатывает всю транзакцию. Допуск возвращается только после commit.

Первый write нужен для сериализации конкурирующих writers до чтения seed.
Не заменять атомарность локальным mutex. Не добавлять ручной BEGIN внутрь Prisma,
новые зависимости, PRAGMA/WAL или настройки durability.
Ошибки блокировки/БД не считаются исчерпанным лимитом и не разрешают генерацию.
Автоматических повторов транзакций нет; ограничения движка проверить на fixture.

`finish(operationId, outcome: 'consumed' | 'uncertain' | 'released')`:
guarded update только из reserved. В той же транзакции только успешный
reserved → released уменьшает used соответствующего дня.
Повтор терминального перехода не меняет расход; конфликтующий поздний outcome
не переводит consumed/uncertain в released.
Неизвестный ID — ошибка. Нарушение счётчика откатывает release, не маскируется max(0).
При сбое finish исходный reserved продолжает занимать место.

### Классификация исходов генерации

В [imageError.ts](../../../../src/services/image/imageError.ts) добавить
ImageNotExecutedError с cause и isImageNotExecutedError.
Это доказательство границы кода, а не предположение по тексту/HTTP-коду.

В [ImageGenerationService](../../../../src/services/image/imageGenerationService.ts):

- generate: отдельно получить OpenAI client; отсутствие конфигурации
  до images.generate обернуть ImageNotExecutedError.
- edit: обернуть только downloadPhoto; editBuffer: отдельно обернуть Sharp,
  toFile и получение клиента до images.edit.
- Не включать сам API-вызов или разбор ответа в catch ранней подготовки.
  Moderation/HTTP-ошибка после обращения, таймаут, пустой ответ/буфер —
  uncertain, без возврата. Сохранить исходные безопасные сообщения и причины.
- Готовая картинка — consumed до доставки в VK.
  Если финализация БД падает, журналировать и продолжить доставку:
  резерв уже занимает место. Повторной генерации нет.
- ImageNotExecutedError — released. При ошибке release место остаётся занятым;
  нельзя обещать успешный возврат.
- Ошибка доставки после готовой картинки не вызывает release.

## Согласованные границы и инварианты

Из задания и общего плана сохраняются следующие требования:

- Одна квота на `vkUserId` за UTC-сутки для `image_generate` и `image_edit`,
  общая для команд и AI tool, личных диалогов, бесед и процессов с общей базой.
- Размер лимита сохраняется. Вызовы мемов и приключений не включаются в эту квоту
  только потому, что используют тот же генератор.
- После подтверждённой генерации ошибка отдельной статистики не создаёт место.
- Сетевые обращения к VK/OpenAI не должны удерживать транзакцию квоты.
- Сохраняются входная JSON Schema, область выбора фото current/reply, адресат
  доставки и защита от дублирующего обычного ответа после отправки.
- Технические записи квоты не изображаются как оплаченные запросы или стоимость.
- При переходе и повторном запуске учитываются существующие сегодняшние usage,
  без потери расхода и двойного подсчёта.

20.11.2026 пользователь согласовал R09-D1: отдельные устойчивые записи квоты
и резервирований, независимо от `ApiUsage`.

способ изменения проверки подлежит указанному выше согласованию.

**Проверка:** Q01–Q07 и существующие пять сценариев image tool;
изменения guards соседних задач не подменяются предположениями.

### R09-I4. Обеспечить переход данных, рестарт и UTC-день — S3

**Зависимости:** D1–D3, R09-I1, согласованный порядок переключения writers.

**Материалы:** [schema.prisma](../../../../prisma/schema.prisma),
[существующие миграции](../../../../prisma/migrations/),
выбранный сервис квоты и интеграция в [VkService](../../../../src/services/vk/vkService.ts).
Новую миграцию нужно добавить отдельной папкой после выбора схемы;
существующие применяемые миграции не переписываются.

Конкретизировать однократный учёт сегодняшних `image_generate`/`image_edit`,
маркер завершения инициализации и согласованную UTC-привязку новой попытки.
Одна и та же новая генерация не должна попасть в расход через резервацию и снова
через usage. Отдельно определить обработку старых in-flight writers при переключении:
поздняя запись старого кода после инициализации иначе может потеряться.
Самовольное предположение о допустимости одновременной работы старой и новой версии
недопустимо. Рестарт не считается доказательством, что внешняя операция не выполнялась.

**Проверка:** Q08–Q11, свежая синтетическая база и обновление существующей схемы
на синтетических данных. Миграции рабочей базы не являются проверкой.

### R09-I5. Проверить результат и синхронизировать контракты — S4

**Зависимости:** готовые R09-I1–I4 и согласованный способ регрессионных проверок.

Выполнить матрицу AC, затем существующие проверки проекта и сборку
в изолированном контейнере. По фактической реализации актуализировать перечисленные
ниже канонические разделы в разрешённой области через профильный навык.
Не вписывать результаты выполнения или отметки прогресса в планы во время реализации.

### Существующие проверки и их ограничения

[imageTool.test.ts](../../../../test/imageTool.test.ts) содержит пять тестов:
успешная генерация/редактирование, отсутствие фото, доступ/порог лимита и ошибка
генератора. `dailyCount` — заданное число; usage и доставка — массивы/mock.
Assertion порога проверяет статус и отсутствие отправки, но не отсутствие вызова
генератора и не SQLite-конкуренцию. Ошибка генератора задана обычным `Error`;
это не доказательство реального отказа провайдера без исполнения.

[vkMessageDeliveryIntegration.test.ts](../../../../test/vkMessageDeliveryIntegration.test.ts)
даёт основу для изолированного VK route и проверок подавления дублирующего ответа,
но не воспроизводит гонку image command/tool или устойчивую дневную квоту.
Карта тестов сама по себе не является результатом запуска.

### Команды будущей проверки

Базовые команды контейнеров подтверждены настройками среды: `docker` и
`docker compose`. Во время этой подготовки контейнеры и приложение не запускались.
Ниже — сценарий для отдельной копии исходников внутри контейнера, без подключения
рабочей базы, логов и секретного окружения. Исходники подключаются только для чтения,
зависимости, generated client и результаты сборки остаются внутри контейнера.

```sh
docker run --rm \
  --mount "type=bind,src=/home/mark/Projects/src/awesome_bot,dst=/source,readonly" \
  --workdir /work \
  --env DATABASE_URL=file:/work/r09-validation.db \
  --env VK_TOKEN=r09-test-token \
  --env LOG_LEVEL=silent \
  node:22-alpine sh -eu -c '
    apk add --no-cache openssl
    cp /source/package.json /source/package-lock.json /source/tsconfig.json /work/
    cp /source/eslint.config.js /source/tsconfig.eslint.json /work/
    cp /source/.prettierrc /source/.prettierignore /work/
    cp -R /source/src /source/test /work/
    mkdir /work/prisma
    cp /source/prisma/schema.prisma /work/prisma/
    cp -R /source/prisma/migrations /work/prisma/
    npm ci
    npm run prisma:generate
    node --import tsx --test test/imageTool.test.ts test/vkMessageDeliveryIntegration.test.ts
    npm run check
    npm run build
  '
```

В команду включены проверенные [eslint.config.js](../../../../eslint.config.js),
[tsconfig.eslint.json](../../../../tsconfig.eslint.json),
[.prettierrc](../../../../.prettierrc) и [.prettierignore](../../../../.prettierignore).
Команды генерации/apply миграции и запуска Q01–Q11 будут добавлены после D1–D3
и выбора места harness: пока отсутствуют согласованные схема и сами проверки.
Миграции допускаются здесь только к синтетической `r09-validation.db`.
`docker compose up --build` не используется как проверка: он запускает приложение
и миграции с рабочими mount/env. Ошибки получения образа/зависимостей фиксируются
как ограничения среды, а не как успешное прохождение сценариев.
