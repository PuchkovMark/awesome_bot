### R10-I1. Описать контракт выбора и приёма ночного действия

**Соответствие общему плану:** S1, S2. **Зависимости:** R10-I0.
**Изменяемый файл:** [mafiaService.md](../../../project/src/services/games/mafiaService.md), раздел «Обсуждение, голосование и ночь».
**Источники:** `privateActionText`, `getSessionsForPlayer`, `handlePrivateMessage`, `submitNightAction`, `hasProcessed`, `persist` в [mafiaService.ts](../../../../src/services/games/mafiaService.ts), `parseNightAction` в [mafiaEngine.ts](../../../../src/services/games/mafiaEngine.ts).

Сейчас раздел описывает роли, разрешение ночи и личные результаты, но не выбор исходной беседы. Расширить его последовательным описанием следующих стадий; существующее описание дневного голосования и разрешения ночи сохранить.

1. **Синтаксис и значение ID.** Описать существующие формы `беседа <ID> <действие>` и `чат <ID> <действие>`. Префикс распознаётся без учёта регистра по текущему шаблону:

   ```text
   /^\s*(?:беседа|чат)\s+(\d{10})\s+(.+)$/iu
   ```

   ID — ровно 10 цифр `conversationId`/VK peer исходной беседы, сравниваемых строкой. Это не ID сессии, не короткий номер чата и не номер игрока. `<действие>` затем отдельно проверяется по роли. Примеры с условными ID: `беседа 2000000001 убить 3`, `чат 2000000002 лечить 3`, `беседа 2000000001 проверить 3` — каждый допустим только для соответствующей роли и подходящей партии.

   Без префикса сначала действует фильтр `privateActionText`, затем `parseNightAction`. Описать обычные примеры `убить 3`, `лечить 3`, `проверить 3`; голый номер `3` поддерживается для убийства/лечения соответствующих ролей, но не для расследования комиссара. Цель парсится как номер 1–15, а при приёме должна существовать в списке и быть живой. Не расширять доступный синтаксис по одному только `parseNightAction`: например, `проверь 3` без префикса не проходит внешний фильтр, хотя `беседа 2000000001 проверь 3` допускается обоими парсерами для комиссара/Дона. Не обещать адресацию ночной цели по имени или VK ID.

2. **Предварительный отбор.** `getSessionsForPlayer` читает мафию в состояниях БД `waiting|active|paused`, затем оставляет только сессии, где пользователь есть в `players`. `eligible` дополнительно требует совпадения указанного ID, если он задан, фазы `night`, живого игрока с ненулевой ролью и успешного разбора действия для этой роли. Проверка живой допустимой цели выполняется позже и не участвует в выборе партии.

3. **Ноль, одна и несколько партий.** Ноль подходящих сессий означает `null` от приватного обработчика, без записи хода и без самостоятельного специального сообщения «нет партии». Одна сессия выбирается для повторной проверки. При нескольких возвращается существующее уточнение со списком их `conversationId` и примером `беседа <ID> убить 3`; ход не записывается и первая/newest сессия не выбирается. Явный чужой ID не добавляет кандидата и не даёт доступ к чужой партии.

4. **Повторное чтение под lock.** Для единственного кандидата используется `serializeGameConversation(selected.conversationId, ...)`: блокировка относится к исходной беседе, а не peer личного диалога. Внутри повторно читается активная сессия; отсутствие сессии или несовпадение её `id` с выбранным даёт `null`. Проверка `hasProcessed` при переданном `eventId` также может вернуть `null`. Новый активный набор в той же беседе не подставляется вместо ранее выбранной партии.

5. **Проверки актуального состояния.** `submitNightAction` заново проверяет ночь, живого участника, роль и разбор действия, затем живую цель. Сохранить ограничения: мафия/Дон не атакуют союзника мафии; маньяк не атакует себя; комиссар/Дон не проверяют себя; повторное самолечение доктора после использования запрещено. Эти отказы возвращают текст; не объединять их с предварительным `null` или уточнением нескольких партий.

6. **Запись и дедупликация.** Новый допустимый ход заменяет прежний того же вида у этого игрока; изменение выбора до конца ночи допустимо и отличается от повторной обработки одного события. Событие при наличии `eventId` и обновление состояния записываются через существующий `persist` с unique-дедупликацией и CAS. Отсутствие `eventId` не даёт гарантии дедупликации по событию. Достаточно сослаться на уже существующее описание транзакции и конфликта в этом документе, не дублируя полный контракт хранения.

7. **Результат и приватность.** При неполном наборе ходов возвращается подтверждение записи; при получении всех обязательных ходов разрешается ночь и публикуется штатный итог в исходной беседе. Результаты расследований доставляет `deliverInvestigations` лично инициаторам. Уточнение выбора содержит только ID доступных бесед; не публикует секретный ход/роль в группе. Сослаться на точный контракт адаптера из следующего шага для интерпретации `null` и выбора family.

### R10-I2. Уточнить приоритет личной игры и сохранение family

**Соответствие общему плану:** S2, S3. **Зависимости:** R10-I0, R10-I1.
**Изменяемый файл:** [gameInteractionService.md](../../../project/src/services/games/gameInteractionService.md), разделы «Публичный контракт и поиск», «Разрешение текущей игры и дедупликация»; при необходимости уточнить оговорку строки `mafia` в «Матрице делегирования».
**Источники:** `GameInteractionService.handle`, `GameInteractionRequest`, `textResult` в [gameInteractionService.ts](../../../../src/services/games/gameInteractionService.ts), `hasPendingPrivateAction`/`shouldHandleMessage` в [mafiaService.ts](../../../../src/services/games/mafiaService.ts).

Текущую общую формулировку о личном ночном ходе уточнить до порядка выполнения:

- Обычный список `sessions` ограничен текущим peer из контекста. Поиск личного ночного действия мафии отдельно смотрит партии пользователя в исходных беседах; ID в `value` не заменяет текущий контекст.
- Для `inspect` в ЛС возвращается `info`: список локальных игр и булев признак доступного ночного действия. `hasPendingPrivateAction` требует ночь и живого участника с ролью кроме `villager`, но не выбирает сессию, не сообщает роль и не проверяет конкретный текст хода. Это не обещание, что ход ещё не отправлен.
- Специальная личная ветвь выполняется только при `isChat=false`, `game=current|mafia`, `action=answer|vote|command` и положительном `shouldHandleMessage`. Пустой `value` для этих действий отклоняется раньше. В этой ветви все три действия передают исходный обрезанный по краям `value` в мафию; дневное `голосую за ...` не добавляется.
- При `game=current` и хотя бы одной локальной сессии возвращается `not_executed` с просьбой выбрать игру. Это относится ко всему найденному локальному списку, включая ожидающие и приостановленные игры. Даже префикс беседы в тексте хода не отменяет этот конфликт family.
- При явном `game=mafia` наличие личной игры не блокирует делегирование ночного хода. Однако MafiaService всё ещё требует однозначного выбора партии; при нескольких нужно указать беседу в `value`.
- Явное `game=standard` не входит в личную ветвь мафии и сохраняется при фильтрации локальных сессий. Не описывать подмену явного family на `current` или мафию и выбор первой подходящей игры.
- Если `shouldHandleMessage=false`, выполняется обычная фильтрация локальных игр по family: ноль или несколько — `not_executed`, одна — делегирование. Поэтому отсутствие подходящей ночной партии или чужой ID не означают безусловный отдельный ответ мафии: при `current` текст может обрабатываться существующей личной игрой по её правилам.
- После делегирования строка, включая уточнение MafiaService о нескольких партиях, становится `status=result`. `null` становится `uncertain` с запретом автоматического повтора. Не трактовать каждый `result` как доказательство записи хода и не превращать `null` в гарантированное «ничего не произошло».

Сохранить существующий раздел дедупликации adventure/battle: R10 не меняет его алгоритм. Добавить ссылку на раздел ночных действий [mafiaService.md](../../../project/src/services/games/mafiaService.md#обсуждение-голосование-и-ночь), не копировать туда весь ролевой парсер.

| Корректно оформленный чужой ID | В чужую сессию доступа нет; собственная партия с другим ID не подставляется. | AC-1, AC-2, AC-4 |

| `3` для комиссара; `проверь 3` без префикса; полный префикс с `проверь 3` | Голый номер не задаёт расследование; внешний фильтр и ролевой парсер имеют разные границы. Префиксная форма допускает проверку комиссара/Дона. | AC-2, AC-4 |

| До `submitNightAction` закончилась ночь, участник выбыл или действие больше не подходит его актуальной роли | Повторная проверка актуального состояния и текст отказа; старый снимок не считается достаточным. | AC-2 |
| Цель отсутствует/выбыла, атака союзника, запрещённая цель на себя | Описаны действующие целевые ограничения, ход не принимается. | AC-2, AC-4 |
| Повтор того же `eventId`; новый event с изменением выбора | Повтор распознаётся в выбранной сессии; новый допустимый ход того же вида может заменить прежний до конца ночи. Без ID гарантия event-дедупликации не обещается. | AC-2 |
| ЛС, валидный ночной ход, `current` и локальная игра, в том числе с префиксом беседы | `not_executed`: требуется выбор family до обращения к приватному обработчику. | AC-3 |
| То же, `game=mafia` | Личная игра не мешает; внутри мафии по-прежнему проверяется число подходящих партий. | AC-3 |
| То же, `game=standard` | Личная ветвь мафии пропускается; обрабатывается выбранный family по обычным правилам. | AC-3 |
| ЛС, `current`, но ночной текст не распознан или указан чужой ID | Обычная локальная маршрутизация; нельзя обещать безусловный отказ всего адаптера при наличии личной игры. | AC-1, AC-3 |
| Возврат `null` после делегирования; строка об неоднозначности | Соответственно `uncertain` без автоматического повтора и `result` с уточнением; `result` не обязательно означает запись хода. | AC-2, AC-3, AC-4 |
| Личная проверка комиссара/Дона и публикация итога ночи | Расследование отправляется лично, штатный итог — исходной беседе; уточнение выбора не раскрывает роли. | AC-2, AC-4 |
