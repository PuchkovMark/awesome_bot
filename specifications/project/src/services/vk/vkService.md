## Доставка результата приключения

`sendAdventureResult` в [исходнике](../../../../../src/services/vk/vkService.ts) вызывается callback adventure-vote job и интерактивными command/tool путями. Для reusedAttachment выполняет sendPhotoAttachment с текстом сцены; для image/imageKey/sessionId — sendPhoto, включающий upload и send. Исключение любой image-операции логируется с conversationId/sessionId и пробрасывается исходным, без второго текстового send. Это относится и к ошибке до send: автоматическая текстовая доставка в такой ситуации не гарантируется. Text-only результат отправляется один раз обычным send.

После успешного sendPhoto сбой `recordImage` перехватывается отдельно и только логируется. Job изолирует ошибку каждого результата и продолжает обход; прямой command caller может вернуть общую ошибку команды, не повторяя сцену. В model-tool caller attempted/beginAction до исполнения препятствуют повтору изменяющего действия в том же ответе. Новых retries/хранилища доставки нет; сохранённая сцена восстанавливается по [continue](../games/adventureService.md) без AI и нового игрового перехода. Это локальный контракт приключения, а не общий новый тип исхода доставки для остальных медиа.

## Запуск и состояние процесса

Конструктор создаёт VK-клиент из `VK_TOKEN`, опционально разбирает `VK_GROUP_ID` в числовой polling group ID и создаёт отдельный `vkPublicApi` только при наличии `VK_SERVICE_TOKEN`. Лимитер экземпляра получает `MAX_REQUESTS_PER_MINUTE` с окном 60 секунд. В памяти экземпляра также живут кэш имён, объединение конкурентных запросов имени и map обработанных message keys; эти структуры не переживают рестарт.

`start()` без `VK_TOKEN` пишет предупреждение и завершает работу до регистрации событий. При включённом VK сначала задаёт API membership-сервису и вызывает `characterService.initialize()`, затем регистрирует handlers, запускает Long Poll и после успешного запуска polling регистрирует meme-day, adventure-vote, reminder, long-term-memory и subagent-delivery jobs. Повторный вызов `start()` не защищён флагом идемпотентности; повторная регистрация обработчиков/задач должна рассматриваться как риск вызывающей стороны. `stop()` останавливает только VK updates, ловит и логирует ошибку остановки; cron jobs останавливаются централизованно scheduler/bootstrap. `sendMessage()` преобразует строковый peer ID в number и делегирует отправку `senderService`.

## Входящие callback `message_event`

Обработчик сначала разбирает `eventPayload` как объект или JSON-строку. Если `getSummaryHoursFromPayload` возвращает 2 или 6, выполняется специальная ветвь callback пересказа. При `null` обработчик проверяет остальные payload-действия:

1. `menu_page` — переход страницы меню; для `admin` повторно проверяется роль администратора бота;
2. `personality_select` — выбор персонажа с проверкой payload, режима обслуживания, доступа/лимитера и `characterService.select`;
3. `meme_vote` — проверка ID/value и включённого голосования, затем запись голоса и snackbar;
4. `fun_feedback` / `fun_again` — сохранение оценки либо повторная генерация только для последнего output того же пользователя/беседы; сохранение оценки дополнительно проверяет принадлежность output к peer, но не владельца;
5. прочие не-summary payload передаются дальше через `next()`.

Для summary callback проверяются режим беседы, maintenance и лимит (бот-администраторы обходят лимитер); затем по периоду загружаются недостающие имена, создаётся пересказ и редактируется сообщение с учётом признака продолжения. Отдельно `message_new` читает такой же объект из `context.messagePayload`, превращает его в команду `summary` и проходит обычный путь команды с повторной отправкой результата и клавиатуры. Ошибки callback отвечают snackbar и логируются. Полные payload, side effects, проверки и различия ветвей приведены в [каталоге команд](../command/commands.md#интерактивные-callback-действия). Кнопки создаёт [SenderService](../sender/senderService.md).

## Общий вход `message_new` и membership events

Один handler принимает `message_new`, `chat_invite_user`, `chat_invite_user_by_link`, `chat_invite_user_by_message_request`, `chat_kick_user`. Исходящие сообщения пропускаются. Дедупликационный ключ — `peerId:id`, либо `peerId:cmid<conversationMessageId>` при отсутствии обычного ID; повторы сразу пропускаются. Map очищается по записям старше 10 минут при размере свыше 5000, затем ограничивается 5000 удалением самых старых.

Для membership-события в беседе handler записывает join/leave статистику с источником события и ID участника/актора. Отдельно пользовательский join записывается через `memberService.recordJoin`; при необходимости загружается имя, строится приветствие, представление профиля или приглашение/шаблон анкеты. Для kick вызываются `memberService.recordLeave`, `gameService.handleParticipantLeave`, `mafiaService.handleParticipantLeave` и при необходимости отправляется сообщение мафии. Ошибка статистики и ошибка приветствия изолированы логированием. Далее событие завершает handler через `next()` и не попадает в обработку обычного сообщения. Полная ежедневная синхронизация состава не запускается; текущий count в [MembershipService](../membership/membershipService.md#статистика) получается только из VK, без DB fallback. Эта ветка инкрементально сверена 20.11.2026 по R07; остальные контракты документа этой сверкой не переаттестованы.

## Маршрут обычного сообщения

Порядок существенен; ранние выходы не доходят до AI:

1. Берутся sender/display name и текст; при пустом тексте беседы payload может быть загружен через VK. Из аудиовложений выбирается первое `AudioMessageAttachment`. Для него применяется пользовательская настройка и `VOICE_ENABLED`; успешная транскрипция заменяет текст и записывает usage, выключенная функция пропускает дальнейшую обработку, ошибка отправляет fallback и прекращает её; в обоих случаях непустой набранный текст смешанного сообщения сохраняется. В историю передаётся исходный набранный текст, а не транскрипт.
2. Проверяется, является ли reply сообщением бота: сначала tracked ID в `senderService`, затем VK sender/outbox признаки и при необходимости принудительная загрузка payload. Это используется для адресации и распознавания ответа на шаблон анкеты.
3. Извлекаются summary-button, image command, обычная команда, slash-префикс, profile command, явная адресация и настройки режима. Неадресованная команда с `!` в беседе (кроме profile command) пропускается. В `quiet` для обычного пользователя сообщение сохраняется в историю и не вызывается AI; исключения включают профиль участника и специальный flow заполнения анкеты.
4. `addressed` считается true для транскрибированного голоса, summary button, profile command, slash-команды или распознанного обращения/ответа боту. Если это не прямая команда, проверяется ожидающий выбор долговременной памяти. В `active` непустое неадресованное сообщение становится `activeEvent` и требует решения модели `decide_chat_response`.
5. Обычные фоновые сообщения беседы сохраняются в `memoryService`, могут запускать автоматический захват долгосрочной памяти и вероятностную авто-реакцию. Авто-реакция дополнительно ограничена настройкой, consent и атомарной отметкой интервала в `ChatSettings`, после чего ставится в пользовательскую очередь.
6. Для обрабатываемого сообщения сохраняются VK reply IDs. Если текст после удаления обращения к боту и начальных пробелов начинается с `/` (`isSlashCommand`), общий обработчик запускается сразу, вне `requestQueue`; несколько таких обработчиков могут выполняться одновременно и не ждут запросов модели. Остальные сообщения ставятся в очередь по sender ID и сериализуются между беседами. Авто-реакции используют прежнюю очередь. При отсутствии ID ответа пишется warning.

В общем обработчике повторно считываются admin, chat settings и maintenance: актуальное состояние может отменить ранее принятое решение. Это относится и к slash-командам, запущенным напрямую. Проверка частоты и ранние выходы маршрута сохраняются до выбора очереди; обход очереди не означает обход прав или лимитов. Затем выполняются ограничения длины (`MAX_INPUT_CHARS`, кроме image command), maintenance и quiet mode. Результаты исполняемых команд обычно отправляются напрямую через `senderService`; отдельная AI-ветвь собирает контекст. Профиль участника, общая/личная история, сохранённые факты, выбранная личность, системные инструкции пользователя/беседы и вложения входят в контекст по различным условиям. Полный перечень prompt-блоков и сбор конкретных вложений остаётся в исходнике; см. [медиа](../media.md) и [AI](../ai/README.md).

Просьбу послушать голосовое в сообщении, на которое ответили, модель может выполнить через [`listen_reply_voice`](../ai/tools.md#listen_reply_voice). Инструмент ищет вложение только в `replyMessage`, проверяет доступ и настройки голоса и возвращает расшифровку в контекст модели.

## AI-инструменты, действия и доставка

Фабрики создаются для текущего sender/peer. Финальный обычный набор содержит 16 tools; `save_questionnaire` добавляется только при явно адресованном групповом сообщении. Неадресованный event в режиме `active` получает ещё `decide_chat_response`; ветвь `questionnaireOnly` передаёт только `save_questionnaire`. Полные имена и остальные provider call arrays — в [едином каталоге](../ai/tools.md).

`checkToolAccess` заново читает глобальную роль бота, `ChatSettings` и maintenance; ошибка чтения закрывает доступ, maintenance запрещает не-администратору, `quiet` запрещает инструменты не-администратору в группе, а для active event состояние должно оставаться `active`. `checkReadToolAccess` дополнительно требует предварительного `respond=true` для active event и закрывает вызов после попытки доставки сообщения. Этот callback передаётся пяти инструментам: `get_current_datetime`, `get_weather`, `manage_location`, `get_subagent_status` и `listen_reply_voice`.

`get_local_chat_history` и `run_subagent` выполняются без дополнительного read/access guard: у их контекстов нет `checkAccess`, а здесь отсутствуют соответствующие привязки. Поиск авторов, pager и прямое чтение снимка не перечитывают права/режим/maintenance и не требуют active decision или отсутствия начатой доставки через эту проверку. Scope остаётся текущим `peerId`; для личного pager дополнительно передаётся `senderId`. Их доступность в обычном/active наборе и исключение из `questionnaireOnly`, входные условия маршрута и проверки перед отправкой ответа сохранены. Контракты — [`get_local_chat_history`](../ai/tools.md#get_local_chat_history) и [`run_subagent`](../ai/tools.md#run_subagent).

`beginAction` разрешает только первое действие после положительного active decision и до того, как было получено VK-сведение, начато другое действие, напрямую доставлен результат команды или начата отправка через `AiMessageDeliveryGuard`. Он сохранён в callback `startJob` прежнего фонового субагента; текущий `runDirect` его не вызывает. Контроль `isActive()` инструментов старого снимка также сохранён. Ряд инструментов имеет свои дополнительные повторные проверки; они описаны в каталоге.

Callback [`get_chat_info`](../ai/tools.md#get_chat_info) принимает закрытую
категорию `public` или `bot_admin`. Он выставляет `vkInfoReturned` для любых
успешных VK-сведений и обновляет
`vkInfoRequiresAdmin ||= requirement === 'bot_admin'`.
`membership` задаёт административную категорию, остальные полученные
сведения — обычную. Оба флага локальны одному сообщению. Смешанный ответ
сохраняет наиболее строгое требование независимо от порядка tools;
отказавший запрос membership не регистрируется как полученный результат.
Матрица action/категории находится в tool, а не дублируется в VK-обработчике.

После вызова `provider.send` сначала записывается usage. Дальше ранние выходы
подавляют дублирующий ответ после direct command/tool delivery или попытки
message delivery. Для `questionnaireOnly` ответ подавляется, если questionnaire
tool не был вызван. Active-mode event без положительного решения сохраняется
как фоновое; перед обычной отправкой повторно читаются настройки, глобальная
роль и maintenance. Только при `vkInfoRequiresAdmin && !latestIsAdmin`
короткий отказ заменяет весь текст модели. Это касается также смешанного
ответа с membership; отдельные фрагменты не выделяются. Обычные VK-сведения
сами по себе глобальную роль не требуют. `settingsService.isAdmin` включает
создателя; роль администратора беседы не заменяет эту проверку.
Ошибки повторного чтения уходят в существующий catch без выдачи `resp.content`.

Изменившийся quiet, maintenance или active mode блокирует обычный ответ
по прежним правилам. При успешной доставке текст ассистента сохраняется
в истории только при `!vkInfoReturned`; после неопределённой доставки
содержательная отправка не повторяется. Сохранённый `vkInfoReturned`
также не даёт обойти финальную проверку прямым send_vk_message или другим
действием через getActionError/beginAction. После ошибки провайдера, если
side effect уже начат, пользователь получает предупреждение проверить
его состояние перед повтором.

Автоматический web search — отдельный предварительный шаг: `findWebSearchQuery` классифицирует текст, `searchService` добавляет результаты в system context; это не один из model tools. При ошибке классификации/поиска ответ продолжается с предупреждением модели не заявлять о проверке актуальности. Relevant long-term memories подмешиваются как недоверенные данные; их недоступность не отменяет запрос.

## Лимиты, права, ошибки и побочные эффекты

- Администратор бота определяется `settingsService.isAdmin`; администраторы обходят пользовательский rate limit. Проверка администратора VK-беседы выполняется отдельным запросом к `messages.getConversationMembers`; при ошибке доступ не подтверждается.
- Rate limit keyed по VK sender ID; для личных сообщений проверяется до основной маршрутизации, для бесед — только для событий, которые будут обработаны (с отдельным поведением active decision). Отклонение отвечает пользователю retry-after, если включено уведомление.
- Maintenance и `quiet` перепроверяются после постановки в очередь; длинный ввод отклоняется до AI. Пермишены отдельных команд/инструментов должны проверяться в их контракте: маршрутизатор сам по себе не является общей авторизацией.
- Сообщения и ответы записываются через `memoryService`; usage — в `ApiUsage`; профиль, мемы, анкеты, игры, память, напоминания и settings изменяются делегированными сервисами.
- `recordUsage` намеренно не прерывает основной flow при ошибке БД. Ошибки транскрипции, команд, инструментов, провайдера, отправки и фона имеют разные fallback; если отправка уже началась или её результат неизвестен, код не должен автоматически повторять потенциально выполненное действие.
- `/image`, `/edit` и image tool используют [ImageQuotaService](../image/imageQuotaService.md) после guards/конфигурации/фото, до генератора. Готовое изображение финализируется consumed до VK; ошибка finish не отменяет доставку. Только ImageNotExecutedError разрешает release. Неизвестный исход и ошибка VK сохраняют расход. Image-specific `recordUsage` принимает createdAt=reservedAt после подтверждённой отправки; сбой статистики не меняет допуск. Остальные callers сохраняют default timestamp. Tool отмечает `commandResultDelivered` до best-effort usage.
