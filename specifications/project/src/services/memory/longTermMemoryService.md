# longTermMemoryService

## Контекст долговременной памяти

`getRelevantMemories` при наличии чувствительных сведений в запросе возвращает пустой список. В группе ищет только записи с `scope=conversation` текущей беседы и только при включённом `ChatSettings.memoryEnabled`. В ЛС ищет `scope=personal` текущего пользователя при включённом `UserSettings.memoryEnabled`; по умолчанию запрашивается до шести записей. Истёкшие и архивные записи не включаются.

Поиск сначала архивирует истёкшие записи только в выбранной области, затем загружает максимум 500 активных записей по убыванию `importance`, `updatedAt`. Кандидаты сортируются по `keywordRelevance`; первые 40 передаются в поиск векторов. При наличии векторов результат допускается при cosine similarity ≥ 0.32 либо лексическом score ≥ 0.15; без пригодного вектора порог лексического score — 0.18. Итоговый score с векторами: `0.8 × semantic + 0.2 × lexical + 0.04 × importance + 0.02 × confidence − min(ageDays × 0.00005, 0.05)`; без векторов используется lexical вместо semantic/смешивания. Результат ограничен 1–20 записями, стандартный лимит — 6. `lastAccessedAt` обновляется после выдачи, а ошибка обновления только журналируется.

`MEMORY_EMBEDDING_API_KEY` включает внешний OpenAI embedding provider; без него поиск остаётся лексическим. Запросы обрезаются до 2000 символов; содержимое старых или иной модели векторов — до 400. Модельно-устаревшие векторы пересчитываются и записываются; ошибка embedding включает лексический fallback. Query embedding кэшируется 5 минут, максимум 250 запросов на процесс. Изменение версии модели и невалидные сохранённые JSON-векторы могут привести к пропуску части семантических совпадений до успешного пересчёта.

## Явное управление

`handleControlMessage` сначала обрабатывает ожидающее уточнение удаления, затем определяет общую или личную область по тексту и контексту. Просмотр общей памяти доступен в беседе; личный список, запрошенный из группы, возвращается отдельно для отправки в ЛС автора. Очистка общей памяти и изменение её настроек требуют `isConversationAdmin`; личную память очищает её владелец. Переключатели использования `memoryEnabled` и автоматического сохранения `autoMemoryEnabled` хранятся раздельно.

При явном добавлении текст проверяется на чувствительные сведения; извлечение кандидатов выполняется через ИИ. Поиск записи для удаления использует порог релевантности; если несколько вариантов близки, создаётся `MemoryActionDraft` с кандидатами и сроком 10 минут. В группе варианты личной памяти возвращаются для личной доставки. После выбора общую запись может удалить её автор или администратор беседы; перед удалением эта проверка выполняется повторно. Просроченный или потерявший кандидатов черновик удаляется.

Распознавание управления основано на регулярных выражениях после удаления необязательного префикса «Пенёк». Порядок обработки: pending selection, очистка общей памяти, очистка личной памяти, список общей/личной памяти, переключатели, явное добавление, удаление. Очистка общей области и её `memoryEnabled`/`autoMemoryEnabled` требуют callback `isConversationAdmin`; ЛС не распознаёт общие операции. Личная очистка и настройки ограничены `vkUserId` текущего запроса. При ошибке отправки приватного списка VK caller не показывает содержимое в группе и возвращает безопасное сообщение.

`parseAddRequest` принимает формы `запомни`, `сохрани`, `добавь в [общую|личную] память`, максимум 2000 символов. Область выбирается по явной групповой формулировке или коллективной подсказке; иначе запись личная. Перед extraction явный путь отклоняет чувствительный исходный текст; внутренний guard также отклоняет instruction-like текст и личные утверждения без маркеров первого лица. Для общей памяти требуется группа, а для неявного автоматического сохранения — коллективный cue.

`parseDeleteRequest` принимает `забудь|удали|убери <описание>`; запрос короче трёх символов и фразы полной очистки не являются точечной командой. Поиск возвращает до шести записей; score должен быть ≥ 0.22. Если два лучших результата различаются менее чем на 0.12, автору предлагается до четырёх вариантов и сохраняются ID в `MemoryActionDraft`. Ответ принимается только в той же паре `(userId, conversationId)` в течение 10 минут: номер, «первый/второй/третий/последний» либо текст, однозначно совпадающий с кандидатом по keyword score ≥ 0.2. Неоднозначный ответ повторно показывает варианты. Неподтверждённая область/кандидат не используется; удаление общей записи повторно проверяет автора или администратора.

## Автоматическое сохранение

`shouldAnalyzeAutomatically` допускает только сообщение длиной после trim от 8 до 2000 символов с candidate pattern и без совпадения secret/sensitive/instruction-like regex. VK вызывает capture асинхронно без задержки ответа: для фоновых сообщений в active-беседе, после инструмента `send_vk_message` и после обычного ответа AI. Ошибки capture журналируются; ошибка не отменяет уже отправленное сообщение. Повтор одного fingerprint для автора/peer подавляется на пять минут; кэш процесса ограничен 2000 ключами.

Для автоматического анализа пользователь должен существовать, а `UserSettings.autoMemoryEnabled` должен быть не `false`. Личная область всегда рассматривается, но личный кандидат сохраняется только при формулировке от первого лица. В группе общая область включается отдельно при `ChatSettings.autoMemoryEnabled` и collective cue. Перед изменением общей записи проверяется, что она существует в той же беседе; изменить чужую запись может только администратор.

## Извлечение и слияние кандидатов

`extractCandidates` загружает до 20 неархивных личных записей пользователя и до 20 неархивных записей текущей беседы (без SQL-фильтра по `expiresAt`), передаёт сообщению и этим фактам модели как недоверенные данные и требует JSON максимум из трёх элементов. Принимаются только разрешённые scope/action/category, непустой content до 400 символов, importance ≥ 0.45, confidence ≥ 0.8 автоматически или ≥ 0.75 при явном запросе, без секретов и instruction-like content. Значения выше 1 ограничиваются 1; `update` требует `targetId` из переданного набора. `validDays` принимается только как целое 1–3650. Ссылки на связанные записи ограничиваются пятью существующими ID. Ошибочный JSON, неизвестные поля/значения и `ignore` не сохраняются.

Личные категории: `preference`, `style`, `profile`, `project`, `plan`, `decision`, `interaction`, `event`; общие: `agreement`, `decision`, `event`, `group_project`, `group_humor`, `shared_preference`. `persistCandidate` вычисляет SHA-256 fingerprint по NFKC/lowercase/схлопнутым пробелам. Срок задаётся `validDays`, иначе для `plan` — 180 дней, для `event` — 90, для остальных — бессрочно. Вектор до 400 символов сохраняется JSON вместе с моделью; его отсутствие не запрещает запись.

Для `update` сервис повторно находит target в owner scope. Дубликат определяется тем же scope и fingerprint, включая ранее архивированную запись; update снимает `archivedAt` и обновляет факт/оценки/срок. Если target и отдельный duplicate одновременно существуют, обновляется duplicate, а target архивируется. Если совпадения нет — target обновляется либо создаётся новая запись. `relatedMemoryIds` затем фильтруются по той же области и активным строкам; связи записываются в обе стороны как JSON-массив. Эти шаги не объединены в транзакцию: сбой после основной записи может оставить частично обновлённые связанные ID. Уникальные индексы `(userId,fingerprint)` и `(conversationId,fingerprint)` служат последней защитой от дубликата; отдельный retry конфликта здесь не выполняется.

`archiveExpiredMemories` запускается ежедневно в 03:15 по timezone процесса и помечает `archivedAt` для всех истёкших воспоминаний, затем удаляет просроченные action drafts. Поиск и просмотр также лениво архивируют истёкшие записи выбранной области. Архивирование не удаляет содержимое; явная очистка удаляет строки области, каскадная очистка родителя определяется схемой.

## Точки вызова и свидетельства

Основной runtime — [`VkService`](../vk/vkService.md): перед ответом подмешиваются релевантные факты как недоверенные system-контекст; pending selection снимает `active`-режим с ветви decision; команда управления исполняется через questionnaire/interaction tool с повторными проверками доступа. Автосохранение запускается fire-and-forget в трёх указанных выше ветвях. Архивирование регистрирует [`longTermMemoryJob`](../../jobs/longTermMemoryJob.md). Подробности о текущих и исторических сообщениях находятся в [memoryService](memoryService.md), а правила эвристик — в [memorySafety](memorySafety.md).

Отдельных unit-тестов `LongTermMemoryService`, `MemorySafety` или embedding provider в `test/` нет. [`vkMessageDeliveryIntegration.test.ts`](../../../../../test/vkMessageDeliveryIntegration.test.ts) подменяет `hasPendingSelection`, `getRelevantMemories` и `shouldAnalyzeAutomatically` и проверяет только окружающий VK routing/delivery; extraction, search, privacy, merge, права и Prisma-запросы не подтверждает. База, секреты и реальные пользовательские данные не читались; тесты не запускались.
