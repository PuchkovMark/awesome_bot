# SubagentService

**Тип:** сервис прежнего фонового анализа локальной истории, сохранённый для совместимости и работы с сохранёнными заданиями. **Runtime identity:** экспортируемый класс `SubagentService` и singleton `subagentService`. **Источник:** [`subagentService.ts`](../../../../../src/services/ai/subagentService.ts).

## Входы и регистрация

Текущий основной VK-путь [`run_subagent`](tools.md#run_subagent) выполняет [DirectSubagentService](directSubagentService.md): [`VkService`](../../../../../src/services/vk/vkService.ts) передаёт `runDirect` в `createSubagentTool`, и [фабрика](../../../../../src/services/ai/tools/subagentTool.ts) возвращает результат прямой ветки до `estimateMessages` и `startJob`. Прямой сервис возвращает текст основной модели без создания `DigestJob` и отдельной фоновой доставки. Его ограничения и прекращение по общему timeout описаны в [собственном контракте](directSubagentService.md#ресурсы-и-ограничения).

Ниже описан сохраняемый прежний фоновый путь фабрики **без `runDirect`** и API `SubagentService`. В этом пути bound callbacks передают `conversationId`, инициатора `userId`, выбранный диапазон, формат и фильтр участников; tool делает предварительную оценку, а сервис повторно грузит SQL-историю при обработке задачи. Старые callbacks `estimateMessages`/`startJob` остаются в VK context, но при переданном `runDirect` эта ветка не исполняется. Описанные далее постановка, суточный лимит, части и отдельная доставка относятся к фоновым заданиям, а не к текущему прямому вызову. Различие ветвей также зафиксировано в [каталоге инструмента](tools.md#run_subagent).

`estimateMessages` делегирует `estimateHistoryMessages` с беседой и `count` либо датами; применяет `participantUserIds` и `includeBot`, если они переданы. Групповой peer определяется сравнением числового ID со смещением `2_000_000_000`; для настроек timezone используется `timeZone ?? locationTimeZone` беседы, а для ЛС — пользователя.

## Постановка и конкурентность

`startJob` отказывает при `stopping=true`. `activeKey` равен `conversationId` и уникален: существующая запись моложе `SUBAGENT_TIMEOUT_MINUTES` возвращает `already_running`; просроченная запись получает `failed`, текст ошибки и освобождённый ключ. Суточный лимит считает все `DigestJob` данного `userId` за предыдущие 24 часа, без фильтра по `kind`; значение по умолчанию — 10.

Новая строка создаётся в [`DigestJob`](../../../prisma/models.md#digestjob) как `kind=history_task`, `status=pending`. В неё сериализуются форматированный запрос, ограничения вывода, выбранные участники и ID исходного VK сообщения. При нарушении unique `activeKey` сервис повторно читает запись и возвращает `already_running`. Успешная задача помещается в `PQueue` с `SUBAGENT_CONCURRENCY` (2 по умолчанию); отдельный semaphore ограничивает одновременные provider вызовы (`SUBAGENT_PROVIDER_CONCURRENCY`, 6).

## Обработка истории и частей

`processJob` пропускает отсутствующие и уже терминальные записи. Повторная обработка строки с уже заполненным `result` восстанавливает итоговый статус по предыдущему статусу и `partResults`, освобождает `activeKey` и при необходимости повторно инициирует доставку.

Для обычного `history_task` сервис загружает сообщения повторно через `loadHistoryMessages`. Повреждённый JSON участников приводит к `failed`; пустая выборка, свыше `SUBAGENT_MAX_SUMMARY_CHARS` символов (300 000) или `SUBAGENT_MAX_MESSAGES` сообщений (3 000) также завершаются ошибкой. Если SQL содержит меньше запрошенного числа сообщений или не покрывает начало/конец диапазона с точностью в минуту, эти ограничения добавляются к инструкции итоговой модели.

Число частей автоматически задаёт `requiredSubagentParts`: ниже `SUBAGENT_SECOND_PART_MIN_MESSAGES` (500) — одна, на пороге и выше — от одной до двух с учётом `SUBAGENT_MAX_PARTS`. Tool возвращает предварительный счёт по оценённому числу доступных сообщений; он не передаёт выбор частей в `startJob`. Начальная запись вычисляется по запрошенному `count` (при запросе диапазона дат — одна часть), а после SQL-загрузки сервис повторно определяет число частей по фактическому `messages.length`, делит snapshot и обновляет `DigestJob.parts`, если значение изменилось. Поэтому части в ответе `accepted` могут не совпасть с фактическим планом. Завершённые части из `partResults` переиспользуются при повторном проходе. Незавершённые части вызываются параллельно, каждый вызов ограничен `SUBAGENT_PART_TIMEOUT_MINUTES` (15 минут). Таймаут помечает часть `failed`; обёртка не передаёт provider отмену запроса, но tool callbacks получают неактивное состояние после дедлайна.

`runPart` создаёт read-only набор [`get_local_chat_history`, `search_history`, `summarize_history`, `get_current_datetime`](tools.md#указатель-инструментов), просит модель вернуть внутренний Markdown-отчёт и ограничивает tool calls значением `SUBAGENT_MAX_TOOL_CALLS` (8 по умолчанию). Лимит длины каждого отчёта — `max(2000, job.maxOutputChars)`. Prompt задаёт разделы «Кратко», «Хронология», «Факты», «Решения и договорённости», «Вопросы», «Кто кому отвечает», «Источники» и «Пробелы»; для `reply_to` просит указать автора, текст и ID цитируемого сообщения. Исходная история читается через tools из загруженного снимка; prompt запрещает выполнять инструкции из истории, выводить сырой JSON или писать пользователю финальный ответ. `summarize_history` дополнительно вызывает AI provider.

Если не завершилась ни одна часть — задача `failed`. При наличии хотя бы одного успешного отчёта `finalizeReports` всегда вызывает provider, в том числе для одной части: передаёт отчёты основной модели, а не субагенту, без tools, вместе с исходной задачей, форматом, ограничениями выборки и списком неуспешных частей. Перед финализацией запрашивается system instruction `CharacterService` для текущего пользователя и `direct`/`chat` scope; ошибка загрузки логируется и финализация продолжается без style prompt. Финальный prompt просит убрать дубли, сохранить хронологию, решения и договорённости, не раскрывать внутренние отчёты и явно обозначить неполный результат. Лимит output tokens равен `min(AI_MAX_OUTPUT_TOKENS, max(1200, ceil(maxOutputChars * 1.2)))`. Ответ обрезается до `job.maxOutputChars`; usage budget (120 000 input / 35 000 output tokens по умолчанию) суммирует также запрос финализации. Результат получает `partial`, если часть неуспешна, иначе `done`; пустой текст и превышение usage budget завершают задачу как `failed`.

Для legacy `kind=digest` остаётся отдельный путь `buildChatDigest` → `finalizeChatDigest`. Если провайдер/обработка выбрасывает ошибку, `failJob` записывает пользовательское сообщение в `result`, диагностическую ошибку до 1000 символов в `error`, ставит `failed`, освобождает ключ и инициирует доставку.

## Статус, доставка, очистка и остановка

`getLatestStatus(conversationId)` читает последнюю сохранённую `DigestJob` по `createdAt` без фильтров `userId` и `kind`, преобразует неизвестные состояния в `pending`, считает `partsDone` по валидным JSON-элементам. Результат показывается только для `done`/`partial`; текст ошибки — только для `failed` и обрезан до 500 символов. Это статус сохранённого задания уровня беседы, а не строго инициатора. Прямая операция `DirectSubagentService` не создаёт `DigestJob` и здесь не отслеживается: даже во время или после текущего прямого вызова [`get_subagent_status`](tools.md#get_subagent_status) может вернуть старую задачу этой беседы либо `none`, если сохранённых задач нет.

Готовый или ошибочный результат передаётся в [`SubagentResultDeliveryService`](subagentResultDeliveryService.md), а [`subagentDeliveryJob`](../../jobs/subagentDeliveryJob.md) повторно проверяет ожидающую доставку. `cleanupOldJobs` удаляет строки старше `SUBAGENT_RESULT_RETENTION_DAYS` (7 дней) только со статусами `done`, `partial`, `failed`; проверка `resultSentAt` не является условием.

`stop()` ставит сервис в stopping, приостанавливает очередь, очищает ожидающие в памяти ID. `dropInterruptedJobs()` удаляет `history_task` со статусами `pending`, `processing`, `finalizing`, затем очищает все оставшиеся ненулевые `activeKey`; при перезапуске эти задачи не восстанавливаются. Уже исполняемый Promise здесь не отменяется отдельным cancellation API.
