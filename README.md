# Awesome Bot

Новый собеседник и помощник VK. Реализованы скелет, конфигурация и логгер, общие контракты, SQLite-хранилище, модель участников и авторизация F1.6a и жизненный цикл подключения F1.6b, каркас версий F1.7, изолированный LLM-клиент F2.1 и текстовый агентный цикл F2.2 на подменах (ожидает валидации) и долговечная очередь по чатам F2.3, локальный роутер F2.4 с политикой публикации. Живой запуск, адаптер VK и LLM ещё не подключены.

## Режимы беседы

Значения схемы и роутера: `silent` — журнал и служебные команды владельца/администраторов; `normal` — дополнительно ответы на обращения; `active` — дополнительно самостоятельные реплики по закрытым поводам и лимитам. Для новой беседы default — `normal`, активного режима в личке нет.

Выключение независимо от режима: при `enabled: false` журнал приостановлен, служебные команды доступны только владельцу. Сообщение при добавлении бота служебное, не зависит от режима и приветствий новичков, но не отправляется при выключенном боте. Приветствие новичков по умолчанию выключено и включается администратором; это другое событие.

Три значения реализованы типом, проверками и миграцией 8. Оба старых режима переводятся в normal с сохранением enabled; прежние миграции неизменны. Роутер проверяет включение и приостанавливает журнал выключенного чата. Самостоятельные вступления активного режима остаются F4.7; текущий active обслуживает обычные обращения. [Правила хранения](docs/specs/storage.md#переход-к-трём-режимам).

## Среда и команды

Проверяемая среда: Ubuntu 22.04.5 LTS, Node.js 26.13.1, npm 11.20.0. Версия Node.js закреплена в `.nvmrc`; при использовании nvm выполните `nvm use`. Основной путь разработки — локальный, Docker необязателен.

```sh
npm ci
npm run lint
npm run typecheck
npm run build
npm test
```

Тесты загрузки ESM требуют предварительной сборки. `build` выполняет линтинг, проверку типов и выпуск JavaScript в `dist`; тесты запускаются отдельно. После установки зависимостей проверки не обращаются к VK и LLM и не требуют секретов.

## Конфигурация приложения

`loadConfig` из `src/config/index.ts` вызывается явно; импорт ничего не читает и не выводит. Загрузчик принимает окружение и рабочий каталог, поддерживает `.env` в формате Node.js без подстановки переменных. Окружение процесса выше файла; пустое значение окружения перекрывает файл и отклоняется. `process.env` не изменяется. Отсутствие обычного `.env` допустимо при полном окружении; отсутствие явно указанного файла или ошибка чтения завершают загрузку безопасной ошибкой.

Образец — [.env.example](.env.example). Создавайте собственный `.env` только при необходимости локального подключения будущих компонентов; сборка и тесты обходятся без него. Заполнители из примера заменяются настоящими ключами локально; их действительность можно будет проверить при реализации клиентов. Настоящий `.env` исключён из Git.

| Параметр | Требование |
| --- | --- |
| `VK_TOKEN` | Обязательный секрет сообщества VK |
| `OPENCODE_API_KEY` | Обязательный секрет провайдера OPENCODE |
| `LLM_MODEL` | Обязательный идентификатор модели; выбран `deepseek-v4.1-flash`, автоматического значения нет |
| `BOT_OWNER_ID` | Обязательный составной UserId владельца (`vk:local-id`); это конфигурация, не проверка личности |
| `ADMIN_REVOCATION_REASON_MAX_LENGTH` | Положительное безопасное целое; по умолчанию 500 Unicode code points |
| `ADMIN_REVOCATION_REASON_RETENTION_DAYS` | Положительное безопасное целое; по умолчанию 90 дней от отзыва |
| `LOG_LEVEL` | `debug`, `info`, `warn`, `error`, `fatal`, `silent`; при отсутствии — `info` |

Обязательные строки не могут быть пустыми, содержать переводы строк или пробелы по краям. Значения не обрезаются молча, ключи не проверяются по сети. Результат — неизменяемый конфиг с провайдером `opencode` и отдельная функция очистки известных секретов из обоих источников. Ошибки содержат только коды причин и известные имена параметров. Подключение конфигурации к реальному запуску остаётся в F3.4.

## Безопасные логи

`createLogger` из `src/logger/index.ts` создаётся явно с уровнем из конфига и его функцией `redact`. Pino пишет JSON-строки в stdout с временем UTC unix ms; экземпляр Pino наружу не выдаётся. При необходимости передайте `additionalSecrets` до записи данных, содержащих новые ключи. `silent` полностью отключает вывод.

Обычные вызовы — `event` с фиксированными кодами `config_loaded`, `config_invalid`, `component_error` и `componentError` с безопасной классификацией ошибки. Неизвестные поля отбрасываются. `message`, `stack`, `cause` и произвольный `name` исходной ошибки не выводятся на обычных уровнях, даже если установлен порог `debug`.

Тексты сообщений и подробности ошибок передавайте только через `debugText` и `debugError`: они создают записи исключительно уровня `debug`, очищая известные секреты. Объекты запросов, конфиги, заголовки и SDK-ответы логировать нельзя. Пользовательские `toJSON` и геттеры диагностических полей не вызываются. Для безопасной ошибки до загрузки конфига доступен `reportConfigError` без передачи исходного окружения.

Очистка скрывает точные вхождения известных секретов, в том числе перекрытые значения из `.env` и окружения. Неизвестные ключи и их base64/URL-преобразования автоматически не распознаются. Секреты новых источников необходимо зарегистрировать до логирования; прямые вызовы Pino/console в компонентах обходят этот контракт и не допускаются.

## Общие контракты

Общие типы экспортируются из `src/contracts/index.ts` без SDK и побочных эффектов. Сообщение `kind: message` и событие участия `kind: membership` различаются явно. Для прав и признака автора-бота предусмотрено `unknown`; неизвестные участник и инициатор служебного события — `null`. Эти значения не означают подтверждённое «нет» и не дают разрешений.

Импорт внутри исходников, например из соседнего слоя:

```ts
import type { IncomingEvent, ChannelAdapter, ToolDefinition } from '../contracts/index.js';
```

Положительные и отрицательные примеры в `tests/typechecks` проверяются командой `npm run typecheck`; отрицательные помечены адресными `@ts-expect-error`. Vitest выполняет примеры обмена событиями и вызова инструментов на двух подменах адаптера. Типовые примеры и подмены не попадают в `dist`.

Чаты и пользователи используют составные строки `platform:local-id`, время — UTC unix ms, id сообщения имеет смысл в области чата. Непустоту, достоверность сведений и совпадение префиксов будет проверять входная граница. TypeScript не заменяет runtime-валидацию или авторизацию. Текст — обычная Unicode-строка; вложения — непрозрачные дескрипторы без raw payload и секретов. Нормализация и обработка данных платформ в эту область не входят. ESLint запрещает платформенные импорты также в `src/contracts`.

`ChannelAdapter` предоставляет асинхронные `capabilities`, `start`, `send`, `sendTyping`, `getUserName`. Успешная отправка возвращает непустой список id частей, недоступное имя — `null`. Снимок возможностей относится к чату и, при наличии, пользователю и содержит время наблюдения. `supported/unsupported/unknown` различают поддержку и неполноту сведений; снимок может устареть и не заменяет проверку прав. Лимит длины содержит число с единицей `utf16/unicodeCodePoints/utf8Bytes` либо `unknown`; оформление перечисляется отдельно от plain text. Реального адаптера, кеша, ретраев и жизненного цикла приложения пока нет.

`ToolDefinition<Parameters, Result>` описывает назначение, корневую объектную JSON Schema, `access: read/write`, доступность `platforms`, требования `requiredCapabilities` и асинхронный `execute(parameters, context)`. Отсутствие `platforms` означает `all`, пустой список — ни одной платформы. Отсутствие требований означает отсутствие требований. Это метаданные для будущего реестра. `ToolContext` передаёт текущие чат, платформу, пользователя, сведения об администраторе и адаптер отдельно от параметров модели; роль и разрешение на действие он не назначает. TypeScript проверяет JSON-представимость схемы и типы функции, но не соответствие произвольной схемы параметрам или runtime-данным. Тестовые примеры двух искусственных платформ не обращаются к VK или OPENCODE.

## Хранилище журнала и настроек

Хранилище использует закреплённые `better-sqlite3` 13.2.0 и `@types/better-sqlite3` 9.6.0. Драйвер и FTS5 проверяются реальными тестами на Node.js 26; после `npm ci` проверки не требуют сети. Нативный драйвер загружается только при явном открытии. Импорт `src/storage/index.ts` не открывает БД, не читает окружение и ничего не выводит.

Пример внутри соседнего слоя исходников:

```ts
import { openStorage } from '../storage/index.js';
import { createLifecycleService } from '../core/index.js';

// Только новая отдельная БД; родительский каталог должен существовать.
const storage = await openStorage('/absolute/path/to/new-bot.sqlite');
try {
  // verifiedSource и ownerId передаёт доверенный компонент приложения.
  const lifecycle = createLifecycleService({ storage, ownerId, source: verifiedSource });
  await lifecycle.verify('vk:2000000001');
  const scope = lifecycle.current('vk:2000000001');
  const result = await storage.messages.append(scope, {
    chatId: 'vk:2000000001', messageId: '100', userId: 'vk:42',
    authorName: 'Имя', role: 'user', text: 'Привет', timestamp: Date.now(),
  });
  // result.status — inserted или duplicate; result.id — id исходной строки.
  await storage.chats.create(scope, {
    responseMode: 'normal', enabled: false, createdAt: Date.now(),
  });
  const history = await storage.messages.list(scope, { limit: 20 });
  void result; void history;
} finally {
  await storage.close();
}
```

Режим normal и enabled: false в примере переданы явно для демонстрации технического API; роутер создаёт отсутствующие настройки как normal/enabled true. Название и индивидуальный промпт при создании без них — `null`, таймзона — `Europe/Moscow`. Настройки читаются через `chats.get(scope)`, меняются через `chats.update(scope, patch)`; `systemPrompt: null` пока очищает устаревшее поле технического API; команды не вправе устанавливать его, сборщик F2.5 не будет его применять. Отсутствующий чат возвращает `null`, update не создаёт его. Повторный create возвращает `existing` и сохранённые настройки, сохраняя дату создания и изменения.

Путь обязателен и абсолютен; для отдельной in-memory БД передайте `:memory:`. Переменной `DB_PATH`, автоматического выбора каталога или подключения к старой БД нет. Миграции применяются при открытии одной транзакцией; изменённая история, более новая или посторонняя схема отклоняются без автоматического переноса. Набор SQL входит в ESM-выпуск и работает без исходного дерева. Бэкап перед будущими обновлениями рабочей БД относится к процедурам эксплуатации.

Журнал принимает роль `user` или `assistant`, фактические составные id автора и чата одной платформы, строковый id сообщения, имя, текст, UTC unix ms и необязательный reply-id. Запись не требует предварительного создания настроек. Дубликат пары `(chatId, messageId)` не меняет исходную запись даже при другом тексте. Одна строка соответствует одному платформенному сообщению; интеграция получения текстов частей длинного ответа остаётся F3.2.

`messages.list` требует проверяемую область подключения и положительный целочисленный `limit`. Необязательные `from/to` задают UTC ms интервал `[from, to)`; выбирается последнее ограниченное окно и возвращается по возрастанию `(timestamp, id)`. Это не обещает полную выдачу за период. Межчатового чтения, публичного SQL, редактирования/удаления журнала и поиска для модели нет. FTS5 поддерживается триггерами; инструменты поиска относятся к F6.3.

Все публичные методы возвращают Promise, но SQLite внутри выполняется синхронно и может блокировать поток. Закрытие повторно безопасно; дальнейшие операции отклоняются с кодом `closed`. Ошибки содержат только фиксированный код и безопасное сообщение, без исходного SQL, параметров, пути и `cause` драйвера. Само хранилище не логирует. Проверки используют временные БД; реальный запуск бота и очистка журнала по сроку не реализованы; удаление всех данных подключения реализовано отдельно. Перенос данных не входит в проект.

## Модель участников и профилей

Миграция 3 добавляет `chat_participants`, `participant_profiles` и `profile_facts`. Участие и профиль определяются парой `(chat_id, user_id)`; факты имеют собственный id и обязательную ссылку на профиль в той же области. Один человек в двух чатах имеет независимые данные. Для участия нужны существующие настройки чата; журнал по-прежнему можно записывать до их создания. При открытии каждого соединения приложение явно включает и проверяет внешние ключи до миграций. Родители с зависимыми данными защищены от удаления и смены ключей; каскадное удаление не реализует правила персональных данных.

Типы `ParticipantRecord`, `ParticipantProfileRecord`, `ProfileFactRecord` и словари меток доступны через типовой импорт из `src/storage/index.ts`. Публичных операций участников и профилей пока нет; административные операции F1.6a доступны отдельно. Синтетические записи и чтение выполняются только техническими помощниками тестов.

Неизвестные даты участия и наблюдений — `null`, роль и статус — явный `unknown`. `last_seen_at` хранит время последнего известного сообщения в конкретном чате; это не онлайн-статус, рейтинг или признак отсутствия активности. Миграция не заполняет эти данные из журнала и не создаёт профили автоматически.

Значение факта — текст; несколько значений одного поля могут сосуществовать без автоматического выбора или замены. Источники — `self/inferred/admin`, надёжность — `unknown/unverified/confirmed`, видимость — `unknown/bot/chat`. Метки обязательны, значений по умолчанию нет. Источник не назначает надёжность, `confirmed` не доказывает истинность, роль `admin` не даёт прав харнеса, `bot` и `chat` не являются разрешением на публикацию. Согласие, приватность и приоритет источников уже согласованы в спецификациях; их исполнение, проверка прав и выдача данных остаются будущим фичам. Срок очистки бэкапов и конкретный текст согласия ещё не выбраны.

Тесты проверяют ограничения и связи с включёнными FK, разные чаты/платформы, сохранность после закрытия, обновление F1.4 без изменения миграций 1–2 и выпуск ESM без исходников. Эти проверки подтверждают готовность модели; реальный сбор профилей, синхронизация VK и продуктовые команды ещё не реализованы. Подробная схема — в [спецификации хранилища](docs/specs/storage.md).

## Роли и авторизация F1.6a

`createAuthorizationService` из [ядра](src/core/index.ts) создаётся явно и асинхронно с `config: config.authorization` и `store: storage.authorization`. До возврата он очищает просроченные причины и планирует ближайшую очистку. При завершении сначала вызовите `service.dispose()`, затем `storage.close()`. Импорт не создаёт таймеры. Для проверок можно передать часы `now` и планировщик `scheduler`.

Доверенный компонент приложения создаёт `service.context({ scope, userId })` только после проверки личности; для административной операции владельца указывает `kind: 'owner'` и явный целевой чат. Объект проверяется по происхождению во время исполнения, копия и контекст другого сервиса отвергаются. `await confirmMembership(scope, userId)` вызывается только после подтверждения принадлежности беседе. Эти фабрики — доверенная граница приложения, их нельзя выдавать модели или заполнять из её параметров. Они не проверяют VK самостоятельно.

`applyTrustedInitialAuthorities` сохраняет исходные основания `creator/inviter`, повтор не дублирует их, конфликт другого владельца основания даёт отказ. Подтверждение участия связано с ревизией и выдаётся заново после значимых изменений. `grant/remove` управляют обычным `explicit`; защищённое основание обычным снятием не удаляется. `check` — предварительное решение: операция сервиса повторно читает права и `enabled` внутри одной SQLite-транзакции с изменением. Платформенный `isAdmin`, имя и текст не повышают роль. Неизвестное действие отклоняется. При выключенном боте административные действия доступны только владельцу.

Только владелец через отдельный контекст может выполнить `revoke`, `restore` и `audit`. Отзыв снимает все основания и препятствует повторному назначению; отмена удаляет отзыв и аудит, но не возвращает старые основания. Запрет автоматического восстановления сохраняется отдельно по чату после отмены. Глобальные права владельца не зависят от локального отзыва. Повтор отзыва не меняет первую причину и время.

Причина обязательна, пробельная отклоняется; превышение возвращает `reason_too_long` с `maxLength`, без обрезки и выдачи текста. Только владелец читает аудит, причина не включается в журнал или контекст инструмента. Срок вычисляется по текущей конфигурации: по истечении удаляется только причина; минимальный след действует до отмены отзыва. Новый больший срок не воссоздаёт удалённый текст. `maintain()` позволяет повторить очистку вручную; `maintenanceStatus()` показывает фиксированный код сбоя без SQL, причины или исходной ошибки. Сбой стартовой очистки отклоняет создание сервиса.

`ToolContext.authorization` необязателен для совместимости, но защищённый инструмент отказывает при его отсутствии. [toolAuthorization](src/tools/authorization.ts) сверяет пользователя, чат, платформу и адаптер; после этого инструмент обязан вызвать защищённую операцию сервиса. Этот помощник не является самостоятельным разрешением записи и не принимает административный контекст владельца для модели.

Миграция 4 добавляет назначения, отзывы, аудит и запрет восстановления; существующая платформенная роль не преобразуется в права бота. Низкоуровневый `storage.authorization` — внутренний инфраструктурный доступ, его нельзя предоставлять модели. Проверки показывают последовательности одного процесса, без заявления о межпроцессной гонке или атомарности с внешним API. Поколения, ревизии и полная очистка реализованы в F1.6b. Живые роли VK, подключение сервиса к запуску, команды и восстановление F4.1 остаются будущими. Очередь и отправитель ещё должны подключить проверку области при выполнении и выдаче результата. Миграция трёх режимов, профильные политики, срок бэкапов и текст согласия этим кодом не реализуются.

Публичные операции хранения F1.6b требуют ConnectionScope: `messages.append(scope, message)`, `messages.list(scope, query)`, `chats.get/create/update(scope, ...)`, `authorization.transaction(scope, callback)`. Прежних перегрузок по одному chatId нет; область создаётся только доверенной границей и проверяется при каждой операции. `uncertain` сохраняет данные и запрещает обычные запросы до явного решения владельца; это не enabled и не режим ответа. Полная очистка и сверка проверены на синтетических данных и реальном SQLite.

## Подключение, неопределённость и удаление F1.6b

`createLifecycleService({ storage, ownerId, source })` — явная доверенная граница. Источник возвращает confidence `confirmed/uncertain/unavailable`, состояние бота и известные creator/inviter, полный либо частичный состав; отдельный подтверждённый выход задаётся departedIds. Время получения события и SDK-тип сами по себе не дают confirmed. [Исследование VK](docs/research/vk-lifecycle-capabilities.md) не подтвердило сильные гарантии платформы; живой адаптер пока не подключён. Синтетический источник есть только в тестах.

`verify(chatId)` применяет ответ только для начатой проверки и ожидаемой ревизии. Поздний ответ получает stale. `current(chatId)` выдаёт область текущего активного поколения; эти фабрики нельзя предоставлять модели или использовать для автоматического перевода старого задания на новое подключение. При uncertain сохраняются данные и настройки, но чтения, записи и авторизация обычного запроса отклоняются кодом uncertain_connection. Это отдельно от enabled и режима.

Принятое человеком разрешение неопределённости — `owner(chatId, confirmedOwnerId)` и `decide(proof, 'continue' | 'new')`. Личность владельца подтверждает приложение до вызова фабрики: равенство строки не аутентифицирует VK. Подтверждение привязано к ожидаемому состоянию, копия и повтор отвергаются. continue сохраняет данные и поколение; new атомарно очищает данные и создаёт новое поколение. Продуктовых команд пока нет. Обычная сверка сама не снимает uncertain.

Подтверждённое удаление активного подключения очищает журнал/FTS, настройки, участие, профили, факты, назначения, отзывы, весь аудит, запрет восстановления и метаданные подключения. Ошибка откатывает всё. Глобальный счётчик не хранит chatId/userId/eventId и не связан FK с таблицами людей или чатов. Новый цикл не переиспользует поколение. После открытия новой Storage выдайте новые runtime-объекты области: сериализованные/старые объекты не принимаются. Данные тестовой версии 4 сохраняются неподтверждёнными до явного решения владельца; боевых данных для переноса нет.

Выход прекращает explicit, но сохраняет creator/inviter; передача меняет только creator. Отзыв сильнее синхронизации. Обычная отмена отзыва не переустанавливает прежние основания; новое назначение — отдельное действие. Неизвестность создателя без подтверждённой передачи не снимает основание.

Гарантии относятся к рабочей БД и одному процессу. Это не доказательство доставки событий VK, атомарности с внешним API, остановки уже начатой отправки или готовности бэкапов F9.3. Все будущие миграции с чатовыми данными должны расширять тест охвата очистки.


## Версии промптов, персонажей и приветствий F1.7

Версии — буквальный неизменяемый текст с номером и UTC-временем. Общий каталог допускает `system_prompt`, `persona`, `greeting_template`; локальные версии и выбор беседы — только `persona` и `greeting_template`. Системный промпт и его выбор общие для приложения. Существующий `chats.systemPrompt` сохраняется без автоматического переноса и применения новых версий к ответам.

Настройки `VERSION_TEXT_MAX_LENGTH=32000` (Unicode code points) и `VERSION_MAX_PER_ENTITY=100` загружаются в `config.versioning`. Передайте их явно в `openStorage(path, { versioning: config.versioning })`; без options используются те же defaults. Хранилище не читает env. Превышение длины или числа версий даёт `StorageError` с кодом `limit_exceeded`, без обрезания или удаления истории. Пониженные лимиты не лишают чтения, выбора и отката прежних данных.

Пример для доверенной композиции приложения (синтетические тексты):

```ts
import { openStorage } from '../storage/index.js';
import { catalogAdministration } from '../storage/catalog-admin.js';
// config и lifecycle source передаёт приложение; источник не задаёт модель.
const storage = await openStorage('/absolute/path/to/new.sqlite', { versioning: config.versioning });
try {
  const catalog = catalogAdministration(storage);
  const system = await catalog.append({
    kind: 'system_prompt', key: 'synthetic-base', text: 'Синтетический текст',
    expectedHead: null, createdAt: Date.now(),
  });
  if (system.status === 'created' && system.value.ref.area === 'global') {
    await catalog.selectSystemPrompt(system.value.ref, null);
  }
  // scope выдан сервисом жизненного цикла для действующего подключения.
  const persona = await storage.versions.append(scope, {
    kind: 'persona', key: 'synthetic-persona', text: 'Синтетическое описание',
    expectedHead: null, createdAt: Date.now(),
  });
  if (persona.status === 'created') {
    await storage.versions.select(scope, 'persona', persona.value.ref, null);
  }
  const selected = await storage.versions.selected(scope, 'persona');
  const prompt = await storage.versions.systemPrompt(scope);
  void selected; void prompt;
} finally { await storage.close(); }
```

`append` создаёт версию, сохраняя прежний выбор. `expectedHead` — ожидаемый последний номер либо `null` для новой сущности; устаревшее ожидание возвращает `conflict`. `get(scope, ref)` читает точную доступную версию либо `null`. `selected` и `systemPrompt` возвращают согласованный снимок ссылки, текста и времени либо `null`, без выбора последней версии по умолчанию. Результат чтения не меняется после смены выбора.

`select(scope, kind, ref, expected)` проверяет ожидаемую прежнюю ссылку и существование цели; возвращает `selected`, `conflict` или `not_found`. Откат — выбор точной старой версии, сброс — `reset(scope, kind, expected)`. Системный выбор меняют только методы отдельного каталога `selectSystemPrompt`/`resetSystemPrompt`; у Storage таких полномочий нет. История не перезаписывается. Пользовательские тексты остаются недоверенными независимо от номера версии.

Инфраструктурный фасад не реэкспортируется из `storage/index`, не доступен модели и не аутентифицирует человека. Команды, инструменты и контекст не импортируют его или путь получения backend из внутреннего реестра; сборка проверяет граф, включая посредников, реэкспорты и динамические загрузки. Корни: `src/tools`, `src/commands`, `src/core/commands`, `src/context`, `src/core/context`, `src/core/context.ts`; при ином размещении новых компонентов список обязательно расширяется. Проверку отдельно запускает `npm run check:catalog`.

Все запросные операции требуют действующую `ConnectionScope`. Локальная ссылка содержит поколение; старое подключение не получает новые данные. Очистка беседы удаляет локальную историю и выборы, сохраняя общие версии, общий системный выбор и другие чаты; ошибка откатывает весь набор. Удаления отдельной версии и автоматического освобождения квоты нет: безвозвратное удаление локальной версии остаётся вопросом вехи 7.

Каркас проверен без VK/LLM и не подключает тексты к ответам. Продуктовые права публикации, команды, библиотека, конструктор, сроки хранения и удаление персональных данных остаются соответствующим будущим фичам.

## Клиент OpenCode Go F2.1

[Модуль llm](src/llm/index.ts) реализует один запрос модели без подключения к боту и без чтения хранилища. Импорт и создание не вызывают сеть. Новых зависимостей и переменных окружения нет; конфигурация llm по-прежнему содержит provider, apiKey и model.

Пример для доверенной сборки приложения (сам вызов complete обращается к провайдеру; автоматические тесты всегда подменяют fetch):

```ts
import { createLlmClient, createLlmSessionId } from './src/llm/index.js';

const client = createLlmClient(config.llm, {
  timeoutMs: 60_000,
  maxResponseBytes: 1_048_576,
});
// secret — отдельный постоянный секрет установки, scope проверяет харнес.
const sessionId = createLlmSessionId(secret)(scope);
const result = await client.complete({
  system: 'Подготовленные системные инструкции',
  messages: [{ role: 'user', text: 'Привет' }],
  maxOutputTokens: 128,
  sessionId,
  signal: abortController.signal,
});
```

Сессия — HMAC от беседы и поколения подключения; сырой chatId в заголовок не передаётся, соответствия не сохраняются. Один и тот же секрет нужен после перезапуска; его безопасное подключение к запуску остаётся F3.4. Смена секрета меняет сессии. Это не анонимизация текста запроса.

Исходы различимы по kind: complete, incomplete, refused, empty, tool_calls, error. Аргументы вызовов — непрозрачные строки, даже если это неверный JSON; клиент ничего не исполняет. Описания tools и история assistant/tool передаются по [контракту](docs/specs/architecture.md#клиент-модели-f21); execute и полномочия провайдеру не передаются. Usage.input/output — числа или null при отсутствии корректных данных. Ошибки содержат фиксированные code/message без исходной диагностики и тел провайдера. Клиент не логирует тексты даже в debug.

Одна попытка, без повторов, redirect и fallback. Timeout охватывает также чтение тела; отмена и лимит байтов прекращают ожидание, ресурсы освобождаются. Для подмены передайте options.fetch с сигнатурой (url, init) => Promise<Response>; примеры — [тесты клиента](tests/llm-client.test.ts) и [инструментов](tests/llm-tools.test.ts). npm test не вызывает реальную модель.

Доступ аккаунта, пригодность условий Go для разговорного бота, инструменты, русский, контекст, устойчивость и лимиты ещё не проверены: отдельная F2.9 обязательна до начала F5.6. Extra Usage может расходовать баланс сверх подписки; настройки сервиса клиент не меняет. До передачи реальных текстов остаётся вопрос человеку о провайдере и формулировках раскрытия в согласии и сообщении добавления. Юридическую часть решает человек; этот пример не разрешает живой запуск.

## Агентный цикл F2.2 на подменах

[createAgentLoop](src/core/agent-loop/service.ts) получает нейтральный LlmClient и возвращает run(input). Статус: **реализовано на подменах, ожидает валидации**. Живой доступ, инструменты, роутер и отправитель этим не подключены; локальная связка с очередью описана ниже.

Пример с подменой без сети:

```ts
import { createAgentLoop } from './src/core/index.js';

const loop = createAgentLoop({
  async complete() {
    return { kind: 'complete', text: 'Привет!', usage: { input: 0, output: 0 } };
  },
});
const result = await loop.run({
  system: '',
  messages: [{ role: 'user', text: 'Привет' }],
  maxOutputTokens: 128,
  sessionId: 'synthetic-session',
});
```

Defaults фабрики: maxSteps = 6, maxAttemptsPerStep = 2, timeoutMs = 120000, retryDelayMs = 1000, retryServerErrors = true. В этой версии есть один логический шаг; server-повтор увеличивает только попытки. Rate_limit возвращается сразу отдельным исходом, остальные ошибки автоматически не повторяются. Паузы входят в общий срок; отмена и deadline останавливают ожидание и новые попытки. Уже обработанный запрос отменой не откатывается и может быть оплачен.

Различайте kind: complete (text), incomplete (partialText), refused, empty, rate_limit, tools_not_supported, cancelled, deadline_exceeded, attempt_limit и error. Только complete содержит законченный текст. В summary доступны steps, attempts, attemptsPerStep, durationMs и usage.input/output с knownTokens/unknownAttempts/overflowed; частичная известная сумма не равна полному расходу. Ошибки не содержат произвольного message/stack/cause клиента; цикл не логирует запросы и ответы.

Опции задаёт доверенная сборка; выбор политики в проде принадлежит владельцу бота, подключение — F3.4. Вход и конфигурация фиксируются, параллельные запуски изолированы, инструментальный ввод отклоняется. Подмены и тесты — [исходы](tests/agent-loop-outcomes.test.ts), [повторы](tests/agent-loop-retries.test.ts), [отмена и ресурсы](tests/agent-loop-resources.test.ts). npm run build и npm test выполняются без настоящих ключей и сети.

F2.9 обязательна до F5.6. [Задача и планы 012](docs/tasks/012-agent-loop.md) остаются активными без даты окончательного завершения. За согласованную [таблицу реакций](docs/specs/agent-loop.md#публикация-исхода-и-молчание) отвечает реализованный локальный роутер F2.4. Молчание при ошибке в active проверено связкой с подменой порта; реальный отправитель остаётся будущей интеграции.

## Проверка нагрузки очереди

`npm run test:queue-load` — отдельный прогон без сети; обычный `npm test` его не запускает. Требуется предварительная `npm run build`, поскольку тест второго владельца использует собранный ESM в отдельном процессе.

Профили: расчётные 4 слота с бюджетом 130 секунд и вместимостью 8 ожидающих; реальный всплеск 500 сообщений в SQLite; удаление беседы с 300 000 сообщений, FTS, 300 000 заданий и 2000 профилей, дополнительно 1000 служебных уведомлений, состояние периода и признаки маршрута. Синтетические данные создаются во временной БД и удаляются. Измерения записываются в файл `awesome-bot-queue-load-results.jsonl` внутри `os.tmpdir()`; строки накапливаются, последние три относятся к последнему полному прогону. `model: true` означает управляемое время и не является замером производительности провайдера.

Начальная модель даёт около 1,85 задания/минуту при четырёх полностью занятых слотах; это расчёт, а не измеренная скорость Go. Пределы — 2 ожидающих задания на чат, 8 всего, актуальность 10 минут. Резерва для тихих чатов нет: справедливый выбор принятой работы не гарантирует допуск при заполненной очереди. До боевого запуска F9.5 повторяет нагрузку и очистку на ожидаемом максимальном объёме с запасом; очистка вместе с запасом должна укладываться в оставшийся срок владения.

## Очередь по чатам F2.3

[createChatQueue](src/core/chat-queue/service.ts) получает открытый Storage, доверенный handler и config; создание не запускает работу. Методы: start(), admit(scope, message, decision), admitRouted(scope, message, decision), stop(), stats(); signal и isRunning() дают текущий предохранитель публикации. decision — чистая синхронная функция после записи журнала, handler выполняет отдельное задание с исходной scope, внутренним messageId и сигналом отмены. Локальный роутер F2.4 подключается через admitRouted; реальный отправитель ещё впереди.

admit атомарно сохраняет журнал и принятое задание. queued содержит jobId и внутренний messageId журнала; storage.queue.get(scope, jobId) читает состояние, storage.messages.get(scope, messageId) — сообщение. При queue_full журнал сохраняется без задания; duplicate никогда не создаёт новое задание, в том числе после переполнения. При stopped приложение может отдельно журналировать разрешённые события прежним API. Локальная входная граница F2.4 применяет enabled/режимы; подключение живых событий остаётся F3.x.

Defaults: maxConcurrentChats = 4, maxQueuedPerChat = 2, maxQueuedTotal = 8, maxQueueAgeMs = 600000, leaseMs = 30000, renewIntervalMs = 10000, stopTimeoutMs = 10000. handlerTimeoutMs по умолчанию равен loopTimeoutMs + handlerMarginMs = 120000 + 10000. Для связки с F2.2 используйте [createAgentLoopQueue](src/core/chat-queue/agent-loop-adapter.ts): он создаёт цикл и проверяет бюджет по одному снимку фактических loopOptions, а не по произвольному объявлению срока. Все пределы — изменяемые настройки, новых переменных окружения нет.

Очередь выполняет FIFO одного чата и циклический выбор готовых чатов, сохраняет ссылки вместо текстов. После перезапуска running становится interrupted без автоповтора и автоматического сообщения; queued сохраняет возраст. rate_limit конечен без перепланирования, server повторяется только внутри F2.2. Сбой одного задания не останавливает следующие. Второй владелец БД отклоняется; потерявший срок или маркер не фиксирует поздний результат. Stop ограничен сроком и освобождает собственные таймеры, но не откатывает уже отправленный внешний запрос и оплату.

В безопасных логах queue_stats — глубина и время ожидания, отклонённые, просроченные и прерванные без текстов и идентификаторов. Накопленные счётчики относятся к окну текущего сервиса; это не долговечный бюджет. После остановки stats — последний снимок. Детали и ограничения — [хранилище](docs/specs/storage.md#очередь-по-чатам-f23), нагрузка — [отдельный прогон](#проверка-нагрузки-очереди).

## Роутер сообщений F2.4

[createMessageRouter](src/core/message-router/service.ts) принимает открытый storage, работающую queue, необязательные logger/authorization/recognizeCommand и onQueueFull. receive(scope, incoming, context?) использует нормализованный IncomingMessage: isBot обязателен; true и unknown не запускают обычную обработку, unknown отражается в stats().senderUnknown и безопасном router_stats. Тексты и идентификаторы в этом счётчике не сохраняются. Контекст команды должен быть выдан доверенным сервисом авторизации и совпадать с личностью/целевой областью; сам роутер команд не исполняет.

Режимы silent/normal/active хранятся после миграции 8; старые mention и always переходят в normal, прежнее always сознательно не сохраняется. Новый чат получает normal/enabled true, существующие настройки не перезаписываются. Silent журналирует, но обычные обращения молчат; выключенный не журналирует и оставляет служебный путь владельцу. В личке active трактуется как normal. Самостоятельных вступлений до F4.7 нет. Прямое обращение Пенек/Пенёк определяется ограниченной грамматикой без модели; неоднозначное обсуждение имени обычный ответ не запускает.

Схема сборки для доверенного приложения с уже подготовленными storage, подменами client/prepare/port и logger:

```ts
import {
  createAgentLoopQueue, createMessageRouter, createPublicationService,
} from './src/core/index.js';

const publication = createPublicationService({ storage, port });
const queue = createAgentLoopQueue({
  storage, client, prepare, logger, onSettled: publication.onSettled,
});
const router = createMessageRouter({
  storage, queue, logger, onQueueFull: publication.queueFull,
});
await queue.start();
// incoming и scope получает доверенная входная граница, не модель.
await router.receive(scope, incoming);
await queue.stop();
```

prepare пока внедряется явно: сборщик контекста F2.5 ещё впереди. Контекстному потребителю передают только storage.contextMessages, а не полный Storage/messages. Его get/list и FTS исключают service_notice; общий messages.get/list сохраняет эти записи для разрешённого аудита. npm run build включает check:context и проверяет обходы через импорты/реэкспорты.

Порт — подмена/будущий отправитель: canReply(scope, signal) подтверждает возможность reply, publish(request) получает scope, kind, text, необязательный replyToMessageId и AbortSignal. Результат — delivered с receipt {messageId, userId аккаунта бота, authorName, timestamp}, failed либо unknown. Delivered записывает фактический ответ/уведомление в журнал; service_notice всегда reply и исключён из контекста. Отсутствие порта означает отсутствие отправки. Действующий ChannelAdapter.send пока не возвращает всех данных receipt; его интеграция остаётся F3.2.

Defaults createPublicationService: noticeIntervalMs = 300000 (пять минут), queueFullTimeoutMs = 10000. Параметры задаёт инфраструктурная сборка; это изменяемые значения, новых переменных окружения нет. Период — положительное безопасное целое с проверкой суммы времени; queueFullTimeoutMs дополнительно ограничен диапазоном таймера. Все причины notice делят один период по чату; перезапуск/смена режима не сбрасывают его. Неудача/неопределённость доставки не возвращает резерв. Фиксированный шаблон: «Сейчас не получилось ответить. Попробуйте позже.»

Публикация после завершения цикла входит в остаток handlerTimeoutMs (default — общий срок цикла плюс запас). Очередь сначала проверяет срок, stop, владение и исходную область, затем передаёт полный исход политике; код completed не заменяет complete с текстом. Перед портом повторно проверяются режим и область. Stop/выключение/uncertain/смена поколения отменяют ожидание; игнорирующий сигнал порт не удерживает слот бесконечно и не записывает позднее подтверждение. Queue_full использует отдельный ограниченный срок и общий предохранитель остановки очереди. Для notice без подтверждённого reply выбирается молчание.

stats() сервиса публикации возвращает безопасные publication_failed/journal_failed; onFailure при необходимости принимает только эти коды. Внешняя отправка и запись SQLite не атомарны: уведомление может быть доставлено до сбоя подтверждения. Автоповтора нет; уже начатую внешнюю отправку нельзя гарантированно отменить. Это локальная реализация на подменах, без разрешения живого доступа Go/VK.

## Согласованные требования F2.5 — ещё не реализованы

[Задача 015](docs/tasks/015-context-builder.md) готовит сборщик: история ограничена исходной записью задания по порядку журнала, а не временем платформы; поздние записи не включаются, окружение предупреждает о возможных новых сообщениях. Reply-источник вне окна учитывается в той же области и границе; для одного вложения без текста предусмотрена нейтральная заглушка без распознавания.

При отсутствии выбранного общего системного промпта модель не вызывается и fallback отсутствует: ошибка конфигурации, отдельный счётчик, проверка перед запуском обработки, публикация как внутренняя ошибка. Если текущее сообщение не помещается, молчаливого усечения и вызова модели нет; различаются слишком большой вход и недостаточный бюджет. Слишком большое текущее сообщение: в normal и личке — короткое reply-уведомление с понятной причиной, в active — молчание. Бюджет, не вмещающий статику: в normal и личке — общее нейтральное reply-уведомление, в active — молчание; отдельная причина и безопасный счётчик для владельца, проверка при запуске. В обоих случаях модель не вызывается; уведомления подчиняются одному общему долговечному периоду F2.4, помечаются служебными и не попадают в контекст.

chats.systemPrompt устарел: F2.5 не применяет его, установка командами запрещена. Техническое поле пока существует; отдельная [F2.10](docs/roadmap.md#веха-2-ядро-без-платформы) удалит его после F2.5 и до F4.2 новой миграцией без изменения прежних, с тестом схемы и обновлением документации. Задача 015 утверждена; [план фичи](docs/plans/015-context-builder.md) утверждён. [План реализации](docs/impl-plans/015-context-builder.md) — черновик, ожидает утверждения перед изменением кода/схемы. План реализации должен состоять из последовательных шагов с зелёной сборкой и тестами после каждого.
