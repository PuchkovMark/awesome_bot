# Правила написания кода

Документ описывает обязательные договорённости для исходного кода проекта. Автоматические проверки настроены в `eslint.config.js`, `.prettierrc` и CI.

## Требования к окружению

- Node.js **22.13+** (см. `.nvmrc`).
- Зависимости устанавливаются командой `npm ci`.

## Команды проверки

```bash
npm run lint        # ESLint без изменений, предупреждения запрещены
npm run lint:fix    # ESLint с автоисправлением
npm run format      # Prettier для src/ и test/
npm run format:check
npm run typecheck   # tsc --noEmit
npm run check       # lint + format:check + typecheck + test
```

Перед отправкой изменений должен проходить `npm run check`.

## Плагины ESLint

- `typescript-eslint` — пресет `strictTypeChecked`, type-aware проверки.
- `eslint-plugin-promise` — рекомендованные правила для работы с промисами.
- `eslint-plugin-import-x` — поддерживаемый форк `eslint-plugin-import` с поддержкой ESLint 10. Включены рекомендованные правила и TypeScript-резолвер; CJS-совместимость и отдельные type-импорты дают ложные срабатывания, поэтому `no-named-as-default`, `no-named-as-default-member` и `no-duplicates` отключены.
- `eslint-plugin-sonarjs` — рекомендованные правила поиска дефектов. Порог `cognitive-complexity` поднят до 200 из-за крупных легаси-обработчиков; отключены шумные стилевые проверки (`prefer-regexp-exec`, `regex-complexity`, `no-nested-conditional`, `super-linear-regex` и подобные).
- `eslint-plugin-security` — выборочные правила безопасности: `eval`, `child_process`, динамический `require`, `fs`-пути, timing attacks, небезопасные буферы и невидимые Unicode-символы. `detect-object-injection` и `detect-unsafe-regex` отключены как шумные; для проверенных путей и регулярных выражений допускаются точечные `eslint-disable` с пояснением.
- `eslint-plugin-unicorn` — режим `unopinionated`. Отключены субъективные правила, которые требуют массовых переписываний (`prefer-ternary`, `no-negated-condition`, `no-array-sort`, `prefer-await` и подобные).
- `eslint-plugin-jest` — рекомендованные правила для `test/**/*.ts`. Проект использует `node:test` и `assert`, поэтому `jest/expect-expect` настроен на `assert.*`, а `jest/no-deprecated-functions` отключён.

## TypeScript

- Режим `strict` обязателен. Не ослабляйте `tsconfig.json` без обоснования.
- Запрещён `any`. Для внешних данных используйте `unknown` и явную проверку типа.
- Не используйте `@ts-ignore`. Если ошибка неизбежна, используйте `@ts-expect-error` с пояснением.
- Запрещены non-null assertions (`value!`). Проверяйте значение или выбрасывайте ошибку.
- Импортируйте типы через `import type` или `type` внутри импорта.
- ESM-импорты локальных файлов указывают расширение `.js`.
- Не оставляйте неиспользуемые переменные, параметры и импорты; неиспользуемые параметры начинаются с `_`.
- Публичные функции и методы должны иметь понятные имена и явные типы параметров. Возвращаемый тип можно выводить, если он очевиден.

## Асинхронность и ошибки

- Используйте `async/await`; не оставляйте «висящие» промисы. Если промис намеренно не ожидается, ставьте `void`.
- Не передавайте `async`-функцию туда, где ожидается синхронный обработчик, без обёртки с обработкой ошибок.
- Ошибки логируйте через `logger`, не через `console`.
- При пробросе ошибки сохраняйте причину: `throw new Error('...', { cause: error })`.
- Не глотайте исключения пустым `catch`. Если ошибка ожидаема, объясните это комментарием.
- Для ожидаемых ошибок возвращайте результат с явным статусом, а не бросайте исключение через границы сервисов без необходимости.

## Именование

- Типы, интерфейсы, классы, перечисления — `PascalCase`.
- Переменные, функции, методы — `camelCase`.
- Константы модуля — `UPPER_SNAKE_CASE`, если это действительно константы.
- Файлы — `camelCase.ts`; имена должны отражать ответственность модуля.
- Булевы значения называйте с префиксом `is`, `has`, `can`, `should`.
- Не используйте сокращения, кроме общепринятых (`id`, `vk`, `ai`, `url`).

## Структура и импорты

- Сначала импорты Node.js, затем внешние пакеты, затем локальные модули.
- Не допускайте циклических зависимостей.
- Бизнес-логика — в `src/services`, инфраструктура — в `src/db`, `src/logger`, `src/di`.
- Не импортируйте внутренние детали сервиса из других сервисов; используйте публичный интерфейс.
- Один модуль — одна основная ответственность.

## Логирование

- Используйте `logger.info`, `logger.warn`, `logger.error` с структурированным объектом: `logger.error({ err, peerId }, '...')`.
- В сообщении указывайте действие и контекст, но не дублируйте данные из объекта.
- Не логируйте токены, ключи, персональные данные и полные тексты сообщений без необходимости.

## Prisma и база данных

- Используйте единый клиент из `src/db/client.ts`.
- Не выполняйте запросы к базе в конструкторах сервисов.
- Для связанных изменений используйте транзакции.
- Не используйте `any` для результатов запросов; описывайте типы через Prisma.
- SQLite-файл и миграции не коммитьте; схема и миграции — единственный источник структуры БД.

## Тесты

- Тесты лежат в `test/*.test.ts` и используют `node:test`.
- Каждый тест проверяет observable-поведение, а не внутренние детали реализации.
- Для внешних API используйте моки или локальный HTTP-сервер; тесты не должны ходить в интернет.
- Тесты должны быть детерминированными: фиксируйте время, случайность и идентификаторы.
- В тестах допускаются послабления для `no-unsafe-*` (моки и `JSON.parse`), но не для логики.

## Форматирование

- Prettier: 100 символов, 2 пробела, одинарные кавычки, точка с запятой, trailing comma.
- Отступы и переводы строк — LF, UTF-8, финальный перевод строки.
- Не смешивайте форматирование и логические изменения в одном коммите.

## Исключения из правил

Исключение допускается только точечно и с объяснением:

```ts
// eslint-disable-next-line @typescript-eslint/no-deprecated -- провайдер принимает только max_tokens
max_tokens: maxOutputTokens,
```

Глобальное отключение правил в `eslint.config.js` допустимо только для правил с известными ложными срабатываниями; причина указывается комментарием.

## Коммиты

- Сообщение коммита формулируется в повелительном наклонении и описывает изменение.
- Не коммитьте `.env`, `node_modules`, `dist`, `logs`, SQLite-файлы.
- Один коммит — одна логическая правка; форматирование выносите отдельно.
