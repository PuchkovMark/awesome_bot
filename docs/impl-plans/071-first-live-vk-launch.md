## Упорядоченные шаги

**При сбое на любом шаге** сохранить версию сборки и настройки. В строке проверки записать канал, роль, шаги, ожидаемый и фактический результат. Воспроизвести проблему и выяснить причину по доступной диагностике. Для исправления завести отдельную задачу со ссылкой на № 071, результатом диагностики и проверяемым критерием. Если причина ещё не подтверждена, указать, что известно и что осталось проверить. Номер задачи записать в исходной строке. Код и настройки для исправления меняются в отдельной задаче. Независимые проверки можно продолжать. После исправления повторить тот же сценарий, сохранить оба результата и версию исправленной сборки. Сценарий в VK повторяет владелец. [Шаблон задачи](../templates/task.md)

### 1. Подготовить сборку и лист приёмки

В новом разделе F9.5 существующего README указать проверяемую сборку, настройки без секретов и время в UTC. До измерений согласовать с владельцем пик обращений за интервал, максимальный объём накопленных данных, запас, допустимое ожидание в очереди и долю отказов. По каждой реализованной функции завести строку с ролью, действием, ожидаемым результатом и двумя полями для наблюдений владельца — «Личка» и «Беседа». Сверить перечень со справочником команд, дорожной картой и сценариями плана фичи. [Сценарии в VK](../plans/071-first-live-vk-launch.md#что-владелец-проверяет-в-работающем-vk) · [Команды](../specs/commands-and-limits.md)

Выполнить `npm run build` и полный `npm test` с подменами VK и модели, поскольку приёмка охватывает всю сборку. Записать результат и версию. Для следующих шагов подходят успешные проверки на той же версии. [Команды сборки](../../package.json) · [Правила проверки](../project.md#проверка-и-документация)

### 2. Измерить всплеск обращений и большую очистку

После сборки выполнить `npm run test:queue-load`. Штатные тесты используют 500 входящих сообщений для всплеска и по 300 000 сообщений и заданий для очистки. Сопоставить настройки, объём и время подачи с согласованным пиком и запасом. Если штатные условия его не покрывают, до приёмочного замера добавить сценарий с согласованными параметрами в соответствующий тест всплеска или очистки. Повторить сборку и нагрузочный тест. [Всплеск](../../tests/load/chat-queue-load.test.ts) · [Очистка](../../tests/load/chat-queue-cleanup.test.ts) · [Генератор данных](../../tests/helpers/queue-load-fixture.ts)

Из результатов текущего прогона на временной SQLite перенести в README число попыток постановки, принятых, отказов `queue_full`, долю отказов от всех попыток и максимальное ожидание принятых. Отдельно записать результат теста с управляемым временем. Для очистки сверить длительность с оставшимся на старте сроком владения очередью с учётом запаса. Проход подтверждают соблюдение согласованных порогов, сохранность контрольной записи во второй беседе и отказ второму процессу в перехвате владения. [Чтение результатов](../../README.md#проверка-нагрузки-очереди)

### 3. Проверить восстановление, лимиты и трассировку

| Мера | Действие и условие приёмки |
| --- | --- |

Провести пробное восстановление в изолированную БД без внешней отправки и открыть её приложением. Сверить известные удаления, отозванные права и доступную запись второй беседы. Записать возраст снимка, длительность, результат сверки и открытия. До успешного восстановления этот пункт остаётся открытым. [Задача 070](../tasks/completed/070-database-backup-and-restore.md) |
| Лимиты | На подменах проверить обычные обращения и поведение на границе квот пользователя и беседы, частоты ответов при флуде, бюджета токенов и общего предела вызовов основной и вспомогательной моделей. Включить истечение ожидания, 429, паузу и восстановление. Записать настройки, ожидаемую и полученную реакцию. [Пределы модели](../../README.md#параллелизм-и-пауза-модели-f91) |

Проверить выдачу объяснения владельцу в личку по выбранным беседе и поколению и отказ обычному участнику. Выполнить `npm test -- tests/response-tracing-publication.test.ts tests/response-tracing-access.test.ts tests/response-tracing-explanation.test.ts tests/application-chat-control.test.ts`. При личном прогоне сверить объяснение с видимым сообщением. [Права на диагностику](../specs/security.md#доступ-к-трассировкам-f26) |

### 4. Запустить бота для личной проверки владельцем в VK

До запуска проверить на тестовых данных доставку действующей версии уведомления F5.8 при первом обращении в личке и при подключении к беседе. Обработку последующих сообщений разрешает подтверждённая доставка для этого чата и поколения. Выполнить `npm test -- tests/application-lifecycle.test.ts tests/storage-chat-disclosure.test.ts tests/application-personal-data.test.ts`. [Правила уведомления](../specs/privacy.md#согласие-и-внешний-провайдер)

В согласованное с владельцем время запустить проверенную сборку в тестовом сообществе командой `npm start`. Дождаться `application_ready`, проверить доступность согласованных лички и беседы и сообщить владельцу, где начинать. Оставить бота работающим на время всей проверки. Владелец лично проходит список из шага 1. Общие функции проверяет в обоих местах. У функции с одним каналом отмечает область действия и проверяет предусмотренную приватную доставку, переход или отказ. Для ролей использовать тестовые аккаунты, для очистки и сброса — специально подготовленные данные. Записать по каждому применимому каналу «прошло», «сбой» или «не проверено» и получить итоговое подтверждение владельца. [Запуск](../../README.md#запуск-приложения) · [Матрица сценариев](../plans/071-first-live-vk-launch.md#что-владелец-проверяет-в-работающем-vk)

Для личной проверки указать начало и конец наблюдения в UTC и значение `LLM_SLOT_WAIT_MS` (по умолчанию 10 000 мс). По событиям `llm_admission` посчитать прямые обращения с `llm_wait_timeout`, фактические ответы HTTP 429 (`rate_limit`) и локальные отказы `llm_provider_paused` по отдельности. Для 429 рассчитать также частоту в минуту. Нулевые значения записать при наличии наблюдения за всем интервалом. Результат с подменой провайдера остаётся в техническом прогоне шага 3. [Диагностические события](../../README.md#параллелизм-и-пауза-модели-f91)

### 5. Получить решение владельца и проверить первый рабочий запуск

Представить владельцу результаты технических проверок и личной приёмки в обоих каналах, а также список открытых сбоев. До обработки реальных сообщений владелец утверждает текст уведомления о профиле и передаче данных провайдеру, а также основание обработки. Для запуска нужны пройденные обязательные проверки, личное подтверждение владельца, выбранные им беседа и дата. При переносе записать причину и условия повторной проверки в README. Задача остаётся открытой.

После разрешения подключить выбранную рабочую беседу штатным способом. Для её поколения подтвердить фактическую доставку вступления с действующим уведомлением, затем получить ответ на адресованное боту сообщение. В README записать дату, согласованное обозначение беседы, версию уведомления и оба наблюдаемых результата без текста переписки. [Вступление и подтверждение доставки](../../README.md#вступление-в-беседу-vk-f36)

### 6. Провести ревью и завершить приёмку

Через `review` сверить критерии № 071 с отчётом в README, проверенной сборкой, тестами и личным подтверждением владельца. Замечания к отчёту устранить и повторить ревью. Сбои бота проходят через отдельные задачи и повтор затронутых проверок на исправленной сборке. Для изменившейся сборки повторить `npm run build` и `npm test`, для изменившихся условий нагрузки — также `npm run test:queue-load`. [Критерии задачи](../tasks/071-first-live-vk-launch.md#критерии-приёмки)

После успешного ревью выполнить `sync-specs`, сверить отчёт со спецификациями очереди, приватности и канала VK, обновить F9.5 в дорожной карте и журнал решений. Указать фактическую дату завершения и статус «выполнено» в задаче и обоих планах. Конечные пути — `docs/tasks/completed/071-first-live-vk-launch.md`, `docs/plans/completed/071-first-live-vk-launch.md` и `docs/impl-plans/completed/071-first-live-vk-launch.md`. При переносе обновить внутренние и входящие ссылки, включая README, дорожную карту и журнал решений, и проверить их цели. [Правила хранения](../project.md#хранение-активных-и-выполненных-задач)
