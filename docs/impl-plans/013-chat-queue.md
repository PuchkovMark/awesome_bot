## Границы и параметры

Реализуется локальная долговечная очередь с одним владельцем БД и подменяемым обработчиком. Роутер F2.4, отправитель, контекст, команды, реальные VK/Go и общий предохранитель F9.1 не подключаются. Интерфейс LlmClient и действующее поведение F2.2 сохраняются. Код очереди и её тестов сейчас отсутствует; все названные ниже новые файлы требуется создать после утверждения этого документа.

Defaults по скорректированному плану: maxConcurrentChats = 4, maxQueuedPerChat = 2, maxQueuedTotal = 8, maxQueueAgeMs = 600000, leaseMs = 30000, renewIntervalMs = 10000, stopTimeoutMs = 10000. Для обработчика handlerTimeoutMs >= loopTimeoutMs + handlerMarginMs; default loopTimeoutMs = 120000, handlerMarginMs = 10000, handlerTimeoutMs = 130000. Все значения проверяются как безопасные положительные целые, поддерживаемые таймерами; renewIntervalMs < leaseMs. Переполнение сумм отклоняет конфигурацию. Принудительная остановка может прервать цикл раньше обычного срока: это отдельное намеренное завершение interrupted.

Связка с F2.2 использует один доверенный снимок настроек цикла для создания экземпляра и проверки бюджета обработчика; указанный отдельно «срок модели», не связанный с фактической конфигурацией, не считается доказательством инварианта. Для произвольного обработчика гарантируется только его собственный конечный срок.

## Упорядоченные шаги

Сбой диагностического получателя не должен останавливать очередь.

Проверить отсутствие привязок глобальной блокировки к удалённым беседам и классификацию всех новых объектов схемы с отрицательным контролем.

### 3. Атомарный приём и ссылки на сообщения

- Цель: обеспечить журнал и принятую постановку одной транзакцией; переполнение фиксирует журнал, а сбой БД откатывает всё. Удаление записи конечного задания не разрешает повторную постановку уже существующего сообщения.
- Модули и файлы: src/storage/queue-store.ts, queue-types.ts, messages.ts, scoped-storage.ts, scoped-types.ts и types.ts; новый узкий контракт чистого синхронного решения в src/core/chat-queue/types.ts. Операция принимает выданную ConnectionScope и сообщение, вставляет журнал, передаёт решению неизменяемый ограниченный снимок без SQL/сервисов. Возвращаемый Promise, неверный результат или исключение отклоняются с откатом. Время передаётся явно; функция не читает часы, I/O и случайность. Асинхронная часть оформляется отдельным заданием, без реализации её бизнес-правил в F2.3.
- Тесты: новые tests/queue-admission.test.ts и tests/queue-message-references.test.ts; расширить tests/storage-scoped.test.ts. Проверить FIFO постановки, дубликаты с изменённым текстом, после перезапуска и после удаления terminal, ранее записанное без задания и отклонённое при переполнении сообщение. Проверить оба предела, освобождение просроченной вместимости, сбой между журналом/заданием, пересекающиеся постановки через отдельные соединения без ложного заявления о гонке одного синхронного вызова. Сообщение при queue_full остаётся доступным в журнале. В очереди нет копий текста; чтение сообщения по ссылке требует scope и не допускает другой чат/поколение. Проверить пропавшую ссылку и каскадное удаление без воссоздания записи.
- Условие готовности: сборка и все тесты проходят; приложение может использовать атомарный путь, прежнее самостоятельное журналирование сохранено. Синхронность проверяется контрактом и рантаймом, чистота доверенной функции дополнительно проверяется ревью.

### 4. Планирование, восстановление области и справедливость

- Цель: создать работающий явно запускаемый сервис с очередью FIFO внутри чата, циклическим выбором готовых чатов и общей границей параллелизма.
- Модули и файлы: новые src/core/chat-queue/service.ts, scheduler.ts; изменения src/core/index.ts, src/storage/queue-store.ts, queue-registry.ts и lifecycle-store.ts. При восстановлении backend сравнивает сохранённое поколение с текущим и только затем выдаёт новую подлинную scope. Закрытые глобальные операции не экспортируются через публичный интерфейс модели/инструментов; архитектурный тест проверяет их недоступность оттуда. Курсор справедливости не оставляет идентификатор удалённой беседы в долговечной глобальной записи.
- Тесты: новые tests/chat-queue-order.test.ts, tests/chat-queue-fairness.test.ts, tests/chat-queue-recovery.test.ts и tests/chat-queue-lifecycle.test.ts. Проверить FIFO, 4 занятых слота и отказ пятому до освобождения, непрерывный горячий поток и конечный допуск готовой тихой беседы; отдельно показать риск отказа в приёме при полностью занятой вместимости. Проверить queued после пересоздания, running → interrupted без вызова обработчика или отправки, возраст без сброса, границу now = expiresAt и будущую дату платформенного сообщения. При uncertain ожидающие не занимают слоты и стареют; после continue запускаются только актуальные queued. Новое поколение и удаление исключают доступ старого задания. Ошибка обработчика не останавливает следующие задания.
- Условие готовности: сборка и тесты проходят; сервис выполняет подменённые задания, не получает новую область для старого поколения и не вызывает сеть. Импорт и создание без явного start не начинают работу.

### 5. Сроки, потеря владения и остановка

- Цель: обеспечить конечные ожидания и корректное освобождение ресурсов во всех путях, включая игнорирующий отмену обработчик.
- Модули и файлы: src/core/chat-queue/service.ts, scheduler.ts; новые src/core/chat-queue/resources.ts; src/storage/queue-store.ts. Собственные таймеры и слушатели отслеживаются и освобождаются; все Promise позднего завершения наблюдаются. Проверка владения выполняется перед взятием и фиксацией; потеря продления закрывает приём и новые запуски. Старый владелец не завершает задания в обход маркера.
- Тесты: новые tests/chat-queue-deadline.test.ts, tests/chat-queue-stop.test.ts и tests/chat-queue-resources.test.ts. Проверить default 130 секунд и изменённые бюджеты, обычный deadline и отдельное прерывание при stop, stop без работы/с queued/с running, идемпотентность, окончание ровно на границе, игнорирование сигнала, поздний успех/отказ и отсутствие повторной записи. Владение продлевается во время ожидания stop; после него освобождается, queued сохранены, новые поступления отклонены. При отказе БД — безопасная ошибка, прекращение работы и восстановление running следующим владельцем после истечения. Проверить длительную паузу/сдвиг часов, удаление и uncertain при текущей работе, запрет позднего результата после удаления и смены владельца. Тесты различают UTC срок БД и монотонные длительности процесса.
- Условие готовности: сборка и тесты проходят; ни игнорирующий отмену обработчик, ни отказ БД не делают остановку бесконечной. Поздний результат не меняет terminal и не порождает публикацию. Прекращение внешней обработки этим не обещается.

### 6. Интеграция F2.2, диагностика и независимость сборки

- Цель: доказать реальные границы между новой очередью, существующим циклом и безопасным логгером на подменах.
- Модули и файлы: сервис/типы очереди, при необходимости новый src/core/chat-queue/agent-loop-adapter.ts для единой проверки снимка настроек без изменения LlmClient или AgentLoop; logger/types.ts и sanitize.ts. Новые tests/chat-queue-agent-loop.test.ts, tests/chat-queue-metrics.test.ts и tests/chat-queue-dist.test.ts; tests/helpers/chat-queue.ts — новый вспомогательный модуль.
- Тесты: реальный createAgentLoop с подменённым LlmClient, server-повторы только внутри одного запуска, rate_limit конечен без нового вызова и не удерживает следующее задание. До собственного срока цикла очередь его не обрывает; при увеличении loopTimeoutMs бюджет пересчитывается или несовместимая сборка отклоняется. Метрики: глубина из БД, ожидание при старте и исходе до старта, rejected только для отказов вместимости, expired/interrupted без повторного счёта одного перехода. Указать окно текущего запуска, неизвестный расход не выдавать за ноль; текста ответа/запроса, chatId, sessionId и маркера владельца в логах нет. Отдельная ESM-сборка dist вне дерева исходников импортируется без сети/таймеров; создание не открывает БД. Публичные методы по чату требуют scope; backend нельзя импортировать из tools, commands и context, включая транзитивные реэкспорты.
- Условие готовности: сборка и все тесты проходят, F2.2 сохраняет свой промежуточный статус. Никакого отправителя, таблицы публикации, юридического согласия и доступа Go этим не реализуется.

### 7. Нагрузочная проверка и большая очистка

- Цель: проверить расчёт вместимости и сроков, а также выбранную атомарную очистку без потери владения. Это самостоятельная проверка, а не комментарий о достаточной скорости SQLite.
- Модули и файлы: новые tests/load/chat-queue-load.test.ts, tests/load/chat-queue-cleanup.test.ts и tests/helpers/queue-load-fixture.ts; отдельная vitest.queue-load.config.ts и команда test:queue-load в package.json. Основная vitest.config.ts исключает tests/load из каждого обычного запуска; отдельный прогон обязателен для приёмки. README описывает команду, среду и воспроизводимый профиль. Новых зависимостей не требуется.
- Тесты: равномерная загрузка, одна шумная и много тихих бесед, всплеск выше вместимости, заблокированные uncertain, предельные времена обработчиков. Управляемое время проверяет модель C/T и FIFO/справедливость, а измеряемый прогон на реальной SQLite проверяет ожидание, отказы, просроченные/прерванные, пропускную способность и длительность остановки. Не принимать 1,85 задания/минуту за измеренный результат: это расчёт для C = 4 и T = 130 секунд; реальные времена отдельно фиксируются.
- Большая очистка: минимум 300 000 сообщений с FTS, связанные участники/факты, версии, административные данные и задания; контроль сохранности другой беседы. Измерить получение транзакции и очистку при продлеваемом владении с запасом не меньше интервала продления. Проверить срок не только после завершения удаления, но и запрет фиксации операции с просроченным маркером; второй экземпляр с отдельным соединением/процессом не получает одновременно действующее владение. Зафиксировать среду, объём и измеренную длительность. Предусловие допуска очистки должно оставлять необходимый запас до истечения lease; обычное ожидание очереди SQLite также входит в бюджет.
- Условие готовности: npm run build, npm test и npm run test:queue-load проходят; атомарная очистка укладывается в подтверждённый бюджет. При провале нельзя молча ослабить тест или добавить порционность с изменением семантики F1.6b: требуется согласовать изменение подхода/конфигурации и повторить прогон. Перед боевым запуском F9.5 обязательно повторяет нагрузку и очистку на ожидаемом максимальном объёме с запасом; текущий стенд не гарантирует произвольный размер БД.

- Шаг 1: типы, конфигурация и безопасные счётчики подготовлены; npm run build и 593 теста прошли. Утверждение плана реализации зафиксировано по сообщению человека 2026-11-22.
- Шаг 2: миграция 7, закрытый backend и владение со сроком реализованы; новые сущности включены в очистку и классификацию. Отдельные соединения проверяют отказ второму экземпляру и старому маркеру. npm run build и 595 тестов прошли; ожидания номера актуальной схемы в двух старых тестах обновлены, миграции 1–6 не менялись.
- Шаг 3: атомарный приём, идемпотентность после переполнения, чтение сообщения по области и ссылка задания реализованы; подмена асинхронного решения отклоняется с откатом. npm run build и 597 тестов прошли.
- Шаг 4: работающий сервис, циклический выбор, восстановление подлинной области только для исходного поколения, перезапуск, устаревание и uncertain реализованы. npm run build и 603 теста прошли. Каркас конечных сроков/остановки включён сразу для безопасного публичного запуска; следующий шаг проверяет его отдельно.
- Шаг 5: проверены конечный срок 130 секунд, ограниченная идемпотентная остановка, игнорирование сигнала, поздний успех/отказ, потеря владения и закрытая БД. Ошибки инфраструктуры отображаются в фиксированные коды очереди. npm run build и 608 тестов прошли; таймеры в проверках освобождены.
- Шаг 6: адаптер связывает фактический снимок настроек F2.2 со сроком очереди; rate_limit конечен, server-повтор остаётся внутри цикла. Проверены безопасные логи, сбой логгера и отдельный ESM-выпуск. Проверка графа импортов расширена на закрытые queue-store/queue-registry; типовой импорт авторизации инструмента сужен до её модуля. npm run build и 616 тестов прошли.
