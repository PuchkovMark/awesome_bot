## Упорядоченные шаги

Перед изменениями сверить исходную ревизию и рабочую копию. После каждого шага с кодом запускать `npm run build` и `npm test -- --maxWorkers=1`. В локальных тестах VK и модель подменяются, БД размещаются во временных каталогах. Ручная функциональная проверка ответов модели через VK остаётся в F3.5.

### 1. Конфигурация установки и безопасная диагностика

- **Цель.** Прочитать и проверить параметры запуска до открытия БД и создания сетевых клиентов.
- **Модули и файлы.** Использовать общий разбор окружения и `.env` из `src/config/index.ts`, расширить допустимые имена в `src/config/types.ts`. Добавить `src/config/application.ts` для проверки параметров конкретной команды. Для запуска нужны `VK_GROUP_ID`, `DATABASE_PATH`, `MODEL_CONTEXT_TOKENS`, `MESSAGE_RETENTION_DAYS`, `LLM_SESSION_SECRET` и действующие параметры клиента и владельца. Путь к БД разрешается от рабочего каталога. Контекст и срок валидируются действующими настройками подготовки и трассировки. Выделить секрет установки из обоих источников конфига в общий редактирующий фильтр. Проверить, что выбранный секрет отличается от ключей выбранных провайдеров. В `src/logger/types.ts`, `src/logger/sanitize.ts` и `src/logger/index.ts` добавить фиксированные стадии и причины приложения. В `.env.example` добавить заполнители. Сохранить режим загрузки для прежних вызывающих сторон.
- **Тесты.** Расширить `tests/config.test.ts` и `tests/config-logger.test.ts`. Проверить приоритет окружения, перекрытые значения и пустые параметры, неверные ID и числа, лимиты контекста и трассировки, постоянный путь, неполную конфигурацию и редактирование обоих значений секрета сессии. Проверить, что диагностика безопасна при ошибках чтения и при импорте без конфигурации.
- **Условие готовности.** Сборка и тесты проходят. Команды получают проверенные параметры своей области. Ошибки до открытия ресурсов различимы без исходных значений.

### 2. Первичный выбор промпта и локальное решение владельца

- **Цель.** Подготовить свежую БД и дать оператору доступ к существующему решению для конкретной беседы.
- **Модули и файлы.** В новом `src/app/setup.ts` использовать текущие `src/storage/storage.ts`, `src/storage/catalog-admin.ts`, `src/core/context/startup.ts` и `src/core/lifecycle/service.ts`. Предусмотреть `npm run init:prompt -- <файл>` с выбранным оператором UTF-8 текстом. Перед выбором проверить бюджет. При прерывании между добавлением и выбором повтор использует совпадающую версию первичной настройки. Существующий активный выбор сохраняется. Для `npm run resolve:chat -- vk:<peer_id> --continue` и варианта с `--new` проверить единственный явный адрес и решение, затем вызвать доверенный API владельца для той же БД. `--new` применяет действующий сброс выбранной беседы. Доверие даёт локальный доступ к установке. Для первичной настройки нужны только её параметры каталога и контекста. Для решения владельца нужны путь к БД и конфигурация владельца.
- **Тесты.** Добавить `tests/application-setup.test.ts`. Проверить свежую БД, миграции, бюджет, сохранённый выбор, повтор после частичной инициализации, несовпадающий ранее сохранённый текст и конфликт выбора. Проверить продолжение и сброс с отдельного соединения с той же БД, точный адрес, устаревшую область, сохранение соседней беседы и отсутствие сетевых запросов.
- **Условие готовности.** Сборка и тесты проходят. Локальная настройка воспроизводима, а решение владельца затрагивает только указанную беседу.

### 3. Владение очередью до начала приёма

- **Модули и файлы.** Расширить доверенные опции `src/core/chat-queue/types.ts` и передать их через `src/core/chat-queue/agent-loop-adapter.ts` и `src/core/chat-queue/service.ts` в `src/storage/queue-store.ts`. При успешном получении владения выполнить начальную паузу выбранной платформы перед первым взятием задания. Согласовать паузу и получение владения одной транзакцией с нейтральной операцией `src/storage/lifecycle-store.ts`. Сохранить штатное восстановление `running` как `interrupted`, ограничения очереди для `queued` и поведение вызовов без новой опции. В случае сбоя откатить транзакцию. Передать сигнал прекращения владения сборке приложения через имеющийся сигнал очереди.
- **Тесты.** Расширить `tests/queue-lease.test.ts` и `tests/chat-queue-recovery.test.ts`. Использовать два экземпляра и одну временную БД. Проверить, что второй экземпляр при отказе владения оставляет ревизии и состояние первого без изменений. Проверить старые активные области, постановку паузы до обработки `queued`, поведение после продолжения, восстановление `running`, другую платформу, отказ паузы и освобождение владения после остановки.
- **Условие готовности.** Сборка и тесты проходят. До явного допуска обработчик отложенной работы VK не запускается. Ошибка нового запуска не меняет беседы работающего экземпляра.

### 4. Готовность и отмена запросов VK

- **Цель.** Объявлять готовность по первой корректной странице Bots Long Poll и закрывать новые запросы при остановке.
- **Модули и файлы.** Уточнить уведомление о первом принятом ответе в `src/channels/vk/long-poll.ts` и передать его через `src/channels/vk/inbound.ts` и `src/channels/vk/channel.ts`. Сохранить обработку событий первой страницы и паузу при разрывах. В `src/channels/vk/api.ts` передавать сигнал в получение сервера, обогащение и повторы чтения. Для общих пакетных запросов профилей применять сигнал приложения. Перед запуском запроса после ожидания использовать действующую проверку допуска. Первое ожидание готовности в композиции ограничить 45 секундами с начала опроса. Этот срок учитывает штатное длинное ожидание одной страницы.
- **Тесты.** Расширить `tests/vk-long-poll.test.ts`, `tests/vk-api-rate-limit.test.ts` и `tests/vk-inbound-integration.test.ts`. Проверить пустую корректную страницу, событие на первой странице, ошибку доступа, смену позиции, отмену ещё при получении сервера, при запросе страницы и в ожидании повтора. Проверить безопасное завершение при позднем ответе транспорта.
- **Условие готовности.** Сборка и тесты проходят. До корректной страницы готовность не устанавливается. Отмена прекращает новые запросы и допуск событий, в том числе после ожидания лимитера.

### 5. Штатная точка входа и остановка приложения

- **Цель.** Собрать проверенный путь и завершать его с предсказуемым исходом.
- **Модули и файлы.** Добавить `src/app/service.ts` для управляемой композиции и `src/app/cli.ts` для входа из процесса. Источник жизненного цикла сохраняет неопределённость при отсутствии доказательств. Использовать текущую политику журнала и публикации, а индикатор набора подчинить исходному допуску задания. Привязать остановку к `SIGINT`, `SIGTERM`, истечению срока готовности, завершению опроса с ошибкой и потере владения. Единый сигнал закрывает новый вход, подготовку, обращения к модели и публикацию. Подключить `npm start`, `npm run init:prompt` и `npm run resolve:chat` в `package.json`. Импорт входного модуля оставляет запуск явной операцией.
- **Тесты.** Добавить `tests/application-lifecycle.test.ts` и `tests/application-cli.test.ts`. Прогнать штатный вход с заменой внешних транспортов. Проверить готовность, отказ при старте, остановку после частичного старта, два чата и журнал до вызова модели, служебное событие, явный допуск владельца и подтверждение отправки. Проверить стабильность HMAC после перезапуска и его смену между поколениями и секретами. Проверить оба сигнала процесса и повторный сигнал, остановку во время опроса, подготовки, модели и публикации, задержку закрытия БД, тайм-аут и поздние результаты. Проверить состояние очереди при повторном открытии БД и безопасную диагностику всех исходов.
- **Условие готовности.** Сборка и тесты проходят. Запуск, подготовка и решение владельца доступны через команды. После закрытия допуска обработка не начинает новые внешние действия. Закрытие БД происходит после завершения связанных операций либо процесс завершается по общему сроку.
