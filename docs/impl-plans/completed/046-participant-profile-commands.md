## Упорядоченные шаги

Каждый шаг завершать сборкой `npm run build` и указанными проверками Vitest на временной SQLite и подмене VK. Приёмка использует существующие факты F5.3. Просмотр заполненной анкеты, её пятнадцатиминутный срок и показ анкеты другим участникам относятся к F8.5.

### 1. Получить собственные действующие факты

В `src/storage/profile-fact-selection.ts` выделить общие правила выбора действующей версии и приоритета источников. Подключить отдельное чтение для проверенного автора через слой авторизации и хранения. Публичный читатель в `src/storage/profile-fact-reader.ts` продолжает отбирать данные для аудитории ответа. Личная выборка возвращает значение, источник, видимость и внутреннюю версию позиции, включая изменение ограничения видимости. Выбор чата из лички проверять по существующему личному маршруту F5.8. Чужой ID в аргументе не даёт права прочитать профиль другого человека.

Расширить `tests/profile-personal-data.test.ts` и выполнить вместе с `tests/profile-public-read.test.ts`. В двух беседах создать тёзок, для одного автора — два разных интереса и закрытое поле. Готово, когда каждый получает только свои действующие значения выбранной беседы, закрытое поле остаётся доступно автору, администратор и модель продолжают получать только разрешённую публичную выборку.

### 2. Связать личный список с получателем и областью

Добавить следующую свободную миграцию в `src/storage/migrations/` и зарегистрировать в `index.ts`. В новом `src/storage/profile-command-store.ts` сохранять получателя, исходный чат и поколение, версию открытия списка, позиции и версии фактов. Хранить технические ключи доставленных частей и событий обработки. Значения фактов в списках SQLite не дублировать. Новый запрос просмотра заменяет предыдущий список автора. Параллельное открытие двух бесед упорядочить до отправки, чтобы позднее подтверждение первого запроса не активировало старую выдачу.

Срок действия списка — **24 часа с открытия по UTC**. На границе срока номер уже недействителен. Просроченные привязки очищать при штатном обслуживании БД. Удаление данных автора и сброс любого участвующего подключения прекращают действие привязок. Восстановление резервной копии не должно снова разрешать ответы на старые списки.

Добавить `tests/storage-profile-commands.test.ts`, обновить проверки миграции, включая `tests/storage-participant-upgrade.test.ts`, и перечень сущностей в `tests/lifecycle-cleanup-coverage.test.ts`. Проверить старую БД, перезапуск, точную границу срока, переключение беседы, запоздавшую квитанцию, очистку и восстановление. Готово, когда возобновляется лишь действующий список с подтверждёнными сообщениями.

### 3. Подключить чтение по команде /профиль

Новый обработчик `src/app/profile-commands.ts` подключить в `src/app/service.ts` к штатным групповому и личному маршрутам по образцу `src/app/personal-data.ts`. В группе область задаёт входящее сообщение. В личке без аргумента используется личный диалог, с аргументом — подтверждённая область указанной беседы. Проверять автора и адрес личной доставки перед каждой отправкой. Пустой профиль получает короткий ответ; при отказе личной доставки в группе разрешена только нейтральная подсказка. Не передавать запрос и ответ модели.

В `src/channels/vk/channel.ts` использовать путь подтверждения из `src/channels/vk/administration-delivery.ts`. Обычный `replyPrivateControl` не сохраняет ID служебной части, а для ответа на список нужен проверенный ID сообщения в личке. Разбивать длинный список по пределу VK с непрерывными номерами, по возможности между позициями. Для ответа на часть принимать только номер позиции, полностью доставленной в составе этого списка. При разрыве внутри длинного значения дождаться всех его частей. Отделять текст факта от номера и метаданных, чтобы перенос строки в значении не подделывал новую позицию. Перед отправкой следующей части повторно проверять область и актуальность.

Добавить `tests/application-profile-commands.test.ts` на основе `tests/helpers/application-response-fixture.ts`. Проверить все три способа выбрать профиль, пустой список, несколько частей, частичную и неопределённую доставку. Готово, когда закрытые значения приходят только в проверенную личку автора, в группе отсутствуют даже названия закрытых полей, а по неподтверждённому сообщению нельзя выполнить правку.

### 4. Исполнить личные команды изменения

В обработчике принимать `/исправить N значение`, `/скрыть N` и `/отклонить N` только ответом автора на актуальное сообщение его списка. В `src/core/authorization/service.ts` и `src/storage/profile-fact-store.ts` добавить узкую операцию изменения собственного факта из проверенной лички. Текущая запись из переписки ищет сообщение-источник в целевом чате; передача туда ID личного сообщения может указать на другую реплику. Личное служебное событие учитывать в его собственной области.

В одной транзакции проверить полномочия, поколение, срок, позицию, версию и защиту от повтора входящего события. Исправление создаёт утверждение самого участника с сохранением ограничения видимости; при замене интереса прежнее значение перестаёт действовать, соседние интересы сохраняются. Скрытие применяет правило F5.3 к выбранному сведению. Отклонение допустимо только для действующего вывода бота. При изменении выбранного факта, смене беседы или неподтверждённом reply предложить повторить `/профиль`. Ввод с личным значением обрабатывать как служебный, включая неверный номер и ошибочно отправленную в группу команду. Полное удаление направлять в уже работающую процедуру F5.8.

Расширить тесты шагов 2–3. Проверить пересылку списка тёзке, одинаковые ID сообщений в разных чатах, две конкурирующие правки одной версии, повтор после перезапуска, скрытие и исправление закрытого интереса, отказ при попытке отклонить собственное утверждение. Готово, когда каждое допущенное событие меняет ровно выбранное сведение один раз, а текст правки отсутствует в FTS, вводе модели, трассировке и публичном ответе.

### 5. Провести сквозную приёмку, ревью и синхронизацию

Через обычный маршрут VK проверить цепочку «просмотр из группы → личный список → скрытие → повторный публичный поиск». Отдельно начать подготовку ответа по публичной карточке, скрыть поле личной командой до отправки и проверить ноль публикаций устаревшего ответа. Выполнить `tests/application-personal-data.test.ts` для прежнего личного подтверждения удаления, `tests/application-participant-tools.test.ts` для публичной выдачи и новые тесты 046. Итоговые проверки — `npm run build`, `npm test -- --maxWorkers=4` и `npm run test:queue-load`.

Провести `review`, устранить замечания, повторить проверку. После успешного ревью выполнить `sync-specs` для команд, профилей, приватности и хранения. Обновить дорожную карту и журнал решений, проставить даты завершения и перенести документы в `docs/tasks/completed/046-participant-profile-commands.md`, `docs/plans/completed/046-participant-profile-commands.md` и `docs/impl-plans/completed/046-participant-profile-commands.md`. Проверить входящие и внутренние ссылки. Готово, когда выполнены критерии утверждённой задачи, сборка и тесты прошли и замечания ревью закрыты.

## Результаты приёмки

Ревью завершено без открытых замечаний. Реализация вошла в рабочую копию `harness` и сохранена в ветке `plan-046-profile-commands` до коммита `f41d527`.

- Прошли сборка, 1185 обычных тестов и 10 нагрузочных теста очереди. Сетевой тест сравнения делегирования OpenCode Go пропущен по умолчанию.
- На подмене VK проверены три способа открыть профиль, пустой профиль, нейтральная подсказка при запрете доставки, тёзки и скрытые поля в личной выдаче. Для длинной позиции потеря подтверждения блокирует правку по всем её частям.
- На временной SQLite проверены разные профили одного автора, совпадающие номера в разных чатах, параллельные правки, переключение списка, поздняя квитанция, перезапуск, срок 24 часа, сброс обоих подключений, подтверждённое удаление и сверка копии. Скрытие, исправление и отклонение сохраняются после открытия базы.
- Сквозной сценарий подтвердил исчезновение интереса из публичного поиска и отмену готовящегося ответа по устаревшим данным. Ввод с личным значением отсутствует в журнале, FTS и запросах модели. Штатная процедура подтверждения F5.8 прошла регрессионные тесты.

Приёмка использовала синтетические факты, подмену VK и управляемые ответы модели.
