## Упорядоченные шаги

Перед реализацией зафиксировать исходную ревизию и уже имеющиеся правки рабочего дерева. После каждого шага выполнять `npm run build` и `npm test` и записывать результат. Все выполняемые в F2.8 сценарии используют SQLite в памяти, синтетические данные и локальные подмены клиента и отправителя.

### 1. Первый сценарий через штатный путь

- **Цель.** Запустить сценарий неполной истории через роутер, SQLite, очередь, сборку контекста, подмену модели и публикацию.
- **Модули и файлы.** Новые `src/evals/types.ts`, `src/evals/scenarios.ts`, `src/evals/runner.ts`. Переиспользовать `src/core/index.ts` и `src/storage/index.ts` для композиции. Для каждого сценария создать новую область в собственной БД в памяти, выбрать синтетическую общую версию промпта и записать начальную историю. Через `createMessageRouter` передать вход, снять фактический запрос на границе клиента и принять публикацию через `createPublicationService` с синтетической квитанцией. Дождаться завершения обработки и публикации по штатным событиям очереди. Ветви без поставленного задания завершаются по результату роутера. Ожидание ограничено, очередь и БД закрываются также при сбое.
- **Критерии.** Сценарий имеет стабильный идентификатор, ревизию, идентификаторы критериев, исходное состояние, вход и инструкции оператора для VK. В сценарии неполной истории старые записи остаются за пределом окна, в запросе видна доступная часть. Для первого положительного прогона предопределённый ответ содержит конкретный доступный факт и оговаривает ограниченность истории. Проверки отдельно видят признаки в запросе и публикации.
- **Тесты.** Новый `tests/evals-runner.test.ts`. Проверить с реальной SQLite и штатной композицией порядок и границу истории, неизменный снимок промпта, доставку через подмену и отсутствие переноса истории между двумя последовательными прогонами. Сравнить результат при одном и том же синтетическом состоянии. Проверка запускается в обычных тестах.
- **Условие готовности.** Сборка и обычные тесты проходят. Первый сценарий воспроизводим, он проходит через существующие порты ядра и возвращает оценку наблюдённых критериев.

### 2. Стартовый набор F2.7 и проверяемые исходы

- **Цель.** Покрыть согласованные источники вложенных инструкций и контрольные случаи, подготовить данные для ручной оценки через VK.
- **Модули и файлы.** Дополнить `src/evals/scenarios.ts`, `src/evals/types.ts`, `src/evals/runner.ts`. Использовать правила из [сценариев F2.7](../../specs/evals.md#граница-данных-контекста-f27). Добавить случаи текущего текста, имени, истории и reply, включая реплику бота, и контрольные обычные запросы в личке и беседе. Для случая с именем подготовить две изолированные синтетические области с разными фактами. Одна ревизия сценария задаёт как проверяемые признаки локального запроса, так и шаги подготовки, точные сообщения и признаки ручной проверки в VK. Для случая, где свойства интерфейса не позволяют установить исходное состояние или проверить критерий, предусмотреть запись «не проверен» с причиной.
- **Исходы.** Различать прохождение, нарушение критерия и технический сбой. Проверки используют разобранные поля, роли, маркеры и событие публикации. Технический отказ клиента не записывается как нарушение поведения модели. Проверки намеренного нарушения и технического отказа выполняются тестовыми вариантами подмены, а стандартный локальный прогон получает положительные фикстуры.
- **Тесты.** Дополнить `tests/evals-runner.test.ts`, добавить `tests/evals-scenarios.test.ts`. Проверить уникальность идентификаторов сценариев и критериев, наличие ревизий и ручных шагов, структуру переданного контекста, отсутствие чужого факта, обычный ответ, контролируемое нарушение и технический отказ. В сценарии reply проверить источник и факт публикации. Для ограниченной истории отдельно описать в ручных шагах наблюдаемый признак ложного утверждения о полном разговоре.
- **Условие готовности.** Сборка и обычные тесты проходят. Стартовый набор использует текущее поведение бота и выдаёт различимые результаты для положительной подмены, нарушения и технической ошибки.

### 3. Ручной запуск, JSON-отчёт и чек-лист VK

- **Цель.** Сделать локальный набор запускаемым оператором и предоставить инструкцию для будущей ручной проверки из того же каталога.
- **Модули и файлы.** Новые `src/evals/report.ts`, `src/evals/cli.ts`, `src/evals/checklist.ts`, существующие `package.json` и `README.md`. После сборки `npm run eval:local -- --out <путь>` запускает собранный ESM-каркас и сохраняет JSON в указанный новый файл. Существующий отчёт сохраняется при повторном запуске на тот же путь. Публиковать готовый файл целиком после успешной записи. Исполнить все сценарии, записать итоги и вернуть ненулевой код при нарушении или техническом сбое. Ошибка пути или аргументов сообщает безопасную причину. Вариант `npm run eval:local -- --checklist` выводит инструкции VK из того же набора без запуска сценариев. README содержит обе команды, расположение отчёта и пример записи результата оператором.
- **Отчёт.** Записать версию формата, время UTC, вид запуска, идентификаторы и ревизии сценариев, модель, точную ссылку промпта из снимка при наличии, версию персонажа при применении, итоги и коды оснований критериев. Каждый повтор сохраняется отдельной записью. Для ручного прогона описать заполнение тех же полей с видом запуска VK и исходом «не проверен» для недоступного наблюдения. Данные отчёта формируются из перечисленных полей, без копирования контекста, текстов ответов, исходных ошибок или секретов. Отчёт хранится отдельно от рабочей SQLite и удаляется оператором после сравнения.
- **Тесты.** Новые `tests/evals-report.test.ts` и `tests/evals-cli.test.ts`. Проверить разбор JSON, точные метаданные, UTC, отсутствие контрольных секретов в отчёте, сохранение технической причины и отказ при записи поверх существующего результата. Из собранного ESM запустить команду с временным файлом и проверить код выхода, синтетический результат и чек-лист. Сопоставить идентификаторы и ревизии в чек-листе и отчёте. Проверки выполняются без конфигурации VK или ключей модели.
- **Условие готовности.** Сборка, обычные тесты и ручной локальный запуск проходят. Сохранён отчёт, а чек-лист задаёт шаги и критерии для проверки через VK после подключения бота и разрешённой проверки провайдера.
