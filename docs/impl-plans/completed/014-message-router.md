## Исходное состояние и границы

Реализованы миграции 1–7, защищённое областью хранилище, авторизация, цикл F2.2 и очередь F2.3. Роутера, метки уведомления, долговечного периода уведомлений и отдельного читателя контекста пока нет. isBot уже обязателен в IncomingMessage. Публичного поиска по журналу пока нет; FTS существует в БД. Текущая связка цикла и очереди теряет полный исход после сведения к completed/failed; очередь дополнительно проверяет срок и владение после завершения обработчика.

Здесь реализуются локальная маршрутизация, политика реакций и проверяемый на подменах контракт публикации. Синтаксис/исполнение команд, самостоятельные поводы F4.7, сборка контекста F2.5 и реальный отправитель не входят. Миграции 1–7 неизменны; старое поведение always не сохраняется. F2.9 остаётся отложенной, F2.2 — «реализовано на подменах, ожидает валидации».

Пути с пометкой «новый» предлагаются этим планом; остальные существуют. Каждый шаг завершается npm run build и указанными тестами. Полный npm test запускается после изменений схемы/общих контрактов и на итоговой приёмке; отдельная нагрузка — после окончательной интеграции очистки. Сборка уже включает lint, проверку границ каталога и typecheck. Зависимости не добавляются, .env/ключи и внешние API не используются. До начала реализации записать базовый коммит для review; каждый законченный шаг оформлять отдельно.

## Технические параметры и проверяемые правила

- Период уведомлений: настройка noticeIntervalMs, начальное значение 300000 мс. Это предложение данного плана реализации, не новый норматив спецификации. Принимается только положительное безопасное целое; переполнение вычисления следующего разрешённого времени отклоняется. Период общий для всех причин одного чата, не меняется пользовательским текстом. При откате UTC-времени назад новое разрешение не выдаётся раньше сохранённой границы.
- Начальный нейтральный шаблон для строк «уведомление»: «Сейчас не получилось ответить. Попробуйте позже.» Код исхода не включается в текст. Шаблон фиксирован приложением, не формируется моделью; сообщение только reply к источнику.
- Хранимый вид сообщения: conversation либо service_notice; для старых записей conversation. Обычный входящий путь не принимает service_notice; успешную служебную запись создаёт только подтверждение доверенного разрешения уведомления. Общий журнал сохраняет все записи, читатель контекста — только conversation.
- Минимальная запись маршрута задания: вид обычного обращения, исходный эффективный режим и признак беседы/лички; привязка к существующим job/message и поколению. Никаких копий текста, имени, контекста или ответа. Старое задание без этих признаков не получает автоматического разрешения публикации.
- Решение роутера не логирует и не выполняет действия. Счётчик причины unknown ведёт внешняя оболочка в окне текущего запуска; долговечная трассировка остаётся F2.6. Счётчик не используется для предоставления прав.

### Граница прямого обращения по имени

Нормализация использует Unicode, регистр и е/ё; сравниваются целые слова Пенек/Пенёк, без совпадений внутри «пенёчек» или «суперпенек». Пробелы, обычная пунктуация и положение имени не определяют тип обращения. Разбор не изменяет исходный текст журнала.

Начальная консервативная грамматика: отдельный зов именем; приветствие с именем; просьба с явным обращением во втором лице или словами «помоги», «подскажи», «расскажи», «объясни», «покажи», «скажи», «ответь»; вопрос с обращением «ты/тебе/тебя/твой» либо формулой «как дела» и именем. Это ограниченный набор признаков, а не понимание любой русской фразы. Обсуждение бота в третьем лице, имя только внутри цитаты и наличие другого явно названного адресата не дают прямого обращения; при противоречии признаков выбирается свободное упоминание. Для иных форм остаются надёжные isMentioned/isReplyToBot. Уточнение словаря не должно расширять самостоятельные поводы.

| Пример | Ожидаемая классификация |
| --- | --- |
| «Пенек помоги с задачей»; «Помоги с задачей Пенёк» | Прямое обращение |
| «Подскажи пожалуйста Пенёк как это сделать» | Прямое обращение |
| «Как ты думаешь Пенек»; «Как дела Пенёк»; «ПЕНЁК!» | Прямое обращение |
| «Пенёк сегодня молчит»; «Мы обсуждали бота Пенек» | Свободное упоминание |
| «Он сказал: “Пенёк помоги”» | Цитата, без прямого обращения |
| «Иван помоги настроить Пенек» | Другой адресат/неоднозначность, без прямого обращения |
| «Пенёчек»; «суперпенек» | Нет распознанного имени |

Положительные пары дополнить переносом имени в начало/середину/конец и заменой пунктуации; отрицательные — вопросами о боте в третьем лице и смешанными цитатами. Если при реализации эта грамматика требует нового продуктового выбора, не маскировать его эвристикой: остановить зависимую часть и согласовать изменение плана.

### 4. Долговечное разрешение уведомления и подтверждение

- Цель: общий период не обходится разными причинами, повтором, перезапуском или двумя соединениями; подтверждение не подделывает служебную запись.
- Модули и файлы: новые `src/storage/notice-store.ts`, `notice-types.ts`, `src/core/message-router/notice-config.ts`; [storage](../../../src/storage/storage.ts), [scoped-storage](../../../src/storage/scoped-storage.ts) и [scoped-types](../../../src/storage/scoped-types.ts). Внутренний фасад публикации не предоставляется командам, инструментам или контексту; расширить [проверку графа](../../../scripts/check-catalog-boundary.mjs) и её [фикстуры](../../../tests/catalog-boundary.test.ts) для закрытого доступа.
- Операция резервирования получает подлинную ConnectionScope, ссылку на исходное сообщение и проверенные признаки маршрута; в одной транзакции проверяет поколение/active, enabled, допустимый текущий режим и время. Период общий для чата; отказ не меняет журнал. Выдаётся непрозрачное разрешение, связанное с источником и областью; резерв при сбое не возвращается. Область нельзя восстановить из голого chatId. Инфраструктурное время берётся доверенной оболочкой, не участником.
- Подтверждение успешного порта принимает данные фактически отправленного уведомления и исходное разрешение, пишет assistant/service_notice с reply к источнику идемпотентно. Повтор подтверждения не дублирует журнал; коллизия с обычным сообщением не переклассифицирует его. Подделка/чужая область/новое поколение отклоняются. Отказ/неопределённость доставки не создают запись об успешном уведомлении и не порождают автоматический повтор. В памяти не остаётся неограниченного списка использованных разрешений; по завершении/отмене они освобождаются.

Значение по умолчанию, неверные числа/переполнение, точная граница периода, откат времени, разные причины и чаты, перезапуск, смена режима. Состязание двух соединений/процессов на один файл — одно разрешение; Promise.all одного синхронного соединения не считается доказательством гонки. Проверить удаление/новое подключение, отмену до отправки, повтор подтверждения и сбой БД после внешнего успеха без нового поколения/повторной отправки.
- Условие готовности: npm run build и тесты проходят; есть локальная атомарность резервирования, нет обещания атомарности SQLite с внешней отправкой. Число периода и шаблон документируются как конфигурация, а не изменяемые моделью данные.

### 5. Атомарный приём с маршрутом и служебная граница

- Цель: подключить чистое решение после записи журнала, сохранить минимальные признаки для перезапуска и отделить выключенный служебный путь.

Использовать существующие [авторизацию](../../../src/core/authorization/service.ts), [настройки](../../../src/storage/chats.ts) и [область](../../../src/contracts/lifecycle.ts).
- Порядок контракта: сначала добавить отдельный типизированный routed-приём рядом с работающим булевым QueueDecision; затем подключить роутер и его потребителей. Снимок routed-приёма включает настройки, прочитанные в той же транзакции после append, и валидированные нормализованные признаки входа. Результат — конечное решение с причиной и минимальными сохраняемыми признаками; Promise/неверная форма откатывают приём. Не считать старый булевый приём разрешением публикации. Старые тесты нейтральной очереди продолжают работать; все производственные пути роутера используют routed-приём.
- Подготовка: перед обычным приёмом доверенная оболочка получает существующую область и создаёт настройки normal/enabled true только при их отсутствии; существующий enabled false не перезаписывает. Включённые сообщения, в том числе молчание true/unknown и silent, журналируются до окончательного решения. При duplicate не повторяются решение, обработчик и уведомление; queue_full остаётся без задания и возвращает данные для политики реакции.

Обычный участник не получает этот путь через действие с минимальной ролью member; текст «я владелец» и isAdmin не помогают.

### 6. Передача полного исхода после окончательной проверки очереди

- Цель: политика видит реальный исход F2.2, а просроченный/прерванный/устаревший результат не начинает публикацию.
- Модули и файлы: [agent-loop-adapter](../../../src/core/chat-queue/agent-loop-adapter.ts), [сервис](../../../src/core/chat-queue/service.ts), [типы очереди](../../../src/core/chat-queue/types.ts), [queue-store](../../../src/storage/queue-store.ts); новый `src/core/message-router/publication-service.ts`. Контракты LlmClient и AgentLoop не расширяются разрешением действий; полные тексты не добавляются в очередь или логи.
- Расширить обработчик совместимым типизированным конвертом полного результата рядом со старым QueueOutcome. Очередь сначала проверяет фактические deadline/stop, владение и область и фиксирует конечный исход; только принятый актуальный результат допускается к обработке политикой. Полный результат удерживается кратко в памяти и передаётся после этой проверки, до потери деталей при сведении к QueueOutcome. Повторный callback, поздний resolve/reject и восстановленный interrupted публикацию не вызывают. Не размещать отправку внутри loop handler до проверки finish. Если полного результата нет из-за сбоя обработчика, политика получает явный принятый исход очереди, а не выдуманный исход F2.2; expired/interrupted/message_missing остаются молчанием. Deadline цикла при ещё действующем бюджете обработчика может дать notice по таблице; после исчерпания общего бюджета новый вызов порта не начинается, допустимое уведомление подавляется ограничением времени.
- Порт публикации принимает разрешённый вид реакции, scope и reply-источник; его подмена возвращает явные delivered/failed/unknown и данные подтверждённой отправки. Перед вызовом проверить текущие enabled/режим и исходный маршрут, сигнал отмены и возможность reply. Старое active не получает уведомление после смены в normal; старое normal не получает уведомление в новом active/silent. Для notice использовать разрешение шага 4, затем подтверждение для журнала. Отсутствие порта означает отсутствие отправки, а не готовность адаптера.
- Жизненный цикл порта управляемый: его ожидание входит в общий срок обработки и положительный запас после F2.2, получает AbortSignal и не блокирует stop бесконечно. Один чат не начинает следующую обработку, пока обслуживается его допустимая публикация; справедливость других чатов сохраняется. Фиксация terminal и внешняя доставка не объявляются общей транзакцией. Утрата владения/stop после фиксации запрещает начинать новый вызов; уже начатую внешнюю отправку нельзя гарантированно отменить. Callback, игнорирующий сигнал, не удерживает слот и не меняет состояние поздним результатом.
- Тесты: новые `tests/router-loop-publication.test.ts`, `router-publication-lifecycle.test.ts`; расширить [цикл/очередь](../../../tests/chat-queue-agent-loop.test.ts), [deadline](../../../tests/chat-queue-deadline.test.ts), [stop](../../../tests/chat-queue-stop.test.ts), [порядок](../../../tests/chat-queue-order.test.ts). Настоящий F2.2 с подменённым LlmClient покрывает все исходы, server-повтор внутри одного шага и конечный rate_limit без перепланирования. Проверить complete против failed/incomplete/refused/empty, тишину active и interrupted, смену mode/disabled/uncertain/generation/владельца очереди между завершением и портом. Проверить край срока до запоздавшего таймера, зависший/бросающий порт, остановку во время отправки, позднее подтверждение без повторной записи/отправки и освобождение ресурсов.
- Условие готовности: npm run build и тесты проходят; результат публикуется на подмене только после окончательной проверки очереди, все ожидания ограничены существующим общим бюджетом. Совместимость старого обработчика не создаёт неявный путь публикации.

### 7. Счётчики и сквозная проверка поведения

- Цель: сделать unknown наблюдаемым без персональных данных и доказать связь между приёмом, исходом, общим периодом и журналом.
