## Упорядоченные шаги

Каждый шаг завершать его целевыми проверками и успешным `npm run build`. Для интеграционных проверок использовать отдельную SQLite, управляемые часы и подмену VK.

### 1. Расширить хранилище участия и зафиксировать порядок наблюдений

Добавить новую миграцию со свободным номером в `src/storage/migrations/`, зарегистрировать в `index.ts`, расширить `src/storage/participant-types.ts`. Включить статус `absent` для подтверждённого отсутствия без известной причины. Сохранить ключ участника внутри беседы, существующие значения и связи профилей и фактов. Раздельно хранить сведения о последней попытке сверки, её полноте и времени последнего принятого полного снимка. Защитить запись поколением подключения и порядком наблюдений, сохраняемым при перезапуске.

Расширить `tests/storage-participant-upgrade.test.ts`, `tests/storage-participant-model.test.ts` и `tests/lifecycle-cleanup-coverage.test.ts`. Обновить БД с заполненными участниками, профилями и фактами, проверить внешние ключи и значения после повторного открытия. Полная очистка поколения удаляет его состояние сверки, соседняя беседа сохраняется.

### 2. Применять события к конкретному участнику

Провести вид нормализованного события из `src/channels/vk/normalize.ts` через `inbound.ts` в прикладной обработчик в `src/app/service.ts`. Для реестра сохранить различие выхода и исключения, которое нельзя восстановить из одного булева признака присутствия. Достоверное вступление обновляет существующую запись. Для одного лишь приглашения запросить сверку. Сохранить отдельное действие существующего механизма полномочий. Учитывать повтор по идентичности события в своей беседе и поколении. Когда порядок противоречивых событий установить нельзя, сохранить достоверное состояние, пометить необходимость сверки.

В пути записи допущенного сообщения в журнал обновлять `lastSeenAt` максимумом известного времени сообщения. Сообщение не назначает роль и не устанавливает дату вступления. Добавить тесты переходов в новом `tests/participant-registry-events.test.ts`. Проверить повтор, позднюю доставку, возвращение после исключения, две беседы, запись без роли и даты. Готовность — результат виден сразу после принятого события, при перезапуске запись не дублируется.

### 3. Получать состав и численность из одной выборки VK

Расширить `HumanMembership` в `src/contracts/adapter.ts` и реализацию `humanMembership` в `src/channels/vk/channel.ts`. Через существующий читатель состава и общий лимитер получать страницы, идентификаторы людей и роль при наличии достаточных данных. Обрабатывать дубликаты, разрывы между страницами, изменившееся общее количество, неожиданные элементы, отмену запроса и потерю доступа. Во всех неоднозначных случаях возвращать признак неполной попытки. Отфильтровать сообщества и не использовать выборку административных свидетельств с фильтром по ID как полный список.

Расширить `tests/vk-budget-membership.test.ts` на полный многостраничный список, достоверно пустой список, оборванный запрос и несогласованные страницы. Проверить, что переданное число людей совпадает с числом уникальных участников принятой выборки. Даже при полностью доступном составе неизвестная платформенная роль допустима. Готовность — потребитель F4.6 сохраняет действующее поведение, сырой ответ VK остаётся в адаптере.

### 4. Атомарно применять снимок к реестру и бюджету F4.6

В `src/core/chat-limits/token-budget-membership.ts` и `src/storage/token-budget-store.ts` объединить завершение наблюдения для двух потребителей. В одной транзакции сверять ожидаемое поколение, актуальность области, номер начатой сверки и версию принятых изменений состава. Полный результат обновляет присутствующих, отмечает отсутствие прежних участников и передаёт в F4.6 точное количество людей. Для отсутствующего сохранять установленную причину `left` или `removed`; новый статус `absent` применять при неизвестной причине. При возвращении, обнаруженном по списку, дату нового вступления оставить неизвестной. Для неполного результата обновить исход попытки, сохранив достоверные сведения о людях и прежнюю численность. Запоздалый результат не должен затирать даже метаданные более новой проверки.

В новом `tests/participant-registry-snapshot.test.ts` воспроизвести исключение Анны в 12:01 между стартом чтения в 12:00 и завершением в 12:02. Старая страница не возвращает Анну, назначается свежая сверка. Проверить также две сверки, завершившиеся в обратном порядке, смену поколения и откат транзакции при сбое. Сверить реестр и бюджет после повторного открытия БД. Действующие ручные пределы и накопленный расход остаются прежними.

### 5. Подключить часовую сверку и проверить штатный запуск

В `src/app/service.ts` объединить вызовы сверки F4.6 и F5.1. Планировать чтение после допуска или возобновления и после изменений состава. Для активных групп добавить часовой цикл с распределением запросов во времени. На одно поколение допускать одну выполняющуюся сверку и один запрос на повтор при изменениях за время чтения. Ошибка VK завершает попытку; новый сетевой запрос допустим при восстановлении доступа или в очередном цикле. При закрытии приложения отменять запросы, при паузе подключения применять штатные правила F3.7. Обработка сообщений и локальная запись события продолжаются без ожидания сетевой сверки.

В новом `tests/application-participant-registry.test.ts` пройти старт, возобновление, серию событий, часовой интервал, отказ VK и восстановление. На двух группах проверить изоляцию, отсутствие двойного обхода страниц для бюджета и своевременную обработку обычного сообщения при задержанном ответе VK. Полный перезапуск сам по себе не должен разрешить приём в чате, оставшемся в `uncertain`.

### 6. Провести ревью и синхронизировать документы

Запустить `npm run build`, `npm test -- --maxWorkers=4` и `npm run test:queue-load`. Провести `review` по задаче, планам и критериям на неполных данных. Устранить замечания и повторить ревью. После успешной проверки через `sync-specs` обновить участников, каналы, хранение и архитектуру, затем дорожную карту и журнал решений. Проставить статусы и даты завершения.

Конечные пути — `docs/tasks/completed/039-participant-registry.md`, `docs/plans/completed/039-participant-registry.md` и `docs/impl-plans/completed/039-participant-registry.md`. Обновить и проверить входящие и внутренние ссылки по [правилам хранения](../../project.md#хранение-активных-и-выполненных-задач). Готовность — сборка, тесты и ревью прошли, спецификации описывают проверенные переходы и условия сверки.

- Проверены полная многостраничная и пустая выборки, неизвестная роль, дубликаты, разрыв чтения, отказ и отмена. Роль в составе не выдаёт прав бота.

Проверены классификация новых таблиц и сохранение удаления из реестра при сообщении, событии и полном снимке. Численность F4.6 сохраняет всех подтверждённых людей.
