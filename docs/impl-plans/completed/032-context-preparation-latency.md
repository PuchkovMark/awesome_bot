## Упорядоченные шаги

На каждом шаге выполнить `npm run build`, проверки шага и `git diff --check`. Для нагрузочных сценариев использовать существующую команду `npm run test:queue-load`. Все измерения выполняются локально.

### 1. Снять исходные измерения

- Расширить [нагрузочный тест контекста](../../../tests/load/context-load.test.ts) с помощью существующих SQLite-фикстур. Сохранить проверку индекса на 50 000 строк. Для сравнения использовать подготовленные заранее истории из 5, 50 и 100 коротких реплик в личке и группе. В одном профиле бюджет вмещает весь набор, в другом останавливает выборку. Проверить число действительно включённых реплик.
- До изменения рабочего кода сохранить исходную ревизию, версию Node.js, параметры бюджета и результаты через существующий `recordQueueLoad`. Для прикладного времени задать фиксированный UTC-момент. Длительность измерять монотонными часами вокруг вызова штатного `prepare`, исключив создание и наполнение БД.
- Предлагаемый режим сравнения — три серии на вариант, в каждой пять прогревочных и 30 измеряемых вызовов. Записать медиану и p95 в миллисекундах для каждой серии. При последующих замерах использовать ту же машину, версию Node.js, фикстуры и порядок запуска. Готовность — исходные результаты воспроизводятся, все измеряемые обращения дают ожидаемый снимок.

### 2. Зафиксировать эквивалентность запроса

- Дополнить `tests/context-integration.test.ts`, `tests/context-format.test.ts` и `tests/context-budget.test.ts` компактными синтетическими примерами с ожидаемыми результатами исходной версии. Сверять точный системный текст, роли и строки сообщений, оценку входа, состояние цитаты и упорядоченные ID источников. Эталонные ожидания зафиксировать до оптимизации.
- Покрыть нулевую историю, кириллицу, кавычки и переводы строк, выдержку из длинной цитаты, её исключение из обычной истории и различие обрамления в личке и группе. Для последней подходящей реплики проверить точное попадание в бюджет и бюджет на единицу меньше.
- Выполнить также `tests/context-order.test.ts`, `tests/context-resources.test.ts` и `tests/history-retention-queue.test.ts`. Готовность — те же проверки проходят на исходной версии и пригодны для обеих последующих правок.

### 3. Устранить повторную работу в сборщике

- В [форматировании](../../../src/core/context/format.ts) и [сборщике](../../../src/core/context/builder.ts) использовать один форматтер времени на подготовку с выбранной зоной. После этой правки выполнить проверки шага 2 и повторить замер шага 1, чтобы увидеть эффект отдельно.
- Затем подготовить сериализованное представление каждой выбранной записи один раз. В [расчёте бюджета](../../../src/core/context/budget.ts) учитывать точную прибавку UTF-8 байтов: для группы — разделители элементов внутри общего JSON, для лички — обрамление отдельного сообщения. При подборе усечённой цитаты меняется только кандидат цитаты. Сохранить резерв окружения и заключительную проверку полной стоимости. Не переносить представления между заданиями.
- Сохранить чтение истории страницами, уступку управления, проверку отмены, дедлайна и доступности источников. Повторить тесты шага 2, `tests/context-boundary.test.ts`, `tests/context-builder.test.ts` и нагрузочный замер. Готовность — совпадают запросы, метаданные и исходы. На длинном полностью включённом окне сравнить медианы и p95 всех серий. Если выигрыш медианы укладывается в межсерийный разброс исходных медиан, повторить измерение и оставить результат открытым.

### 4. Измерить путь до первого подтверждения отправки

- Добавить новый нагрузочный сценарий `tests/load/context-response-latency.test.ts`, опираясь на `tests/context-queue.test.ts` и `tests/router-loop-publication.test.ts`. Использовать штатные роутер, очередь, подготовку контекста и публикацию. Метки времени снять на стенде в точках приёма, начала обработки, начала и конца подготовки, вызова и возврата модели, подтверждения первой части отправителем. Создание данных и запуск стенда вынести за границы измерения.
- Проверить один запрос, серию из одного чата и конкурентные запросы из разных чатов. Для сравнения исходной и итоговой версий запустить один и тот же сценарий с одинаковыми успешными ответами, задержками подмен и настройками квот; удостовериться, что сравниваются доставленные ответы. Отдельно учесть время между измеренными этапами, чтобы полный интервал сходился с разбиением.
- В результатах приёмки привести таблицу до и после по профилям, объёму фактически выбранной истории, медиане и p95. Указать миллисекунды выигрыша на сборке и разницу полного времени на стенде, включая случай, когда эта разница сопоставима с шумом. Готовность — сквозные и нагрузочные проверки проходят, каждый результат можно воспроизвести по записанным параметрам.

## Итог проверки

Изменения оформлены коммитами `99bb4fd` (замер подготовки), `ecf9599` (эталонные снимки), `0dc00a4` (форматтер времени), `d4ff65c` (подсчёт UTF-8) и `66fd5a9` (сквозной стенд).

- Проверки на исходном коде и после оптимизации подтвердили точный системный текст, JSON и роли, состояние цитаты, упорядоченные ID и границу бюджета. Дополнительно сравнили полные результаты подготовки в 72 сочетаниях размера бюджета, типа чата и варианта цитаты, включая пустой текст с вложением. Сохранены отмена, срок обработки и ограничения F4.4.
- `npm run build`, 969 тестов через `npm test -- --maxWorkers=1`, 10 нагрузочных тестов через `npm run test:queue-load` и `git diff --check` прошли. Нагрузочный набор сохраняет проверку индекса на 50 000 строк. Ревью относительно `95fd0ae` прошло без замечаний.
- Один форматтер времени для записей и точный учёт UTF-8 уменьшают работу на длинном окне. В личке с 100 репликами медианы исходных серий лежат в диапазоне 200–216 мс, после обеих правок — 2,17–2,22 мс. Для беседы диапазоны 169–181 мс и 2,27–2,39 мс. Выигрыш превышает межсерийный разброс.

### Подготовка контекста

Время наполнения базы исключено. В каждой из трёх серий 5 прогревочных и 30 измеряемых вызовов `prepare`. Проверены полные снимки и число реплик во всех вызовах. Все замеры сравнения выполнены на одной машине с Node.js 26.13.1. Для ограничения памяти на исходном коде сборка мусора запускалась между вызовами за пределами измеряемого интервала. ### Время до первого подтверждения

[Стенд](../../../tests/load/context-response-latency.test.ts) использует штатные роутер, очередь, подготовку, агентный цикл и публикацию. В каждом профиле проведены два прогрева и 12 измеряемых прогонов с новой подготовленной БД. В профиле одной беседы поступают три обращения подряд, в параллельном профиле — по одному в трёх беседах. Очередь допускает три ожидающих задания на беседу, квоты запросов и исходящих публикаций соответствуют штатным значениям. Заданы задержки подмен 25 мс для модели, 2 мс для проверки reply и 8 мс для отправки.

Очередь измерена от входа в роутер до выдачи задания. Публикация измерена от входа в её обработчик до вызова первой успешной квитанции порта. В колонке «Прочее» учтены промежутки между этапами. Сумма этих интервалов проверена для каждого ответа, для строк таблицы медиана и p95 посчитаны отдельно. Каждый включённый ответ подтверждён и записан в журнал.
