## Исходное состояние и общие условия

В F1.4 реализованы SQLite-хранилище, миграции 1–2, журнал, настройки и 218 тестов. Проверка внешних ключей в [соединении](../../../src/storage/connection.ts) ещё не включается явно. Новых сущностей и их типов нет. Новые файлы ниже обозначены явно; существующие файлы изменяются только в пределах утверждённого плана.

Реализация начинается после человеческого утверждения этого документа. Каждый шаг завершается `npm run build` и `npm test` и отдельным коммитом своих изменений; сборка включает линтинг и typecheck. Предшествующие удаления старого проекта и несвязанные рабочие изменения отделяются от фичи. Новые зависимости и изменение lock-файла не требуются.

Результат ограничен схемой и типами. Публичный объект `Storage` и его runtime-экспорты сохраняются: без репозиториев участников, профилей и фактов, выдачи модели и продуктовых CRUD-операций. Технические записи/чтение выполняют только внутренние тестовые помощники на синтетических данных, с явной областью чата и пользователя. Они не становятся кодом приложения или доказательством готовности будущей авторизации.

## Упорядоченные шаги

### 1. Типы модели и проверка внешних ключей соединения

- Цель: задать согласованные представления данных и гарантировать включённые внешние ключи до миграций на каждом соединении приложения.
- Модули и файлы: новые `src/storage/participant-types.ts`, `tests/typechecks/participant-model.ts`, `tests/storage-foreign-keys.test.ts`; изменения [экспорта хранения](../../../src/storage/index.ts), [соединения](../../../src/storage/connection.ts) и при необходимости [тестов соединения](../../../tests/storage-connection.test.ts).
- Работа: определить readonly-типы участника, профиля, факта и словарей утверждённого плана. Поля соответствуют схеме, nullable-сведения представлены явно; обязательные роль, статус, источник, надёжность и видимость не получают default или необязательность. Использовать общие `ChatId`, `UserId`, `Timestamp`; типы не назначают роль харнеса. Экспортировать только типы, без runtime-перечислений и новых методов Storage.
- Соединение: после явного открытия драйвера включить `foreign_keys` и проверить результат до callback и миграционной транзакции. Неуспех возвращает безопасную ошибку и закрывает созданное соединение. Не переносить PRAGMA внутрь транзакции, не менять ленивую загрузку и отсутствие действий при импорте.
- Тесты: на нескольких независимо открытых соединениях проверить `PRAGMA foreign_keys = 1`, в том числе внутри callback инициализации и после повторного открытия файловой БД. Контролируемая внутренняя подмена отказа включения подтверждает отсутствие готового соединения, закрытие и безопасную ошибку без нового публичного параметра тестирования. Реальные успешные соединения не подменяются.
- Типовые примеры: корректные известные и неизвестные сведения, nullable-даты и источник. Адресные `@ts-expect-error` проверяют обязательные поля, словари, типы id/времени, запрет произвольной роли и пропуска видимости/надёжности. Проверка типов не объявляется runtime-валидацией или проверкой достоверности. Примеры остаются вне `dist`.
- Условие готовности: `npm run build` и `npm test` проходят; FK включены до инициализации каждого соединения, ошибки безопасны, runtime-экспорты и действующий публичный API не расширены.

### 2. Миграция модели и проверки ограничений

- Цель: добавить три таблицы и проверить связи в области чата на реальной SQLite-схеме.
- Модули и файлы: новый `src/storage/migrations/003-participants-and-profiles.ts`, `tests/helpers/participant-fixture.ts`, `tests/storage-participant-model.test.ts`; изменения [набора миграций](../../../src/storage/migrations/index.ts) и [тестов миграций](../../../tests/storage-migrations.test.ts). Миграции 1–2 не меняются.
- Схема участия: STRICT-таблица `chat_participants` с первичным ключом `(chat_id,user_id)`, внешним ключом на существующий `chats`, nullable `joined_at`, `role_observed_at`, `status_observed_at`, `last_seen_at`, обязательными `role: member/admin/unknown` и `status: present/left/removed/unknown`. Без SQL-default роли/статуса и без автоматического заполнения из журнала.
- Схема профиля: STRICT-таблица `participant_profiles` с тем же ключом, составным FK на участие и явными `created_at/updated_at`. Профиль не требуется для существования участника; глобального id профиля нет.
- Схема факта: STRICT-таблица `profile_facts` с AUTOINCREMENT id, обязательным ключом участия и FK на профиль, `field_key`, текстовым `value`, `source_kind`, nullable `source_user_id/source_message_id/source_note`, обязательными `reliability/visibility` и `created_at/updated_at`. Индекс `(chat_id,user_id,id)`; уникальность по одному ключу поля не вводится.
- Ограничения: проверить составные id и совпадение платформ, обязательность компонентов связей, допустимые словари, неотрицательное безопасное целочисленное время и `updated_at >= created_at`, непустой ключ поля. Источник `self` при известном авторе требует совпадения с пользователем профиля; другие известные авторы должны относиться к той же платформе. Ссылки на автора источника и сообщение не становятся обязательными FK. Пустое текстовое значение факта допускается. Каскадные удаления/изменения ключей и триггеры назначения меток не вводятся.
- Технические помощники: параметризованные вставки и выборки синтетических данных с обязательными `chatId/userId`, через внутренние тестовые соединения с включёнными FK. Все соединения закрываются, временные файлы очищаются; SQL и драйвер не экспортируются приложению.
- Тесты связей: участник без чата, профиль без участия, факт без профиля, дубли участия/профиля, nullable-компоненты ключей, смешанные платформы, неверный автор `self`, недопустимые метки/время отклоняются. Для межчатового случая существует только родитель другой беседы: тест не должен проверять лишь отсутствие всех родителей. Проверить запрет удаления/смены ключа родителя с зависимостями и `foreign_key_check`.
- Тесты данных: все статусы, роли, источники, метки надёжности и видимости, отсутствие default, сохранение null/unknown, неизвестного автора/сообщения источника. Unicode, кавычки и текст, похожий на SQL или инструкции, сохраняются буквально. Несколько фактов по одному ключу не вытесняют друг друга. Одинаковый пользователь в разных чатах и одинаковые локальные id разных платформ имеют независимые участия, профили и выборки фактов.
- Регрессия миграций: заменить фиксированную «неизвестную» версию на версию выше текущей; ошибочный тестовый набор продолжает последовательность реального набора. Сохранить проверки отката после реального изменения схемы, неизвестной/изменённой истории, посторонней БД и отсутствующего FTS-модуля; не ослаблять их ради новой версии.
- Условие готовности: `npm run build` и `npm test` проходят; версия 3 создаётся штатным мигратором, связи и CHECK реально отклоняют ошибки, все метки сохраняются без автоматических правил, прежние миграции не переписаны.

Импорт с пустым окружением по-прежнему не загружает драйвер, не создаёт файлы и ничего не выводит.
- Условие готовности: `npm run build` и `npm test` проходят; обновление и повторное открытие сохраняют журнал, настройки, FTS и новую модель, выпуск включает миграцию, интерфейсы потребителей F1.4 не меняются.
