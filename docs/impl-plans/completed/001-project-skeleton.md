## Исходное состояние и общие условия

Исходников приложения, зависимостей и конфигураций сборки пока нет. Все перечисленные ниже файлы реализации — новые, пока не созданные. Работа ограничена F1.1: без конфигурации приложения, логгера, контрактов, БД, SDK VK/LLM и запуска бота.

При начале реализации проверить доступ к установленному Node.js 26 и npm: `PATH`, менеджер версий и настройки оболочки. Учитывать ограниченное представление домашнего каталога в песочнице: отсутствие видимого файла не доказывает его отсутствие на хосте. Не устанавливать другую версию автоматически. Зафиксировать фактические версии; при необходимости доступа вне песочницы использовать штатное разрешение. Если подключить существующую среду не удастся, сообщить конкретную причину; Docker допустим как запасной вариант с сохранением прав пользователя.

Каждый шаг завершается доступной на нём сборкой, линтингом и тестами; отдельный коммит включает только изменения этого шага. Существующие посторонние изменения не включаются. Временные тестовые проекты и результаты сборки не попадают в Git. При изменении промптов и моделей evals потребовались бы отдельно; в этой фиче они не меняются.

## Упорядоченные шаги

### 1. Воспроизводимый TypeScript/ESM-скелет

- Цель: получить собираемый проект на установленном Node.js 26 с рабочим Vitest и базовым ESLint.
- Модули и файлы: новые `package.json`, `package-lock.json`, `.nvmrc`, `.gitignore`, `tsconfig.json`, `tsconfig.build.json`, `eslint.config.mjs`, `vitest.config.ts`, `README.md`; новые пустые ESM-модули `src/core/index.ts`, `src/channels/index.ts`, `src/tools/index.ts`, `src/storage/index.ts`, `src/llm/index.ts`; новый `tests/esm.test.ts`.
- Работа: подобрать совместимые стабильные версии TypeScript, ESLint, typescript-eslint, Vitest и `@types/node`, проверить требования к Node.js, закрепить проверенный набор и lock-файл. Объявить ESM, строгий TypeScript и NodeNext; выпускать только исходники приложения из `src` в `dist`. Проверка типов отдельно охватывает тесты и настройки инструментов. Конфигурацию `.mjs` проверять TypeScript через `allowJs`/`checkJs` и ESLint. Подготовить команды `lint`, `typecheck`, `build`, `test`; `build` последовательно запускает линтинг, проверку типов и выпуск JavaScript, без запуска тестов. На этом шаге ESLint ещё не проверяет платформенные границы.
- Тесты: `tests/esm.test.ts` проверяет загрузку выпущенных модулей всех пяти слоёв самим Node.js в ESM-режиме без запуска приложения. Проверка вызывается после сборки; тест сообщает об отсутствующих артефактах, а не пропускается. Выполнить чистую установку через `npm ci`, затем `npm run build` и `npm test`; отдельно убедиться, что `dist` не содержит тестов и конфигураций.
- Условие готовности: чистая установка воспроизводима, сборка и тесты проходят, пустые модули загружаются в Node.js. README уже содержит фактические версии, команды и назначение слоёв. Папки зависимостей и результатов сборки исключены из Git; прикладной точки входа нет.

### 2. Правило платформенных границ и его тесты

- Цель: блокировать прямые платформенные импорты в `core` и `tools`, сохранив разрешённые импорты адаптеров.
- Модули и файлы: новый `scripts/eslint/platform-imports.mjs`, новый `tests/platform-imports.test.ts`; изменения `eslint.config.mjs`, `tsconfig.json` и README.
- Работа: реализовать локальное AST-правило и подключить его с уровнем ошибки к вложенным TypeScript-файлам `src/core` и `src/tools`. Список запрещённых пакетов хранить в одном месте конфигурации, первоначально `vk-io`; имена подмодулей учитывать с границей `/`. Проверять статические импорты и реэкспорты, в том числе только типов, TypeScript import-type и import-equals, динамический `import` и `require`. В защищённых слоях отклонять вычисляемые имена динамической загрузки. Служебные `.mjs`-файлы включить в проверку JavaScript-типов и линтинг. Не добавлять запреты между остальными слоями и анализ транзитивных зависимостей.
- Тесты: через API ESLint и настоящую flat config проверить оба защищённых слоя и вложенные пути. Матрица содержит корень `vk-io`, подмодуль, `import type`, типовой и обычный реэкспорт, TypeScript import-type/import-equals, динамический импорт, `require`, вычисляемую загрузку. Разрешённые случаи: нейтральные локальные/Node.js импорты, пакет с похожим, но другим именем, платформенный импорт в `channels`. Добавление вымышленного платформенного пакета через параметры правила подтверждается отдельным тестом без установки SDK и добавления второго адаптера. Недопустимые исходники передаются строками и не участвуют в компиляции приложения.
- Условие готовности: `npm run build` и `npm test` проходят; тесты подтверждают наличие диагностики именно правила границ, а не ошибки парсера. Разрешённые примеры не дают этой диагностики. Никакие платформенные SDK для проверок не установлены.

### 3. Проверка сборки при нарушении границ

- Цель: подтвердить, что реальная сборочная команда прекращается из-за запрещённого импорта, а корректный проект собирается.
- Модули и файлы: новый `tests/build-boundaries.test.ts`, при необходимости новый `tests/helpers/skeleton-fixture.ts`; изменения README и `vitest.config.ts`, если нужен отдельный таймаут интеграционной проверки.
- Работа: создать временную копию минимального скелета и конфигураций с доступом к уже установленным зависимостям; не выполнять сетевую установку в тестах. Запускать дочерние процессы с текущим исполняемым Node.js и npm. Команда `build` не вызывает тесты, чтобы исключить рекурсивный запуск Vitest. Очистка удаляет только созданные тестом временные каталоги.
- Тесты: корректная временная копия успешно выполняет `npm run build`; добавленный платформенный импорт в `core` либо `tools` приводит к ненулевому коду и диагностике правила границ. Проверить также импорт только типов. Убедиться, что отрицательный исход не объясняется недоступным SDK: линтер должен завершить сборку раньше TypeScript. Дополнить ESM-проверку подтверждением, что загрузка скомпилированных модулей выполняется без VK, LLM, секретов и побочных действий приложения.
- Условие готовности: сборка основного скелета и все тесты проходят; отрицательные сценарии ожидаемо блокируются линтером, исходное дерево не изменяется. После установки зависимостей тесты не обращаются к сети.
