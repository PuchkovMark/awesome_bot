## Упорядоченные шаги

### 1. Передать исходный диалог, номер и время события

- **Цель** — собрать технические поля события на доверенном входе и довести их до существующей операции учёта повторов.
- **Модули и файлы** — в `src/app/chat-control.ts` брать источник, номер и время из исходного события. Для команды в беседе источником служит `IncomingMessage.chatId`. Для личной команды владельца преобразовать подтверждённый `peerId` в `ChatId` на входе приложения, а целевую область выбрать по аргументу и поколению. Личный вход поддерживает владельца без активного подключения его лички в SQLite.
- В `src/core/authorization/service.ts`, `src/storage/authorization-types.ts`, `src/storage/authorization-store.ts` и `src/storage/chat-control-store.ts` передавать единый внутренний набор полей исходного события. Проверять принадлежность источника входному диалогу, положительный безопасный номер и валидное UTC-время. Проверки прав, актуальности целевого поколения, учёт повтора и изменение состояния остаются в одной транзакции. Групповой роутер продолжает журналировать вход; отдельная отметка используется там, где она применяется сейчас. Номер личного сообщения не участвует в отборе вступлений целевой беседы.
- Передать эти поля у всех потребителей той же операции. В `src/app/persona-commands.ts`, `src/app/chat-passport.ts` и `src/app/questionnaire-editor.ts` взять время из исходной реплики. Уточнить внутренние типы в `src/storage/scoped-types.ts`, `src/storage/chat-passport-types.ts` и `src/storage/questionnaire-types.ts`. В `src/storage/scoped-storage.ts`, `src/storage/questionnaire-progress-store.ts` и `src/storage/questionnaire-management-store.ts` использовать диалог соответствующей области и уже доступное время события.
- **Тесты** — обновить вызовы изменённых контрактов и проверить допустимый и несовпадающий источник в `tests/chat-control-service.test.ts`. Сохранить сценарии правки паспорта и анкеты, выбора персонажа, старого повтора, обработки команды из лички и порядка приветствий. До изменения схемы SQLite используется действующий ключ.

  ```sh
  npm run build
  npm test -- tests/chat-control-service.test.ts tests/storage-chat-control.test.ts tests/questionnaire-progress.test.ts tests/application-chat-control.test.ts tests/application-persona-commands.test.ts tests/application-chat-passport.test.ts tests/application-questionnaire-template.test.ts tests/application-questionnaire-management.test.ts
  ```

- **Условие готовности** — сборка и целевые тесты проходят. Все места учёта получают исходный диалог, номер и время. Правила ролей, журналирования и адресации ответов соблюдаются.

### 2. Различить отметки в SQLite и проверить обновление базы

- **Цель** — разделить события разных диалогов и сохранить защиту от повторов для известных старых номеров.
- **Модули и файлы** — добавить новую миграцию `src/storage/migrations/057-control-command-origin.ts` и зарегистрировать её в `src/storage/migrations/index.ts`. Действующая цепочка заканчивается версией 56. Новая миграция перестраивает `chat_control_commands` с двумя формами отметок. У новой строки заполнен `source_chat_id`. У перенесённой строки источник неизвестен, а `legacy_before` хранит начало следующей секунды после миграции в UTC-миллисекундах. Ограничения SQLite различают эти формы. Для новых строк уникальна комбинация цели, поколения, инициатора, исходного диалога и локального номера. Для прежних строк уникален их существующий набор полей. Связь с поколением цели сохраняет каскадное удаление. Сохранение ID источника допускается без записи о его подключении.
- В `src/storage/chat-control-store.ts` проверять точное совпадение новой отметки и совпадение со старой при времени события до сохранённой границы. На точной верхней границе применяется учёт по источнику. Проверка и запись происходят внутри транзакции изменения настроек. Ошибка записи откатывает отметку вместе с изменением. Техническая запись содержит идентификаторы, а для старой формы также границу перехода.
- Проверить, что `src/storage/database-restore.ts` переносит актуальные строки целевого поколения из доверенной БД вместе с границей. Оба файла SQLite уже приводятся к известной схеме перед сверкой в `src/app/database-backup.ts`. Хранение границы в строке позволяет перенести её вместе с остальными полями. Проверить очистку отметок автора в `src/storage/personal-deletion.ts` и очистку целевого поколения.
- **Тесты миграции и записи** — добавить сценарий на базе версии 56 с прежними отметками в двух беседах. Проверить сохранение настроек, отказ для дубля до границы и в секунду миграции, независимые источники начиная со следующей секунды, повтор с теми же новыми полями и сохранность границы при повторном открытии. В тесте использовать границу, фактически записанную SQLite. Проверить откат при ошибке изменения после захвата отметки. Дополнить ожидания списка миграций в `tests/storage-dist.test.ts` и `tests/storage-participant-upgrade.test.ts`.
- **Тесты восстановления и очистки** — в `tests/storage-database-restore.test.ts` восстановить снимок со старой схемой при актуальной рабочей БД с перенесённой и новой отметками. Проверить, что граница взята из рабочей БД, повтор сохраняет новое состояние, а отдельное событие из другого диалога допускается. Проверить удаление обеих форм отметок при применимой очистке без затрагивания соседней беседы.

  ```sh
  npm run build
  npm test -- tests/storage-migrations.test.ts tests/storage-dist.test.ts tests/storage-participant-upgrade.test.ts tests/storage-chat-control.test.ts tests/chat-control-service.test.ts tests/storage-database-restore.test.ts tests/application-database-backup.test.ts tests/lifecycle-cleanup-coverage.test.ts tests/storage-personal-data.test.ts
  ```

- **Условие готовности** — сборка и целевые тесты проходят. Чистая и обновлённая базы принимают раздельные события. Старые и новые повторы защищены после перезапуска и восстановления. Проверки целостности, очистки и изоляции двух бесед проходят.

### 3. Проверить коллизию и повторы через вход VK

- **Цель** — покрыть три критерия задачи через штатное приложение и SQLite.
- **Модули и файлы** — расширить `tests/application-chat-control.test.ts`. Его подмена VK уже хранит сообщения по паре `peer_id` и локального номера. Для повтора передать адаптеру сохранённое событие с исходным временем. Проверять отправку по фактическому адресату и подтверждённой записи подмены VK.
- **Тесты** — владелец включает приветствия в A и B двумя событиями с одинаковым локальным номером. Затем он выключает A из проверенной лички событием с тем же номером. Проверить подтверждение в личке, выключенную A и включённую B с приветствиями. Новыми командами включить A и выключить приветствия в B. Повторить три исходных события и сверить настройки и число отметок. В отдельном случае отклонить личное подтверждение после изменения, включить A новой командой и повторить исходное выключение. На служебных входах модель не вызывается.
- В отдельном прогоне выполнить команду из лички владельца с разрешённой отправкой VK до создания записи этого подключения в SQLite. Проверить итог и подтверждение владельцу. Вход от чужого отправителя и команда с устаревшим целевым поколением оставляют текущие настройки прежними.

  ```sh
  npm run build
  npm test -- tests/application-chat-control.test.ts tests/application-command-help.test.ts tests/application-new-member-greeting.test.ts tests/application-questionnaire-invitations.test.ts
  ```

- **Условие готовности** — сборка и целевые тесты проходят. В каждом из трёх исходных диалогов одинаковый номер относится к отдельному событию. Повторы и отказ отправки подтверждения сохраняют состояние последующих команд.
