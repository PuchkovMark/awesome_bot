## Упорядоченные шаги

Каждый шаг завершается рабочей сборкой `npm run build`, целевыми тестами и `git diff --check`. Переход импортов, автоматическое форматирование и ручное улучшение читаемости оформляются отдельно.

### 1. Зафиксировать правила и проверить формат на небольшом модуле

Создать `docs/code-style.md`, связать его с корневым AGENTS.md. Показать на примерах различие локального и платформенного ID, единицы времени, проверку отмены после чтения и назначение комментариев. Закрепить Prettier в devDependencies и lock-файле. Предложение для пилота — два пробела, одинарные кавычки и ширина 100. Ввести команды `format` и `format:check` с одинаковым охватом. Из прохода исключить выпущенные нумерованные миграции, сгенерированные файлы, зависимости, lock-файл и документацию.

Применить пилот к `src/config` и `tests/config.test.ts`. В отдельной временной копии проверить ненулевой код проверки на отклонении, сохранность файла после проверки и идемпотентность исправления. Условие готовности — пилот проходит целевой тест, а общая сборка продолжает работать во время поэтапного перехода.

### 2. Проверить и распространить относительные импорты без расширения

В `tsconfig.json`, `tsconfig.build.json` и `package.json` подготовить разрешение путей в исходниках и выпуск ESM. Кандидат для проверки — режимы ESNext и Bundler с последующей обработкой путей выпуска через закреплённый инструмент. На небольшом модуле проверить импорт типа, значения, реэкспорт и существующие формы динамического импорта. Из чистого каталога выпуска загрузить собранный модуль обычным Node.js и вызвать экспортированную функцию. Убедиться, что переход к определению в редакторе открывает исходник.

Затем перевести относительные ссылки на локальные TS-модули по проекту. Отдельно проверить пути к реальным JS-файлам в dist-тестах, строки тестовых фикстур и импорты MJS, которые выполняет Node напрямую. Сверить резолверы `scripts/eslint/` и трёх проверок границ в `scripts/`. Проверить разрешённый и запрещённый импорт в новой форме. Выполнить `tests/esm.test.ts`, `tests/platform-imports.test.ts`, `tests/build-boundaries.test.ts` и полный набор тестов. Приёмка — старые точки входа загружаются, а запрет слоя выдаёт прежнюю предметную диагностику.

### 3. Применить формат по каталогам

Обработать контракты и конфигурацию, ядро и инструменты, хранилище, адаптеры, LLM, приложение, логгер и evals. Включить соответствующие тесты, затем оставшиеся фикстуры, нагрузочные тесты, `scripts`, `eslint.config.mjs` и обе конфигурации Vitest. Проверить полноту охвата по фактическому дереву. До первого прохода по сборщику зафиксировать исходные замеры 032 либо сохранить их на исходной ревизии по её плану.

Для каждой группы просмотреть diff, повторно запустить форматтер и тесты затронутых модулей. Для хранилища проверить миграции и контрольные суммы. Для скриптов повторить проверки границ. Условие готовности — каждый включённый каталог проходит проверку формата и повторный проход даёт пустую разницу.

### 4. Улучшить читаемость сборщика на зафиксированной базе

В `src/core/context/builder.ts` уточнить локальные имена и сделать видимыми чтение источника, проверку актуальности, выбор цитаты и проверку бюджета. Обновить пример до и после в руководстве. В этой правке сохранить алгоритм и содержимое входа модели. Скоординировать базовую ревизию с 032 при пересечении изменений.

Проверить `tests/context-builder.test.ts`, `tests/context-budget.test.ts`, `tests/context-integration.test.ts`, `tests/context-resources.test.ts` и `tests/history-retention-queue.test.ts`. Приёмка — совпадают порядок, границы бюджета и обработка недоступных источников, отмены и истечения срока.

### 5. Включить обязательную проверку и провести приёмку

Включить `format:check` в `npm run build`. Из чистой временной копии проверить установку по lock-файлу, полный охват форматирования и повторный запуск `npm run format` с пустым diff. Внести временное отклонение и убедиться, что сборка указывает проблемный файл. Затем на чистом состоянии выполнить сборку, `npm test -- --maxWorkers=1`, `npm run test:queue-load` и проверку загрузки dist без сетевых вызовов. Проверить неизменность выпущенных миграций относительно исходной ревизии.

### 6. Ревью и актуализация спецификаций

Провести `review`, устранить замечания и повторить затронутые проверки. После успешного ревью выполнить `sync-specs`: сверить описание сборки в README, `docs/specs/architecture.md`, правила разработки и границы `docs/specs/context.md`. Отразить фактический результат в журнале решений, проверить статусы и даты завершения. Конечные пути — `docs/tasks/completed/031-typescript-code-style.md`, `docs/plans/completed/031-typescript-code-style.md` и `docs/impl-plans/completed/031-typescript-code-style.md`. Обновить и проверить внутренние и входящие ссылки по [правилам хранения](../../project.md#хранение-активных-и-выполненных-задач).
