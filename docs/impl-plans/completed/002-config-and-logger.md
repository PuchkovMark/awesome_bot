## Исходное состояние и общие условия

После F1.1 доступны сборка NodeNext/ESM, ESLint, Vitest и пять пустых слоёв. Конфигурации приложения и логгера нет. Новые пути ниже обозначают предлагаемые файлы, а не существующие компоненты. Текущие зависимости и конфигурации TypeScript сохраняются, кроме необходимых для F1.2 изменений.

Провайдер — OPENCODE, модель в примере — `deepseek-v4.1-flash`. В F1.2 нет реального клиента, SDK, endpoint, проверки ключей по сети, запуска VK или бота. Модель не вызывается; оценочный прогон поведения этой фиче не требуется.

Каждый шаг оставляет проект собираемым с проходящими тестами и оформляется отдельным коммитом только своих изменений. После изменения исходников выполнять `npm run build`, затем `npm test`; сборка уже включает линтинг и проверку типов. Окружение тестов задаётся явно, реальные `.env` и секреты не читаются. Предшествующие изменения, особенно удаления старого бота, не включаются в коммиты F1.2.

## Упорядоченные шаги

### 1. Загрузка и проверка конфигурации

- Цель: получить проверенный неизменяемый конфиг без глобальных побочных эффектов и без утечек при ошибках.
- Модули и файлы: новые `src/config/index.ts`, `src/config/types.ts`, `src/config/errors.ts`, `src/config/secrets.ts`, `tests/config.test.ts`; изменения [ESM-теста](../../../tests/esm.test.ts) и [README](../../../README.md).
- Работа: реализовать явный загрузчик с передаваемыми окружением, рабочим каталогом и необязательным путём `.env`. Использовать `util.parseEnv`; приоритет — окружение, файл, разрешённые значения по умолчанию. Проверять `VK_TOKEN`, `OPENCODE_API_KEY`, `LLM_MODEL`, `LOG_LEVEL` строго по таблице плана. Провайдер фиксируется как `opencode`; `LLM_MODEL` остаётся обязательным, не подставляется автоматически. Конфиг имеет только известные поля и замораживается вместе с вложенными частями. Ошибка содержит фиксированный код и только известные имена параметров, без исходных значений, пути с пользовательским содержимым, исходного `cause` и полного окружения.
- Работа с секретами: во время загрузки собрать секретные значения обоих источников, включая перекрытые. Держать их отдельно от сериализуемого конфига в закрытом контексте; наружу для будущего логгера предоставить функцию очистки строк без возможности перечислить исходные секреты. Сам конфиг передаётся только компонентам, которым нужны его параметры, и не используется как метаданные логирования. Не возвращать частичный конфиг при ошибке.
- Тесты: корректный конфиг из окружения и временного файла; приоритет и перекрытие пустым значением; каждый отсутствующий/пустой обязательный параметр; пробелы и переводы строк; все допустимые и недопустимые уровни, `info` только при отсутствии `LOG_LEVEL`. Проверить игнорирование посторонних переменных, отсутствие подмены ключа OPENCODE параметром Anthropic, необязательный отсутствующий `.env`, отсутствующий явно заданный файл и ошибку чтения. Ошибку доступа подменять детерминированно, чтобы тест не зависел от UID. Проверить неизменность исходного словаря, безопасный текст/поля ошибки и наличие очистки перекрытых секретов.
- Регрессия: расширить ESM-тест новым модулем конфигурации и ожидаемым каталогом `dist/config`; сохранить проверку, что тесты и конфигурации инструментов не выпускаются. Дополнить README реализованными правилами загрузки.
- Условие готовности: сборка и все тесты проходят. Загрузчик возвращает корректный конфиг либо безопасную ошибку; импорт модуля ничего не загружает и не выводит. Pino и SDK пока не нужны.

### 2. Ограниченный интерфейс безопасного логгера

- Цель: записывать предусмотренные события и отладочные подробности без свободной сериализации входных данных.
- Модули и файлы: новые `src/logger/index.ts`, `src/logger/types.ts`, `src/logger/sanitize.ts`, `tests/logger.test.ts`; изменения [манифеста](../../../package.json), lock-файла, [ESM-теста](../../../tests/esm.test.ts) и README.
- Работа: выбрать стабильный Pino, совместимый с закреплённым Node.js 26, проверить его актуальные требования и установить точную production-зависимость. Экземпляр Pino и свободные методы форматирования наружу не выдавать. Создание логгера явно принимает уровень, функцию очистки/дополнительные зарегистрированные секреты и необязательный тестовый поток вывода. По умолчанию JSON-строки идут в stdout, время — UTC unix ms. Не добавлять транспорты, файловое хранение и процессные обработчики.
- Контракт: обычные события имеют фиксированные коды `config_loaded`, `config_invalid`, `component_error` и проверяемые поля с перечислимыми значениями. `config_loaded` записывается на `info`, ошибки — на `error`; интерфейс позволяет создавать предусмотренные события на уровнях, согласованных с планом, без произвольного строкового сообщения. Отладочный метод создаёт только запись `debug`. Минимальный вызов для ошибки конфигурации принимает безопасный код и известные имена параметров и работает до получения полного конфига; сырые ошибки загрузки в него не передаются.
- Очистка: перед Pino строить новый объект только из разрешённых полей с проверками во время выполнения. Неизвестные поля отбрасывать, обычную ошибку превращать в безопасную категорию; не сериализовать `message`, `stack`, `cause` и произвольный `name` на обычных уровнях. Отладочный метод допускает только очищенный текст и контролируемые текстовые подробности ошибок, без пользовательских сериализаторов. Из допускаемых строк убирать известные секреты до вывода; обработка повторных и пересекающихся вхождений не должна оставлять части полного известного секрета. Неизвестные/кодированные секреты не объявлять автоматически распознаваемыми.
- Тесты: разбирать фактически записанный JSON из тестового потока. Проверить пороги `debug/info/warn/error/fatal`, `silent`, время и структуру. Секреты в отладочном тексте и подробностях ошибок очищаются; пользовательский текст внутри обычной ошибки отсутствует даже при пороге `debug`, пока явно не использован отладочный метод. Проверить вложенные неизвестные поля, произвольные `name/cause`, объекты с `toJSON`, некорректные коды событий и значения после обхода TypeScript через приведение типов. Редактор не меняет исходные объекты и не вызывает пользовательские сериализаторы. Проверить повторные и перекрытые секреты из обоих источников, а также дополнительно зарегистрированный секрет.
- Регрессия: ESM-тест включает `dist/logger`, проверяет отсутствие вывода и необходимости ключей при импорте. Существующие тесты границ и сборки продолжают использовать полный набор текущих исходников и зависимостей.
- Условие готовности: сборка и все тесты проходят; Pino закреплён в манифесте и lock-файле. Ни один предусмотренный путь логирования не выводит тестовые секреты, обычные события не раскрывают тексты сообщений.

### 3. Совместная проверка конфигурации и логов

- Цель: проверить безопасное поведение компонентов вместе до создания будущей точки входа.
- Модули и файлы: новый `tests/config-logger.test.ts`, при необходимости новый `tests/helpers/log-output.ts`; изменения [ESM-теста](../../../tests/esm.test.ts) для проверки импорта в отдельном процессе. Корректировки компонентов допускаются только по выявленным проблемам F1.2.
- Работа: тестовая композиция сначала загружает конфиг и только после успеха создаёт зависимый компонент через подменённую фабрику. Это проверка порядка использования, а не новая прикладная точка входа. Передать закрытый контекст очистки логгеру, а конфиг — только подменённому потребителю. При неуспехе записать безопасную диагностику без полной конфигурации логгера.
- Тесты: при неполном конфиге фабрика потребителя не вызывается; безопасная ошибка содержит нужное имя параметра без значения. При успехе событие загрузки не содержит конфиг или ключи; тестовый потребитель получает OPENCODE и `deepseek-v4.1-flash`. Проверить секреты окружения и файла с разными значениями одного параметра: оба удаляются из допускаемого отладочного текста. Проверить ошибку чтения и ошибку валидации до создания основного логгера. Отдельный процесс импортирует модули с пустым окружением и временным рабочим каталогом без `.env`: stdout/stderr пусты, чтение конфигурации и выход процесса не происходят. Реальные SDK и сервисы не используются.
- Условие готовности: сборка и все тесты проходят, тестовая композиция подтверждает отказ до создания зависимостей и безопасную диагностику во всех проверенных ветвях. Глобальное окружение и реальные файлы пользователя не изменены.

## Результат выполнения

Шаги 1–5 выполнены 2026-11-21 на Node.js 26.13.1 и npm 11.20.0. Установлен Pino 10.4.0 как точная production-зависимость; dotenv, библиотеки схем и SDK не добавлялись. Основные компоненты — явный загрузчик, неизменяемый конфиг, закрытый контекст очистки, ограниченный логгер и отдельная безопасная диагностика до конфигурации.

Проверки рабочего дерева и чистой временной копии: `npm ci`, `npm run lint`, `npm run typecheck`, `npm run build`, `npm test` — успешно. После чистой установки lock-файл не изменился. Пройдено 107 тестов в шести файлах: сохранённые сценарии F1.1 и новые проверки конфигурации, логов, совместного отказа/успеха и примера окружения. Импорт скомпилированных модулей проверен отдельным Node.js-процессом с пустым окружением: чтения `.env`, изменений окружения и незапрошенного вывода нет; процесс достигает контрольной отметки после импорта.

Ревью выполнено по скиллу `review` в текущем обсуждении на базе `1e1c99d`, с учётом предшествующего состояния рабочего дерева и уточнения провайдера пользователем. Проверены коммиты `f420c99`, `5be6d47`, `0156961`, `b1de403`; все критерии задачи подтверждены, неустранённых замечаний нет. Изоляция данных чатов и журналирование входящих сообщений пока неприменимы: этих компонентов нет в F1.2. Предшествующие удаления старых исходников не включены в коммиты реализации; новые компоненты не используют их архитектуру.

Ограничения сохранены явно: очищаются известные зарегистрированные секреты; неизвестные и преобразованные ключи автоматически не распознаются. Подробности ошибок доступны только на `debug`; обычные события содержат безопасную классификацию. Прикладная точка входа, SDK, endpoint и реальные вызовы остаются вне F1.2.

После успешного ревью выполнен `sync-specs`: архитектура и правила логов описывают согласованный результат, F1.2 закрыт, задача и оба плана перенесены в соответствующие каталоги `completed/`, внутренние и входящие ссылки обновлены.
