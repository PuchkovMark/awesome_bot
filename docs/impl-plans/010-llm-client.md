## Границы и технические допущения

Документ утверждён человеком; реализация выполняется по шагам. Клиент не подключается к боту, хранилищу, версиям или реальному API. Новых зависимостей и миграций нет. Все HTTP-взаимодействия в тестах подменяются; настоящие ключи и файлы .env не используются. F2.9 остаётся отдельной фичей и обязательна до завершения F2.2, даже если F2.1 уже пройдёт проверки без сети.

Предлагаются следующие локальные параметры: timeoutMs по умолчанию 60000 мс, maxResponseBytes по умолчанию 1048576 байт. Оба можно явно переопределить положительными безопасными целыми при создании клиента. maxOutputTokens — обязательное положительное безопасное целое на каждый запрос без скрытого значения по умолчанию; допустимость величины для модели проверяется в F2.9. Эти числа — предложение плана реализации, а не новые лимиты беседы, тарифа или качества модели. Действующая конфигурация F1.2 передаёт provider/apiKey/model; новые переменные окружения сейчас не нужны.

Непрозрачная сессия предлагается как HMAC-SHA-256 с отдельной меткой назначения над однозначным кодированием chatId и generation. Секрет установки явно внедряется в отдельную фабрику вычисления, не берётся из API-ключа и не создаётся случайно при каждом запуске. Для настоящего запуска F3.4 должен подключить постоянный секрет из инфраструктурной конфигурации с редактированием в диагностике; здесь используются только синтетические секреты. Нет таблицы соответствий или сохранения хешей удалённых бесед. При одинаковых секрете и области результат одинаков после пересоздания фабрики, при новом поколении — другой; смена секрета меняет все сессии. Вычисление не подтверждает актуальность области: её проверяет будущий харнес.

Для каждого шага обязательны npm run build и npm test; build уже включает lint, проверку границы каталога и typecheck. После успешных проверок — отдельный коммит только файлов шага. Существующие посторонние изменения не включаются. Результаты и отклонения фиксируются в этом плане; изменение согласованного поведения возвращается человеку.

## Упорядоченные шаги

### 1. Нейтральные формы запроса и результата

- Цель: задать транспортный контракт без SDK, VK, исполнения инструментов и чтения данных.
- Модули и файлы: новые src/llm/types.ts и src/llm/errors.ts; существующий [src/llm/index.ts](../../src/llm/index.ts). JSON-типы берутся из [контракта JSON](../../src/contracts/json.ts), без изменения контракта исполняемого инструмента.
- Формы: LlmRequest содержит system, messages, tools, maxOutputTokens и отдельные sessionId/signal. LlmToolDescription содержит name, description, parameters. Сообщения — user с текстом, assistant с текстом и/или toolCalls, tool с callId и текстовым результатом. LlmToolCall содержит id, name, arguments: string. Описания и результаты — данные; нет execute, ToolContext, ролей или произвольных HTTP-параметров.
- Результат: различимые варианты complete, incomplete, refused, empty, tool_calls и безопасная ошибка. В tool_calls есть непустой список вызовов и возможный сопутствующий текст, который не является финальным ответом. Usage содержит независимые nullable-счётчики input/output; отсутствие не равно нулю. Ошибки имеют фиксированные коды и безопасные сообщения без raw/cause/исходных ошибок. Внешняя граница Promise не выбрасывает ошибку провайдера наружу.
- Тесты: новые tests/llm-contracts.typecheck.ts и tests/llm-contracts.test.ts; проверка вариантов, непрозрачной строки аргументов и отсутствия SDK/платформенных полей. Отдельно проверить, что описание инструмента не требует функции исполнения.
- Условие готовности: типы экспортируются без побочных эффектов; build и тесты проходят, действующие модули продолжают работать. Не публиковать фиктивную фабрику клиента, обещающую ещё не реализованный вызов.

### 2. Вычисление идентификатора сессии без хранения

- Цель: реализовать принятую границу идентификатора отдельно от содержимого модели и HTTP.
- Модули и файлы: новый src/llm/session.ts, [src/llm/index.ts](../../src/llm/index.ts); используется стандартный node:crypto и доверенная форма ConnectionScope из [контракта жизненного цикла](../../src/contracts/lifecycle.ts).
- Действия: явная фабрика с копией секрета и валидацией входа; HMAC над JSON-массивом из метки назначения, chatId и generation, результат в hex. Не использовать простое склеивание полей, несекретный хеш или API-ключ. Нет кэша, БД, фоновых задач и генерации секретов при импорте. В HTTP-клиент по-прежнему приходит готовый sessionId; он не получает ConnectionScope.
- Тесты: новый tests/llm-session.test.ts: стабильность после пересоздания, различие бесед/поколений/секретов, отсутствие коллизий неоднозначного склеивания на выбранных примерах; ошибка пустого секрета/неверной области безопасна. Проверить отсутствие сырого идентификатора в результате и отсутствие файловых/сетевых операций; тесты не объявлять доказательством криптографической стойкости. Синтетический секрет не попадает в диагностику.
- Условие готовности: функция воспроизводима и не создаёт сохранённых соответствий; build и все тесты проходят. Подключение постоянного секрета в живое приложение остаётся явно указанной обязанностью F3.4.

### 3. HTTP-клиент и нормализация ответов

- Цель: получить рабочий одиночный вызов через подменяемый fetch, включая формы инструментов.
- Модули и файлы: новые src/llm/client.ts, src/llm/opencode.ts и src/llm/validation.ts; [src/llm/index.ts](../../src/llm/index.ts). Новые tests/helpers/llm-http.ts, tests/llm-client.test.ts, tests/llm-tools.test.ts и tests/llm-response.test.ts. Существующая конфигурация не меняется.
- Запрос: явная фабрика получает конфигурацию llm и опции транспорта/параметров; импорт и создание не делают запросов. До первого await проверить ввод и скопировать конфигурацию, сообщения, вложенные схемы и списки вызовов. Отклонить непредставимые JSON-схемы и неверные формы фиксированными ошибками. Системный текст передавать отдельно от сообщений людей. Использовать только фиксированный Go endpoint, POST, Bearer, Content-Type, собственный User-Agent и x-opencode-session; redirect: error. Нет произвольных заголовков, fallback и автоматических повторов.
- Инструменты: сериализовать tools как описания функций, assistant.tool_calls и сообщения role=tool с tool_call_id. Результаты передавать буквально как строки. Аргументы вызовов не JSON.parse и не проверять по схеме; JSON.parse конверта HTTP-ответа допустим. Никакого реестра и вызова execute. Подмена проверяет точное тело и отсутствие служебных полей прав/адаптера, а не только ответ клиента.
- Ответ: принимать один choice; проверять структуру, finish_reason, текст и usage. stop с непустым текстом — complete; length — incomplete; фильтрация/явный отказ — refused; пустое содержимое — empty. tool_calls с непустым списком — отдельный результат: непустые уникальные id, непустые имена, строковые arguments; неизвестное имя сохраняется для проверки будущим харнесом. При одновременно приложенном тексте не выдавать complete. Некорректные формы или несовместимые сочетания завершения/вызовов — безопасная ошибка, а не угадывание намерения. length вместе с вызовами считается неподдерживаемым незавершённым вызовом и ничего не исполняет. Не возвращать reasoning_content, raw-объект и внутренние поля провайдера.
- Тесты: синтетические complete/length/refusal/empty, неизвестная причина, несколько choices, битый JSON и неверные типы; независимые отсутствующие/нулевые/неверные usage. Инструменты: описание → запрос, предыдущий вызов + результат → следующий запрос, несколько вызовов в ответе, текст вместе с вызовами, неизвестное имя, пустые/повторные id и неверный тип аргументов. Неверный JSON внутри строковых arguments сохраняется буквально и не исполняется. Кириллица, пробелы и переносы сохраняются. На этом шаге уже есть конечный таймаут и ограничение тела из общих параметров; полный разбор граничных случаев — шаг 4.
- Условие готовности: подмена подтверждает корректный Go-запрос и нормализованные исходы; ни одного настоящего запроса, build и все тесты проходят.

### 4. Ограничение ожидания и безопасные ошибки

- Цель: закрыть зависания при чтении тела, отмену и отказ транспорта без повторной отправки.
- Модули и файлы: src/llm/client.ts, src/llm/errors.ts, src/llm/validation.ts из предыдущих шагов; новые tests/llm-failures.test.ts и tests/llm-resources.test.ts, tests/helpers/llm-http.ts.
- Действия: общий deadline включает заголовки и чтение потокового тела; ограничивать накопленные байты до JSON.parse. Не доверять одному Content-Length. Предварительно отменённый сигнал исключает сеть; собственный AbortController объединяет deadline и сигнал вызывающего компонента. Прекращать ожидание даже при подмене, игнорирующей abort; позднее завершение не доставляет второй результат и не создаёт unhandled rejection. При выходе удалять слушатели, очищать таймер, отменять reader. Ошибку исходного тела не прикладывать к публичному исходу.
- Тесты: 401, 403, 429, 5xx, redirect и неожиданный HTTP-статус; исключения fetch/reader и не-Error значения. Для каждого исхода число HTTP-попыток не больше одной, endpoint не меняется. Управляемые часы и потоки проверяют задержанные заголовки/части тела, зависание после заголовков, границу размера в байтах с кириллицей, ложный Content-Length, отмену до/во время вызова и гонки отмены с успехом. После всех исходов нет оставшихся таймеров, слушателей и необработанных отказов.
- Безопасность: поместить синтетические секреты и тексты в HTTP-body/headers/statusText/message/stack/cause и убедиться, что они не выходят в сериализованном результате и диагностику. Клиент не логирует запрос/ответ даже при debug; дополнительный интерфейс логирования не вводить ради клиента.
- Условие готовности: все ожидания ограничены, категории различимы, одна попытка и отсутствие утечек проверены; build и все тесты проходят.

### 5. Изоляция параллельных обращений и проверка сборки

- Цель: подтвердить снимок данных, независимость сессий и работу скомпилированного пакета.
- Модули и файлы: новые tests/llm-isolation.test.ts и tests/llm-dist.test.ts; существующие [tests/esm.test.ts](../../tests/esm.test.ts), [tests/platform-imports.test.ts](../../tests/platform-imports.test.ts), [tests/build-boundaries.test.ts](../../tests/build-boundaries.test.ts); исправления src/llm по результатам проверки.
- Тесты: два параллельных вызова с разными сессиями, обратный порядок ответов, ошибка/отмена одного не влияет на другой. После вызова изменить исходную конфигурацию, сообщения, вложенную схему tools и список вызовов: транспорт и результат первого запроса сохраняют снимок. Нет общей истории, чтения профилей или каталога. Подменой проверить отсутствие execute и произвольных runtime-полей в HTTP. Не утверждать, что транспорт клиента заменяет проверку прав харнесом.
- Сборка: импорт из dist вне дерева исходников и вызов с подменой транспорта; импорт/создание не читают env/БД, не вызывают fetch, не запускают таймеры и ничего не печатают. Проверки платформенных границ остаются зелёными. Существующий ESM-тест расширить только необходимыми проверками.
- Условие готовности: снимок и изоляция подтверждены фактическими HTTP-телами, dist работает самостоятельно; build и все тесты проходят.
