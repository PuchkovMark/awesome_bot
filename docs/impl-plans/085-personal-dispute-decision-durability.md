## Упорядоченные шаги

### 1. Добавить в SQLite отметки о жалобах и результатах разбора

- **Цель** — различать исходную команду в личке, спорную реплику в беседе и решение по конкретной операции удаления.
- **Модули и файлы** — добавить новую миграцию `src/storage/migrations/058-personal-disputes.ts` и зарегистрировать в `src/storage/migrations/index.ts`. На момент составления плана последняя версия — 57. Для каждой принятой жалобы хранить уникальную пару из исходного диалога и локального номера команды VK, код операции удаления и платформенный номер спорной реплики. Для пары из операции и номера реплики хранить текущее состояние разбора. Беседу и поколение определяет операция удаления. Внешний ключ на неё обеспечивает очистку при удалении поколения. Обе отметки должны переживать физическое удаление текста сообщения.
- При миграции пометить существующие строки `personal_hidden_messages` с `disputed=1` как открытые споры прежней схемы. Безусловные скрытия и `history_deleted_inputs` сохраняют своё значение. У старых жалоб номер события неизвестен. Точное распознавание повторов начинается с жалоб, принятых после обновления. Новые таблицы хранят только идентификаторы и состояние разбора.
- **Тесты** — в `tests/storage-migrations.test.ts` проверить обновление базы версии 57 с открытым спором и удалённой репликой, повторное открытие БД, уникальность события и очистку одного поколения при сохранении соседнего. Обновить проверку состава технических таблиц и историю миграций в перечисленных ниже наборах.

  ```sh
  npm run build
  npm test -- tests/storage-migrations.test.ts tests/storage-dist.test.ts tests/storage-participant-upgrade.test.ts tests/storage-personal-data.test.ts tests/lifecycle-cleanup-coverage.test.ts
  ```

- **Условие готовности** — сборка и тесты проходят. Видимость сообщений и список открытых споров до и после миграции совпадают. Проверка внешних ключей SQLite проходит.

### 2. Фиксировать жалобу и решение в момент обработки личной команды

- **Цель** — повторная доставка принятого события не меняет результат разбора, в том числе после перезапуска или сбоя доставки подтверждения.
- **Модули и файлы** — в `src/app/personal-data.ts` передавать в `reportMessage` исходные `peerId` и `cmid` проверенной личной команды. В `src/storage/personal-data-store.ts` внутри транзакции целевого поколения сначала проверять отметку события. При повторе сохранить видимость и статус очистки. Для нового события применить текущие проверки заявителя, подтверждённого удаления и границы `cutoff_id`. Если жалоба открывает спор, одновременно зафиксировать состояние «открыт» для этой операции. Сохранить отметку каждой принятой жалобы, включая жалобу на реплику, уже ожидающую разбора.
- В `resolveDisputed` записывать решение для каждого спорного основания, которое закрывает команда. В той же транзакции «оставить» снимает эти пометки, а «удалить» фиксирует `history_deleted_inputs` и передаёт сообщение действующей очистке. Сохранить проверку владельца и отправлять подтверждение после фиксации. В `src/storage/personal-deletion.ts` учесть решение при повторном вычислении зависимых скрытий по той же операции. Безусловное удаление, открытый позднее спор и ограничения других операций действуют независимо.
- **Тесты** — в `tests/application-personal-data.test.ts` принять две разные жалобы на реплику, решить «оставить» и повторить оба события из лички. Проверить список владельца, журнал и полнотекстовый поиск. Повторить для «удалить» до и после фоновой очистки. В `tests/storage-personal-data.test.ts` проверить одинаковые номера команд в разных личках, новое допустимое обращение после «оставить», независимое основание для скрытия и повтор после перезапуска. При принудительном откате транзакции отметка и видимость откатываются вместе.

  ```sh
  npm run build
  npm test -- tests/application-personal-data.test.ts tests/storage-personal-data.test.ts tests/storage-history-retention.test.ts tests/profile-personal-data.test.ts
  ```

- **Условие готовности** — сборка и тесты проходят. После ответа «Решение сохранено.» повтор исходной жалобы оставляет реплику и список споров в подтверждённом владельцем состоянии.

### 3. Применять актуальное решение при сверке снимка

- **Цель** — восстановленная БД учитывает принятое решение и распознаёт уже обработанную жалобу до открытия доступа к беседе.
- **Модули и файлы** — в `src/storage/personal-data-restore.ts` сверять отметки по операциям тех поколений, которые допущены в `src/storage/backup-history.ts`. Сначала сопоставить операции и реплики по коду удаления, беседе, поколению и платформенному номеру. Перенести из доверенной БД номера принятых жалоб, в том числе когда текста уже нет. При пересчёте через `confirmDeletion` и `invalidateDependentData` учесть актуальный исход. Старая пометка о споре не должна заново скрыть оставленную запись, а старое «оставить» не должно закрыть более поздний открытый спор. Сохранить действие безусловных удалений и границ истории.
- Для открытого спора прежней схемы без явного решения проверить ту же подтверждённую операцию и ту же реплику в доверенной БД. Проверять фактическую видимость через `personal_visible_messages`, границы из `src/storage/history-retention-store.ts` и отметки удаления. При положительной проверке снять только соответствующую старую пометку. При отсутствии доказательств сохранить скрытие. Локальный ID строки SQLite использовать только в той базе, из которой он прочитан.
- **Тесты** — в `tests/storage-database-restore.test.ts` сверить снимок с открытым спором для обоих решений, случая более поздней жалобы и удаления текста до восстановления. Для старой схемы проверить подтверждённую видимость и случаи, когда в доверенной БД реплика отсутствует, скрыта или истёк срок её хранения. Повторить сверку персональных данных и проверить неизменность результата. В соседней беседе использовать тот же платформенный номер.

  ```sh
  npm run build
  npm test -- tests/storage-database-restore.test.ts tests/storage-personal-data.test.ts tests/storage-database-backup.test.ts tests/storage-departed-participant-restore.test.ts
  ```

- **Условие готовности** — сборка и тесты проходят. Журнал, поиск и список споров в изолированной копии согласуются с актуальными решениями и ограничениями каждого допущенного поколения.

### 4. Проверить оба решения через VK и штатный `backup restore`

- **Цель** — воспроизвести три критерия задачи на временной базе. Повтор события и восстановление снимка проверять в отдельных сценариях для каждого решения.
- **Модули и файлы** — добавить новый тест `tests/application-personal-dispute-restore.test.ts`. Использовать подмены VK и модели из `tests/helpers/application-response-fixture.ts` и запуск собранного CLI по примеру `tests/application-database-backup.test.ts`. Для этого сценария дать стенду внешний временный каталог и возможность повторно подать исходное событие с заданными диалогом и номером. На остановке закрывать все подключения SQLite, сохраняя каталог для `backup restore`. После переключения открыть базу заново по тому же пути.
- **Тесты** — записать в беседах A и B по реплике одного автора с одинаковым локальным номером. Другой участник подтверждает удаление своих данных в A и указывает реплику A через `/сообщить-упоминание`. В первом сценарии владелец принимает решение, после чего VK повторяет ту же жалобу. Во втором создать снимок, пока спор открыт, затем принять решение через личку владельца, остановить приложение и вызвать `backup restore` на этом снимке.
- До возобновления обработки прочитать журнал, полнотекстовый поиск и список споров из восстановленной БД. После запуска продолжить те же поколения диалогов штатным решением владельца, запросить `/спорные-записи` в его личке и повторить исходное событие. При «оставить» реплика в A видна в журнале и поиске, при «удалить» она скрыта в обоих местах. В каждом случае эта реплика отсутствует в списке споров, а контрольная реплика в B доступна. Использовать актуальные UTC-метки для стенда и CLI, чтобы проверяемые реплики находились внутри срока хранения.

  ```sh
  npm run build
  npm test -- tests/application-personal-dispute-restore.test.ts tests/application-personal-data.test.ts tests/application-database-backup.test.ts
  ```

- **Условие готовности** — сборка и тесты проходят. Все четыре сочетания решения и сценария проверены по фактической выдаче A и B. Повтор после переключения базы подтверждает перенос отметки о жалобе.
