## Упорядоченные шаги

После каждого шага выполнить указанные тесты и `npm run build`. Для реестра и цикла достаточно синтетического инструмента и подмен модели и адаптера. Для подключения инструментов участников нужны реестр F5.1, правила допуска F5.8, выбранное обращение F5.2 и разрешённый источник публичного интереса F5.3. Схема хранения профиля сама по себе не подтверждает разрешение на выдачу.

### 1. Отобрать и исполнить инструмент в доверенной области

В новом `src/tools/registry.ts` собрать определения из `src/contracts/tool.ts`, отклонять дубли имён. По доверенным контексту и адаптеру формировать список схем для конкретной попытки. Перед исполнением сверять имя с выданным списком, перепроверять текущие возможности, валидировать объект аргументов и отклонять неизвестные поля. Использовать `src/tools/authorization.ts` и отдельную проверку роли харнесом для изменяющих действий. Сам обработчик проверяет полномочия и поколение при доступе к данным.

В новом `tests/tool-registry.test.ts` проверить две искусственные платформы, общий и платформенный инструменты, пустой список платформ, неподтверждённую возможность, её отзыв, некорректный JSON и подстановку chatId. Запустить также `tests/tool-authorization.test.ts`. При отказе до вызова счётчик обработчика равен нулю. Ошибка и диагностика содержат безопасный код без параметров вызова.

### 2. Провести инструментальный обмен через штатный цикл

В `src/core/agent-loop/{service,types,validation}.ts` подключить реестр через доверенные зависимости. Сохранить текущий текстовый путь. Перед каждой попыткой, включая повтор после ошибки провайдера, заново определить доступные схемы. Для ответа с вызовами сохранить сообщение assistant и вернуть по одному сообщению tool с исходным идентификатором каждого вызова. Строки результата передавать как данные. При повторе продолжения повторно проверить актуальность результатов, использовать сохранённые результаты без повторного исполнения. Применять существующие пределы шагов, попыток и общего срока.

Через `src/core/chat-queue/agent-loop-adapter.ts` проверять резерв F4.6 на фактический запрос со схемами и результатами. В новом `tests/agent-loop-tools.test.ts` и существующем `tests/chat-queue-agent-loop.test.ts` проверить несколько вызовов в одном ответе, исходные идентификаторы, смену списка между шагами, отказ в вызове, отмену, повтор провайдера и исчерпание бюджета. При продолжении с одним повтором ожидаются одно исполнение читающего инструмента, отдельный учёт каждой попытки модели, одно списание F4.3 и один конечный ответ. Этот шаг даёт проверяемый реестр для задачи 036.

### 3. Реализовать карточку, поиск и список участников

В новом `src/tools/participants.ts` описать три читающих инструмента. Подключить чтение в исходном поколении через контракты F5.1, F5.2, F5.3 и F5.8. Для списка выбирать подтверждённых присутствующих. Применить видимость для аудитории ответа до поиска и сортировки. Разрешить имя, фамилию, доступное выбранное обращение и явно указанный публичный интерес. При закрытии профиля оставить только базовые данные, разрешённые F5.8. Карточка принимает только однозначную локальную ссылку, связанную с подтверждённым автором, цитатой, упоминанием или разрешённым результатом. При совпадении имён предложить уточнение через цитату или упоминание. Проверить ответ на отсутствие служебных меток.

В новом `tests/participant-tools.test.ts` проверить все три операции на двух беседах с тёзками, обычным участником и администратором. Сравнить выдачу до и после изменения одного закрытого поля, включая порядок, подсказки и количества. Проверить выбранное обращение, публичный интерес и подтверждённую цитату второго тёзки. Готовность — каждый положительный результат объясняется видимыми данными конкретной беседы. До готовности источников выполнять эти сценарии с фикстурами.

### 4. Применить общий предел и защитить продолжение и публикацию

В `src/tools/participants.ts` и цикле связать три операции с единым множеством уже показанных участников исходного обращения. Обрабатывать вызовы одной пачки в согласованном порядке. По умолчанию поиск и список выдают до пяти человек, сортировка по отображаемому имени и локальному ключу. После десяти разных людей можно повторно получить разрешённую карточку уже показанного человека. Отдельно сообщать об отсечении по пределу и неполноте состава. Вместе с результатом хранить внутри харнеса зависимости для проверки актуальности, включая источники совпадения в поиске. Подключить их к проверкам перед каждым вызовом модели и перед отправкой через штатный маршрут приложения в `src/app/service.ts`.

В тестах инструментов взять неполный снимок из 12 известных участников, запросить 20, затем карточки десятого и одиннадцатого. Проверить обе отметки неполноты, стабильный порядок, общий потолок при нескольких вызовах и независимый счётчик нового обращения. В новом `tests/application-participant-tools.test.ts` отозвать видимость после поиска перед продолжением, затем в отдельном сценарии перед публикацией. В первом случае устаревший результат не передаётся модели, во втором — ноль отправок в VK. Повторить при смене поколения и переходе в uncertain.

Включить прямое обращение без инструментов, запрос о тёзке с уточнением, неполный список и инструкцию внутри строки профиля.
