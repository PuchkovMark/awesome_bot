## Границы и порядок проверки

Это черновик перед реализацией. Каждый шаг заканчивается зелёной сборкой, соответствующими тестами и отдельным коммитом только своих изменений. Сначала убирается поддержка поля из API/SQL, пока столбец ещё существует; затем новая миграция удаляет его. Это позволяет сохранить рабочее состояние после каждого шага без временного псевдополя и без совместимых перегрузок.

Используются текущие Node.js, npm и зависимости проекта. [npm run build](../../package.json) включает lint, проверки импортов каталога/контекста, typecheck и ESM-сборку. Для каждого шага выполняются build и полный npm test, поскольку затрагиваются общие контракты хранения. Адресные тесты допускаются при исправлении конкретной ошибки; перед завершением шага полный прогон должен пройти. Сетевые обращения VK/LLM подменяются, зависимости и конфигурационные параметры не добавляются.

Поиск systemPrompt/system_prompt разделяет: удаляемое свойство настроек, действующие операции общего каталога и исторические схемы/тексты. Источники старых миграций и их контрольные суммы не меняются. Боевые данные не предполагаются, но upgrade существующей тестовой БД проверяется полноценно.

## Упорядоченные шаги

### 1. Удаление поля из контрактов и работающего API настроек

- Цель: настройки больше не принимают и не возвращают индивидуальный промпт, при этом проект работает на текущей схеме со старым nullable-столбцом.
- Модули и файлы: [публичные типы](../../src/storage/types.ts), [внутренние типы](../../src/storage/legacy-types.ts), [SQL настроек](../../src/storage/chats.ts); [настройки](../../tests/storage-chats.test.ts), [интеграция хранения](../../tests/storage-integration.test.ts), [обновление профилей](../../tests/storage-participant-upgrade.test.ts), [помощник контекста](../../tests/helpers/context.ts), [контекст](../../tests/context-builder.test.ts), [связка контекста](../../tests/context-integration.test.ts). Проверить остальные текущие потребители поиском, не менять законные версии/методы общего промпта.
- Изменения: исключить systemPrompt из ChatInput/ChatSettings/ChatPatch на обоих уровнях; убрать колонку из действующих SELECT/INSERT и словарей UPDATE/валидации. Старый столбец на этом шаге остаётся в схеме и получает SQL default null при новых строках; имеющиеся значения не читаются. Методы общего промпта и contextState не переименовываются.
- Строгий отказ: неизвестное поле отклоняется до записи при create/update, включая null, undefined и смешанный patch с допустимым названием/режимом. Неверный create отклоняется и для существующего чата; другой чат и прежние настройки не меняются. Отсутствующий чат не создаётся невалидным запросом.
- Тесты: новый `tests/legacy-chat-prompt-contracts.typecheck.ts` запрещает свойство во входах и чтении публичных/внутренних контрактов; типовые проверки входят в build. Дополнить runtime-тесты отказов в storage-chats и проверки отсутствия собственного поля в выдаче. Сохранить проверку сброса title через null, всех остальных настроек, даты, идемпотентности и повторного открытия; старые тесты сохранения индивидуального промпта заменить соответствующими проверками оставшихся полей, а не убрать покрытие настроек.
- Фикстуры: убрать запись LEGACY_SECRET через текущий chats.create в helpers/context. Проверки, которые после этого лишь искали отсутствующий текст без его внесения, не считать доказательством миграции: перенести проверку старого текста в целевую upgrade-фикстуру шага 2. Исторический SQL, создающий старую схему для upgrade, сохраняется.
- Условие готовности: npm run build и npm test проходят; действующие операции настроек не обращаются к system_prompt, новые и старые вызовы с systemPrompt явно отклоняются, общее чтение системной версии работает. Физическое удаление столбца на этом промежуточном шаге ещё не заявляется.

### 2. Новая миграция и проверка обновления существующей БД

- Цель: убрать столбец из конечной схемы новой и существующей БД с доказанной сохранностью остальных данных.
- Модули и файлы: новый `src/storage/migrations/011-remove-legacy-chat-prompt.ts`; [реестр миграций](../../src/storage/migrations/index.ts), существующий [механизм migrate](../../src/storage/migrate.ts) использовать без изменения его семантики. Новые `tests/storage-legacy-chat-prompt-migration.test.ts`, `tests/helpers/legacy-chat-prompt-fixture.ts`; существующие [миграции](../../tests/storage-migrations.test.ts), [схема F2.5](../../tests/storage-context-migration.test.ts), [ESM хранения](../../tests/storage-dist.test.ts), [старый upgrade](../../tests/storage-participant-upgrade.test.ts), [охват очистки](../../tests/lifecycle-cleanup-coverage.test.ts).
- Изменения: миграция 11 удаляет только chats.system_prompt штатным удалением столбца SQLite; операция такого класса уже используется миграцией 8. Реестр получает следующую версию; тексты 1–10 сохраняются. Не пересоздавать альтернативный набор миграций для новой БД, не отключать внешние ключи ради обхода ошибки и не переносить текст в другие таблицы.
- Upgrade-фикстура: создать базу ровно версии 10 с непустым отличимым индивидуальным текстом, разными настройками двух чатов, сообщениями/FTS, активной областью и минимальными связанными правами/версиями/выбором/очередью. Сохранить контрольные суммы и снимки остальных данных. Сравнение заданий queued/running/terminal выполнять до запуска очереди, чтобы её штатное восстановление не выдавалось за изменение миграцией.
- Тесты схемы: PRAGMA table_info подтверждает отсутствие столбца на новой БД и после upgrade; записана версия 11, повторный migrate/повторное открытие не меняет результат. Остальные колонки chats, настройки, строки связанных таблиц, FTS-поиск и foreign_key_check сохранены. Общая версия и локальные версии персонажа/приветствия не получают старый индивидуальный текст. После upgrade подготовить контекст реальным сборщиком F2.5 и проверить точную выбранную общую версию и отсутствие старого текста в system/messages.
- Откат: на версии 10 применить набор с миграцией 11 и следующей заведомо ошибочной миграцией только внутри теста; подтверждается откат всей недостающей последовательности, возврат старого столбца/значения и отсутствие записей новых версий. Ошибка не приводит к частичной потере настроек. Рабочий набор миграций не содержит этой искусственной версии.
- Существующие проверки: ожидания конечного списка миграций/их числа обновить до 11; старые проверки прежних контрольных сумм сохранить. Проверку наличия system_prompt в исторической схеме F2.5 привязать к явной версии до удаления, а не требовать столбец от последней схемы или просто удалить тест. Исходники старых схем не переписывать.
- Условие готовности: build и полный npm test проходят; чистая БД и upgrade имеют одну целевую схему без столбца, прежние миграции неизменны. Тест фактически использует старый текст до удаления, а не проверяет его отсутствие на пустом входе.

### 3. Регрессия общего промпта, изоляции и выпуска

- Цель: подтвердить прежнюю работу общего каталога/F2.5 и отсутствие скрытой зависимости потребителей от удалённого поля.
- Модули и файлы: новый `tests/legacy-chat-prompt-context.test.ts`, upgrade-помощник шага 2; существующие [выбранные версии](../../tests/version-selection.test.ts), [согласованный снимок](../../tests/version-snapshot.test.ts), [контекстная очередь](../../tests/context-queue.test.ts), [публикация ошибок подготовки](../../tests/context-notices.test.ts), [изоляция хранения](../../tests/storage-scoped.test.ts), [публичная граница](../../tests/storage-public-boundary.test.ts), [очистка](../../tests/lifecycle-cleanup.test.ts), [ESM хранения](../../tests/storage-dist.test.ts), [ESM контекста](../../tests/context-dist.test.ts). Действующие reader/очередь/цикл не менять, если тесты не выявят необходимое исправление в рамках удаления.
- Тесты: после upgrade запустить локальную связку очереди, подготовки и подменного клиента. При выбранном общем промпте клиент получает его точную версию, бывший индивидуальный текст не возвращается в контекст. При отсутствии общего выбора, но непустом старом поле до миграции, после обновления остаётся missing_system_prompt, отдельный счётчик и ноль вызовов клиента; fallback не возникает. Действующие storage.versions.systemPrompt/contextState.systemPrompt и инфраструктурный выбор каталога проходят регрессию.
- Совместимость: сохранены null для отсутствующего чата, scope-проверки, повторное создание и дата, независимые настройки чатов. Удаление беседы по-прежнему очищает локальные данные и оставляет общие версии. ESM-выпуск открывает обновлённую БД и работает с текущими настройками без исходников/сети.
- Аудит: поиск действующих полей/SQL и фикстур не оставляет писателей удалённого столбца. Каждый оставшийся systemPrompt/system_prompt относится к общему каталогу, отрицательному тесту либо исторической схеме; название операции общего промпта не служит поводом для удаления. Границы каталога и полного журнала продолжают проверяться build.
- Проверки: npm run build, npm test; npm run test:queue-load для регрессии текущих нагрузочных фикстур/большой очистки на новой схеме. Новые нагрузочные сценарии и платные evals не вводятся: формат/текст общего промпта, модель и рабочие лимиты не меняются.
- Условие готовности: все проверки проходят, критерии задачи имеют фактические тестовые подтверждения; нет ни старого текущего API, ни молчаливого обхода через каталог/персонажа. Нельзя закрыть шаг одним поиском слова без проверки миграции и реального запроса клиента.
