## Границы и параметры для утверждения

План реализует ядро на подменах, без инструментов, сети, чтения БД и .env, новых зависимостей, миграций и изменения клиента F2.1. [Ядро](../../src/core/index.ts) сейчас экспортирует авторизацию и жизненный цикл; файлов агентного цикла пока нет. LlmClient внедряется через его нейтральный тип, HTTP-реализация не импортируется ядром. Настоящий Go не вызывается.

Предлагается фабрика createAgentLoop(client, options) с методом run(input). Опции фиксируются при создании и не меняются моделью или содержимым запроса. maxSteps по умолчанию 6 уже согласован; предлагаемые новые defaults: maxAttemptsPerStep = 2 (первая попытка и один повтор), timeoutMs = 120000 мс на весь запуск, retryDelayMs = 1000 мс, retryServerErrors = true. Новые числа — предложение этого черновика. Счётчики — положительные безопасные целые; срок и пауза — положительные целые до 2147483647 мс из-за ограничения таймера Node.js. Пауза может быть длиннее оставшегося срока: тогда срок завершается без нового обращения. Переменные окружения для этих опций сейчас не вводятся.

Политику и пределы повторов в проде утверждает владелец бота; F3.4 передаст их инфраструктурной конфигурацией. Ядро не добавляет команд управления или собственную проверку личности владельца: фабрика доступна доверенной сборке приложения, модель не получает к ней инструмент. В этой версии есть только отключение повторов server, без произвольного списка расширяемых категорий. rate_limit всегда конечный исход; его перепланирование остаётся очереди F2.3 и проверке F2.9.

Один логический шаг в первой версии может иметь несколько попыток. После результата этого шага запуск завершается; искусственного перехода к следующему нет. maxSteps сохраняется для будущего полного цикла, но сейчас больше одного шага не производится. Тесты не объявляют проверенным отсутствующий инструментальный переход между шагами.

После реализации, review и sync-specs задача 012 и F2.2 получают статус «реализовано на подменах, ожидает валидации» и остаются активными. F2.9 обязательна до F5.6. Финальное выполнение и перенос всех документов в completed — отдельная условная часть последнего шага после валидации. Эти правила меняют прежнюю блокировку приёмки каркаса до F2.9 и не разрешают живой запуск.

На каждом шаге обязательны npm run build и npm test, включая существующие проверки ESM, платформенных границ и каталога. После успешного шага — отдельный коммит его файлов, без посторонних изменений. Число тестов и результаты фиксируются в этом документе. Ни один шаг не должен оставлять неработающие импорты или обещать готовность ещё не реализованного поведения.

## Упорядоченные шаги

### 1. Нейтральные типы, безопасные исходы и счётчики

- Цель: разделить логические шаги, попытки и исходы без инфраструктурной зависимости.
- Модули и файлы: новые src/core/agent-loop/types.ts, errors.ts, validation.ts и summary.ts в этом каталоге; существующий [src/core/index.ts](../../src/core/index.ts). Типы клиента берутся из [src/llm/types.ts](../../src/llm/types.ts) только через import type.
- Контракт: вход содержит system, текстовую историю user/assistant, maxOutputTokens, sessionId и signal. Нет tools, tool-истории, callId, toolCalls и произвольных параметров клиента. Результаты различают complete с text, incomplete с partialText, refused, empty, rate_limit, tools_not_supported, cancelled, deadline_exceeded, attempt_limit и безопасную error с фиксированной категорией. В attempt_limit остаётся только безопасный lastErrorCode = server; не сообщение провайдера. Невалидная конфигурация даёт фиксированный TypeError, неверный ввод — безопасный исход без обращения.
- Сводка: steps, attempts, attemptsPerStep, durationMs и независимые input/output. У каждого счётчика токенов knownTokens (число либо null при переполнении), unknownAttempts и overflowed; точный итог допустим только при unknownAttempts = 0 и отсутствии переполнения. Пока обращений не было, оба расхода достоверно равны нулю. Ошибка без usage — неизвестный расход попытки, а не ноль.
- Тесты: новые tests/agent-loop-contracts.typecheck.ts и tests/agent-loop-summary.test.ts. Проверить типовое исключение инструментов, сумму известных значений с неизвестными, явный ноль, неверные usage и переполнение. Разделить число шагов и попыток в проверках; не создавать публичную фиктивную фабрику до рабочего run.
- Условие готовности: типы и вспомогательные функции собираются без SDK/платформ, диагностические поля фиксированы; build и все тесты проходят.

### 2. Рабочий текстовый запуск и обработка исходов

- Цель: получить независимый одиночный логический шаг без инструментов.
- Модули и файлы: новый src/core/agent-loop/service.ts; типы, validation/errors/summary предыдущего шага; [src/core/index.ts](../../src/core/index.ts). Новые tests/helpers/agent-loop.ts и tests/agent-loop-outcomes.test.ts.
- Действия: создать явную фабрику с неизменяемой конфигурацией и run. До асинхронной работы проверить и скопировать разрешённые поля входа. Каждый вызов клиента получает отдельную копию этого снимка. Не импортировать или создавать HTTP-клиент. Уже на этом шаге запуск имеет конечный общий срок и передаёт сигнал отмены; тесты однопопыточного пути используют maxAttemptsPerStep = 1, повторы добавляются следующим шагом.
- Исходы: проецировать проверенный результат клиента в разрешённые поля, без передачи исходного объекта/message/stack/cause/reasoning_content. Только корректный непустой complete — успех с буквальным текстом. incomplete остаётся частичным; refused/empty/rate_limit — конечные отдельные исходы. tool_calls возвращает tools_not_supported без разбора аргументов и без сопутствующего текста. Неожиданные значения и отказ/синхронный throw клиента дают client_failure, не пробрасываются и не повторяются.
- Тесты: complete сохраняет пробелы/кириллицу/переносы; неполные, пустые, отказные, инструментальные и ошибочные ответы не становятся успехом. Некорректный вход и поля инструментального режима отклоняются до вызова. Даже при maxSteps = 6 есть один шаг; первая вызванная попытка даёт steps = 1, attempts = 1, attemptsPerStep = [1].
- Условие готовности: run работает с синтетическим LlmClient без сети и побочных действий при создании; build и все тесты проходят.

### 3. Ограниченные повторы server внутри одного шага

- Цель: реализовать согласованную политику, не смешивая пределы.
- Модули и файлы: src/core/agent-loop/service.ts и summary.ts; новый tests/agent-loop-retries.test.ts и tests/helpers/agent-loop.ts.
- Действия: первая попытка запускает шаг, каждая отправка увеличивает attempts и счётчик текущего шага; server допускает повтор после отменяемой конечной паузы только при retryServerErrors = true, наличии слота maxAttemptsPerStep и общего времени. Не сбрасывать срок или число попыток и не дополнять историю текстом ошибки. Не вычислять произведение maxSteps и maxAttemptsPerStep ради обхода независимых пределов. После конечного исхода не начинать следующий логический шаг.
- Тесты: server → complete с default даёт один шаг и две попытки; server до предела даёт attempt_limit с lastErrorCode, без дополнительной отправки. maxSteps = 1 допускает две попытки этого шага; retryServerErrors = false даёт одну попытку и error/server. Успех последней попытки не отбрасывается. rate_limit даёт отдельный исход и ровно одну попытку даже при большом maxAttemptsPerStep; network/timeout, постоянные ошибки и отказ Promise не повторяются. На повторе используются те же system/messages/sessionId/maxOutputTokens, неизвестный расход первой ошибки сохраняется.
- Условие готовности: server — единственная автоматически повторяемая категория, отдельные счётчики точны, границы попыток и срок не обходятся; build и все тесты проходят.

### 4. Общий срок, отмена, паузы и освобождение ресурсов

- Цель: обеспечить конечность ожидания независимо от поведения подмены.
- Модули и файлы: src/core/agent-loop/service.ts; при необходимости новый src/core/agent-loop/timing.ts; новые tests/agent-loop-resources.test.ts, tests/agent-loop-deadline.test.ts, tests/helpers/agent-loop.ts.
- Действия: учитывать общее время вызовов и пауз, не запускать следующую попытку после дедлайна или отмены. Для длительности использовать монотонное время; абсолютные даты/таймзона чата не влияют на бюджет. Передавать объединённый сигнал клиенту и ограничивать ожидание даже при игнорировании abort. Безопасно наблюдать поздний результат/отказ Promise без вторичной доставки или unhandled rejection; чистить собственные таймеры и слушатели при любом исходе.
- Тесты: предварительная отмена даёт steps = 0, attempts = 0; отмена в первой попытке, в повторе и во время паузы прекращает обращения. Дедлайн внутри первой попытки и между попытками, пауза длиннее остатка времени и ответ на границе срока не продлевают запуск. Timeout клиента остаётся error/timeout без повтора, общий срок даёт deadline_exceeded. Подмена, игнорирующая сигнал, не удерживает run; поздний usage не меняет уже возвращённую сводку. Проверить отсутствие таймеров/слушателей после успеха, отказа, лимита, отмены и дедлайна управляемыми часами без реального ожидания.
- Условие готовности: каждый запуск возвращает один безопасный исход в пределах времени, расход незавершённых попыток остаётся неизвестным; build и все тесты проходят.

### 5. Снимки, параллельная изоляция, диагностика и ESM

- Цель: подтвердить границы ядра и отсутствие скрытого общения с инфраструктурой.
- Модули и файлы: новые tests/agent-loop-isolation.test.ts, tests/agent-loop-security.test.ts, tests/agent-loop-dist.test.ts; существующие [tests/esm.test.ts](../../tests/esm.test.ts), [tests/platform-imports.test.ts](../../tests/platform-imports.test.ts), [tests/build-boundaries.test.ts](../../tests/build-boundaries.test.ts). Изменения существующих тестов только по необходимости.
- Тесты: два параллельных запуска с разными сессиями, обратным порядком исходов, отказом и отменой одного не смешивают историю, счётчики или результат. Изменение исходной конфигурации/истории после запуска и изменение переданной копии самой подменой не меняют повтор. В HTTP ничего не отправляется; ядро вообще не создаёт транспорт.
- Безопасность: добавить синтетические секреты и полный контекст в неожиданные поля, message/stack/cause и tool_calls подмены. Проверить, что они не выходят в ошибках, сводке и диагностике и что execute не вызывается. Фиксированные категории ошибок выбираются по разрешённым кодам, сообщение подмены не цитируется. Модель не может изменить maxSteps/maxAttemptsPerStep или включить повтор rate_limit.
- Сборка: импорт и создание компонента из dist вне исходников, запрет неожиданных env/БД/сети/таймеров при импорте/создании; вызов только с подменой клиента. Существующие проверки ESM/платформ/каталога проходят. Не добавлять проверку «active не публикует» в один цикл без отправителя: это не докажет продуктовый сценарий.
- Условие готовности: изоляция, безопасные метаданные и отсутствие зависимостей от Go подтверждены; build и все тесты проходят.
