## Подход и ключевые решения

### Выбранный сервис и проверенные сведения

Пользователь выбрал подписку OpenCode Go. Модель остаётся `deepseek-v4.1-flash`, ключ — `OPENCODE_API_KEY`, имя модели явно передаётся из `LLM_MODEL`. [Слой llm](../../src/llm/index.ts) пока пуст; [конфигурация](../../src/config/types.ts) уже хранит провайдера, модель и ключ. План вводит изолированный текстовый клиент, без агентного цикла или подключения к ответам бота.

Официальные источники проверены 2026-11-21, без ключа и вызова модели:

| Сведения | Источник и граница вывода |
| --- | --- |
| Go использует базу `https://opencode.ai/inference/go`; совместимый путь Chat Completions — `/openai/v1/chat/completions` | [Base URLs](https://opencode.ai/docs/console/harnesses#base-urls); полный маршрут для этого плана — `https://opencode.ai/inference/go/openai/v1/chat/completions` |
| JSON POST и Bearer-авторизация; Chat Completions — документированное семейство API | [Inference API](https://opencode.ai/docs/console/api/inference/); это протокол OpenCode, не обращение к серверам OpenAI |
| Идентификатор `deepseek-v4.1-flash` соответствует Chat Completions; модель представлена в Go | [Каталог моделей](https://opencode.ai/docs/console/models/), [список Go](https://opencode.ai/console/go); доступность конкретному ключу не проверена |
| Go требует запросов coding agent, собственного User-Agent и стабильного `x-opencode-session`; для DeepSeek нужны подходящие настройки региона | [Go](https://opencode.ai/docs/console/go/#where-can-i-use-it); пригодность обычного общения бота этим не доказана |

Выбор подписки снимает вопрос маршрута для проектирования клиента. Он не считается подтверждением разрешённости разговорного трафика или доступности модели аккаунту. До реального подключения в F3.x владелец должен выяснить применимость условий Go к боту и проверить доступы; здесь остаются синтетические проверки без сети. Клиент не добавляет вымышленные задания программирования и не представляется OpenCode, Claude Code или другим агентом.

### Единый контракт и отсутствие состояния диалога

Предлагается нейтральный интерфейс одного текстового обращения. Запрос содержит отдельный системный текст, упорядоченный список сообщений `user/assistant`, предел выходных токенов и доверенные служебные параметры: непрозрачный идентификатор сессии и сигнал отмены. Пустой список сообщений и неверные параметры отклоняются до сети; пользовательский текст сохраняется буквально. Провайдер, модель, ключ и таймаут фиксируются при явном создании клиента, а не выбираются содержимым сообщения.

Клиент делает снимок конфигурации и запроса до начала асинхронной работы. Он не хранит общую историю сообщений, не читает БД, версии или профили и не добавляет сведения из других запросов. Два параллельных обращения не смешивают данные. Нейтральные типы не содержат SDK или платформенных типов; HTTP-преобразование остаётся в слое llm.

Идентификатор сессии приходит от доверенного вызывающего компонента отдельно от текста модели. Он стабилен для одной беседы в пределах подключения, различается между беседами и меняется при новом подключении. В HTTP-заголовок не передаются сырой chatId, имя участника или текст сообщения. Клиент не вычисляет идентификатор из содержимого, не создаёт хранимые соответствия и не обещает сам проверять поколение: это обязанность будущей границы харнеса. Получение долговечного идентификатора без персонального следа после удаления определяется при интеграции F2.3/F3.4; тесты F2.1 явно передают синтетические сессии.

### Прямой HTTP-вызов без SDK

Предлагается встроенный `fetch` Node.js с подменяемой HTTP-границей. Для небольшой текстовой части протокола отдельный SDK не требуется. Все тесты используют подмену; она позволяет проверить фактический адрес, заголовки, тело и число попыток, а не только заранее нормализованный ответ. Импорт и создание клиента не вызывают сеть, не читают `.env` и не запускают таймеры.

Вызов идёт только на выбранный HTTPS-маршрут Go, с честным User-Agent приложения и обязательной сессией. Произвольные адреса и заголовки из сообщения не принимаются. Redirect отклоняется; автоматического перехода на другой endpoint, модель, бесплатный вариант или оплату по использованию нет. В теле передаются только согласованные текстовые поля и ограничение вывода, без произвольного passthrough параметров.

Это не гарантия отсутствия дополнительных списаний на стороне сервиса: [настройка Extra Usage](https://opencode.ai/docs/console/go/#usage-beyond-limits) может расходовать баланс при исчерпании подписки. Клиент не меняет настройки аккаунта; их проверка относится к реальному запуску. Тарифы и расчёт стоимости F2.1 не реализует.

### Нормализация ответа

Предлагается следующая семантика; это политика клиента для утверждения, а не утверждение о качестве модели:

| Ответ | Результат для будущего харнеса |
| --- | --- |
| Один текстовый ответ, завершение `stop`, непустой после проверки пробельности текст | Полный ответ; исходный текст возвращается без trim и переписывания |
| Текст с завершением `length` | Отдельно помеченный незавершённый ответ; не выдаётся за полный, сам не публикуется |
| Явный отказ/фильтрация | Безопасный исход отказа; внутренние диагностические поля не становятся текстом пользователю |
| Вызов инструмента, включая ответ с одновременно приложенным текстом | Неподдерживаемый вариант; ничего не исполняется и не маскируется обычной репликой |
| Неверный JSON/структура, несколько вариантов вместо одного, неизвестная причина завершения | Некорректный либо неподдерживаемый ответ, без выбора произвольной альтернативы |
| Отсутствующее, пустое или только пробельное содержимое | Явный пустой результат; не успешная реплика и не повод скрытно повторить запрос |

Скрытые рассуждения и поля `reasoning_content` не используются как финальный текст и не копируются в логи. Дополнительные поля провайдера не становятся инструкциями и не возвращаются как raw-объект.

Результат несёт нормализованный расход входных и выходных токенов, если сообщены корректные значения. Отсутствие остаётся неизвестным отдельно для каждого счётчика; ноль допустим только как явно сообщённое значение. Неверные числа не суммируются и не заменяются оценкой. Точные имена типов и правила валидации дополнительных метаданных относятся к плану реализации. Тарифные поля и внутренние идентификаторы аккаунта наружу не передаются.

### Ошибки, длительность и повторы

Ошибки конфигурации/ввода, авторизации, запрета доступа, ограничения провайдера, временного серверного сбоя, сети, таймаута, отмены и некорректного ответа различаются безопасными исходами. HTTP 403 не трактуется автоматически как неверный ключ или исчерпанная квота. Raw response, заголовки, тело ошибки, исходные message/stack/cause не выдаются вызывающему компоненту. Обычная диагностика использует существующий безопасный логгер; полного запроса и ответа клиент не логирует даже в отладочном режиме.

Один вызов клиента означает одну HTTP-попытку, включая ошибки 429/5xx и разрыв соединения. Автоматических ретраев, фонового ожидания квоты и смены маршрута внутри клиента нет. Единственный владелец ограниченных повторов — будущий харнес/агентный цикл F2.2, который должен учитывать общий срок и возможность повторного списания за уже обработанный запрос. Готовность этих повторов здесь не заявляется; F2.1 предоставляет различимые категории, а не скрытый второй цикл ретраев. Это сохраняет целевую политику устойчивости приложения без обещания идемпотентности внешнего API.

Положительный конечный таймаут ограничивает ожидание транспорта и чтения ответа, не только получение заголовков. Отмена до вызова исключает сеть; отмена во время работы останавливает ожидание и передаётся транспорту. Чтение ответа ограничено размером, чтобы JSON не создавал неограниченное потребление памяти. Таймеры и обработчики освобождаются при любом исходе; результат после завершения/отмены не доставляется повторно. Параметры и числовые defaults таймаута, размеров и выходного бюджета выбираются в плане реализации, а не следуют из числа токенов в спецификации контекста.

## Альтернативы и причина выбора

- Маршрут Console с оплатой по использованию не соответствует выбранному Go; скрытый fallback на него исключён.
- SDK скрывает часть HTTP-поведения и может вводить собственные повторы. Встроенного транспорта достаточно для ограниченного контракта; замена транспорта остаётся локальной для llm.
- Вызов CLI OpenCode добавляет состояние coding agent и чужой агентный цикл; здесь нужен изолированный API-клиент будущего харнеса.
- Автоматическое сохранение диалога или подбор промпта в клиенте смешивает ответственность и данные; весь контекст передаёт вызывающий компонент.
- Стриминг, инструменты, мультимодальность и дополнительные API-семейства расширяют задачу до будущих фич. Их неподдерживаемые варианты отклоняются явно.

## Изменения спецификаций

После реализации и успешного ревью [архитектура](../specs/architecture.md) опишет Go-маршрут, единый контракт и ответственность за повторы. [Агентный цикл](../specs/agent-loop.md) уточнит будущую обработку полного/неполного ответа и ошибок без объявления цикла готовым. [Контекст](../specs/context.md) зафиксирует границу подготовленного запроса и снимка данных.

[Безопасность](../specs/security.md), [privacy](../specs/privacy.md) и [логи](../specs/commands-and-limits.md) уточнят отсутствие raw-диагностики, честную идентификацию и непрозрачную сессию. Условия реального использования Go останутся отдельным ограничением запуска. Правила evals не меняются. Сейчас спецификации не переписываются под ещё не реализованный подход.

## Влияние на контракты и данные

Нужны нейтральные типы запроса/ответа/ошибок и явная фабрика в слое llm с подменой транспорта. SDK провайдера в core/tools/contracts не появляется. Клиент получает готовые параметры конфигурации; будущий план реализации определит настройки сетевого таймаута и ограничений, сохранив явную загрузку и безопасные ошибки F1.2.

БД и миграции не меняются. Постоянное состояние сессий, очередь, выбор версий и трассировки не создаются ради теста клиента. Результат F1.7 и существующее chats.systemPrompt не подключаются к модели автоматически. Изменение модели на другое API-семейство потребует реализации соответствующего адаптера в llm, но не правок ядра: единый интерфейс не обещает поддержки произвольного протокола одним URL.

## Риски

- Условия Go ориентированы на coding agent. Выбранная подписка не подтверждает пригодность разговорного бота; этот вопрос должен быть разрешён до живой интеграции, без маскировки трафика.
- Доступность модели, региональные настройки, лимиты и Extra Usage зависят от аккаунта. Документальные сведения не заменяют проверку реального доступа; клиент не изменяет настройки аккаунта и не гарантирует бесплатность попытки.
- Ошибка нормализации может выдать обрезанный ответ или рассуждение за финальную реплику. Нужны отрицательные сценарии для всех перечисленных вариантов и неизвестных значений.
- Изменение входа во время ожидания может смешать параметры запросов. Проверяются снимок, параллельность и изоляция сессий.
- Таймаут только до заголовков оставляет зависшее чтение тела; проверяются задержанные заголовки/части тела, отмена и освобождение ресурсов. Подмена транспорта не доказывает поведение внешнего сервиса.

## Допущения

Только текст, одна HTTP-попытка, один вариант ответа и выбранное семейство Chat Completions. Тесты — подмены и синтетические данные без сети, настоящих ключей и `.env`. Проверяются запрос, неизвестный usage, неблагоприятные ответы, HTTP-ошибки, таймаут/отмена, лимит тела, отсутствие повторов, утечек и действий при импорте. Сохраняются сборка, линтинг, типы, границы и ESM; README отражает ограничения. Готовность реального API и качество модели этими тестами не заявляются, платные evals не запускаются.

## Открытые вопросы

Выбор Go сделан человеком; блокирующих вопросов для ограниченного клиента с тестами без сети нет. На утверждение предлагаются описанные границы, нормализация ответов, встроенный транспорт и отсутствие автоматических повторов в клиенте. Числа и конкретные сигнатуры остаются плану реализации.

До живого использования F3.x нужно подтвердить применимость условий Go к обычному общению бота, доступность модели и настройки аккаунта. При отрицательном результате выбор подходящего сервиса возвращается человеку; разрешение не выдумывается и маршрут не подменяется. При интеграции харнеса определяются долговечная сессия по подключению и ограниченные повторы; ни готовность хранения сессий, ни готовность внешней доставки этот план не утверждает.
