## Подход и ключевые решения

### Граница ядра

В [ядре](../../src/core/index.ts) уже есть авторизация и жизненный цикл подключения; агентного цикла пока нет. Предлагается отдельно создаваемый компонент с внедряемым [LlmClient](../../src/llm/types.ts). Он получает готовые системные инструкции, историю user/assistant, maxOutputTokens, непрозрачную сессию и сигнал отмены. Параметры ограничений задаёт доверенный вызывающий компонент. Импорт и создание не вызывают модель, не читают окружение и не запускают работу.

Провайдер, HTTP, ключи, chatId, адаптер, хранилище и выбор версий не входят в эту границу. Подготовка контекста остаётся F2.5, очереди — F2.3. Вызывающая граница отвечает за актуальную область подключения и отмену старого задания; цикл не повышает старое поколение и не обещает сам проверить права или состояние беседы.

Для первой версии не принимаются описания инструментов, история tool и сообщения assistant с вызовами. Такой вход отклоняется до обращения к клиенту; дополнительные поля не могут включить инструментальный режим. tools клиенту не выдаются. Запрошенный подменой вызов завершается безопасным отказом без разбора аргументов и исполнения. Это осознанное ограничение первой версии из дорожной карты; полноценный инструментальный цикл этим планом не реализуется.

Конфигурация фиксируется при создании, вход — при запуске. Исходные объекты не меняются. Для каждой попытки используется независимое представление одного снимка: подмена клиента не может изменить историю следующей попытки. Не добавляются сообщения «продолжи», тексты ошибок или частичный ответ, не смешиваются данные параллельных запусков.

### Результаты запуска

Результат отдельно передаёт исход и безопасную сводку выполнения. Только complete содержит законченный ответ для дальнейшей отправки; отправитель в цикл не входит.

| Исход клиента или выполнения | Поведение цикла |
| --- | --- |
| complete с корректным непустым текстом | Возврат исходного текста без trim и переписывания; успех последней разрешённой попытки остаётся успехом |
| incomplete | Отдельный незавершённый исход с помеченным частичным текстом для вызывающего компонента; сам не публикуется и не продолжается автоматически |
| refused / empty | Отдельные конечные исходы без повторного обращения и без выдуманного ответа |
| tool_calls, в том числе с текстом | Неподдерживаемый инструментальный исход; сопутствующий текст и аргументы не становятся ответом, инструкции не исполняются |
| rate_limit | Отдельный конечный исход лимита провайдера, без автоповтора; решение о повторе остаётся будущей очереди |
| Безопасная ошибка клиента | Конечная фиксированная категория либо ограниченный повтор по правилам ниже; message клиента не копируется вслепую |
| Отказ Promise или неверная форма результата подмены | Фиксированная ошибка границы клиента без исходной диагностики; без повторов |
| Отмена / исчерпание общего времени | Отдельный конечный исход, прекращающий ожидание и будущие обращения |
| Исчерпание попыток шага перед повтором server | Отдельный исход лимита попыток с безопасной категорией последней ошибки; шаги при этом не увеличиваются |

Несмотря на TypeScript-контракт, возвращённая форма проверяется во время исполнения и проецируется в разрешённые поля. Неизвестный вариант или пустой complete не проходит как успех. Не возвращаются raw-объекты, reasoning_content и произвольная диагностическая строка клиента. Исходы не превращаются автоматически в тексты участникам: это обязанность будущей интеграции.

### Шаги, время и ограниченные повторы

Логический шаг и попытка обращения разделены. maxSteps сохраняет default 6 из спецификации и ограничивает логические шаги будущего агентного цикла. Отдельный maxAttemptsPerStep включает первую попытку и повторы одного шага. Повтор server не расходует следующий шаг и не обнуляет предел попыток. В первой версии без инструментов один запуск содержит только один логический шаг: после любого конечного исхода нет искусственного перехода к следующему. Достижимость maxSteps больше одного появится с будущим инструментальным циклом; сейчас она не имитируется ради теста.

Сводка считает начатые шаги, общее число начатых попыток и попытки каждого шага. Проверка ввода и предварительная отмена дают ноль шагов и попыток. Шаг начинается вместе с первой фактической попыткой; синхронный сбой подмены её учитывает. Успех последней разрешённой попытки остаётся успехом. Лимит попыток возвращается, только если следующий допустимый повтор уже невозможен. Значение maxAttemptsPerStep определяет план реализации; дополнительного бесконечного уровня повторов нет.

Автоповтор по умолчанию разрешён только для server в пределах попыток шага и общего срока. Его можно явно выключить доверенной конфигурацией. rate_limit возвращается отдельным конечным исходом без ожидания и повторного вызова; повтор при квотах — решение будущей очереди F2.3, проверяемое в F2.9. Сеть, таймаут отдельного клиента, отмена, постоянные ошибки, неизвестные отказы подмены и неподдерживаемые ответы автоматически не повторяются. Retry-After не выдумывается из отсутствующих метаданных текущего контракта.

Повтор server использует тот же снимок запроса после конечной отменяемой паузы. Даже server не доказывает отсутствие уже выполненной и оплаченной обработки; гарантии идемпотентности и отсутствия повторной оплаты нет. Клиент F2.1 остаётся однопопыточным. Очередь в дальнейшем не должна создавать второй независимый цикл server-повторов или сбрасывать бюджет исходного задания.

В проде выбор политики повторов и её пределов принадлежит владельцу бота, заданному BOT_OWNER_ID. Точка сборки приложения F3.4 передаёт утверждённую им инфраструктурную конфигурацию ядру; сейчас подключение к запуску не реализуется. Модель, текст участника, результат инструмента и обычный администратор беседы не выбирают и не расширяют политику. Первая версия предоставляет только явное отключение server-повторов; новые категории не включаются произвольным списком. Команды изменения политики и новая модель прав не добавляются.

Общий конечный срок охватывает все шаги, попытки и паузы и не продлевается при повторе. Его завершение отличается от timeout отдельного клиента. Отмена и общий срок прекращают ожидание даже при подмене, игнорирующей сигнал; сигнал передаётся клиенту, поздний ответ не доставляется повторно и не запускает новую попытку или шаг. Освобождаются собственные таймеры и слушатели. Уже отправленный запрос отменой не откатывается. Значения срока и паузы, сигнатуры и средства управляемого времени определяются планом реализации.

### Сводка выполнения и границы диагностики

Возвращаются число начатых шагов, число попыток по каждому шагу и всего, конечный исход, длительность и расход для будущего учёта. Для input/output независимо сохраняются сумма известных значений и число попыток с неизвестным расходом. При любом неизвестном слагаемом сумма известных токенов не выдаётся за полный расход. Неожиданный отказ, отменённый незавершённый вызов и ошибка без usage оставляют расход этой попытки неизвестным; нулевое число попыток отличается от неизвестного расхода состоявшейся попытки. Некорректные счётчики и переполнение не превращаются в достоверные суммы.

Сводка не содержит текстов, аргументов инструментов, сессии, ключей или исходных ошибок. Она не является долговечной трассировкой: запись и привязка к доверенной области запроса остаются F2.6 и вызывающей границе. Цикл не пишет запросы, ответы или диагностические подробности даже через debug. Отдельный механизм логирования ради этого компонента не вводится.

### Сообщение участнику или молчание

Уточнение 2026-11-22 по плану 013: таблицей «исход → сообщение или молчание» владеет F2.4/роутер, строки согласованы человеком 2026-11-22 в [таблице публикации](../specs/agent-loop.md#публикация-исхода-и-молчание). Наличие безопасного message в ошибке не означает разрешение его публиковать. Цикл возвращает исход без самостоятельной отправки и не принимает продуктовый режим как разрешение сообщить об ошибке.

Согласованное правило: в активном режиме ошибка не даёт сообщения. Оно фиксируется независимо от выбора ответственной границы и проверяется [оценочным сценарием](../specs/evals.md#ошибка-в-активном-режиме-не-даёт-сообщения). Правила для остальных исходов и режимов выбираются отдельно до интеграции F2.4/F4.7; этот вопрос не блокирует нейтральный цикл.

## Альтернативы и причина выбора

- Немедленно включить инструменты означало бы добавить реестр, авторизацию и непроверенную совместимость reasoning_content. Это расширяет утверждённый объём; первая версия явно отклоняет такие вызовы.
- Универсальные автоматические повторы для всех ошибок создают повторную оплату при неизвестном результате и маскируют постоянные сбои. Выбран явный узкий допуск и общий предел.
- Автоматически продолжать incomplete отдельным сообщением меняло бы историю и могло выдавать противоречивое продолжение. Частичный результат остаётся отдельным исходом для дальнейшего решения.
- Подключить HTTP-клиент и хранилище внутри цикла связало бы ядро с инфраструктурой и живым доступом. Внедрение нейтрального клиента даёт проверяемый каркас независимо от F2.9.

## Изменения спецификаций

После реализации и успешного review [агентный цикл](../specs/agent-loop.md) опишет реализованный режим без инструментов отдельно от целевого полного цикла: исходы, конечные попытки, общую длительность и явный допуск повторов. [Архитектура](../specs/architecture.md) уточнит фактического владельца повторов, внедрение клиента и отсутствие инфраструктурных зависимостей. [Контекст](../specs/context.md) уточнит неизменяемую границу уже подготовленного запроса; сборщик останется будущим.

[Безопасность](../specs/security.md) и [правила логов](../specs/commands-and-limits.md) при необходимости сошлются на отсутствие инструментальных разрешений и безопасную сводку. Готовность записи трассировок, отправителя или очереди не заявляется. В evals добавлен конкретный сценарий отсутствия сообщения при ошибке в активном режиме; применение к реальному пути публикации относится к интеграции роутера и отправителя. Подмена проверяет код, реальная модель — качество. Сейчас спецификации не переписываются под ещё не реализованное поведение.

## Влияние на контракты и данные

Появятся нейтральные контракт запуска и исходов в ядре, явная фабрика с клиентом и ограничениями, сводка выполнения. Точные имена, поля и размещение определит план реализации. Контракт F2.1, транспорт Go, конфигурация окружения, общий каталог и API хранения не меняются. БД, миграции, долговечное состояние, фоновые задания и новые зависимости не нужны: отдельный вызов сейчас не обещает продолжения после перезапуска процесса.

После реализации, успешного review и sync-specs F2.2 и задача 012 получают статус «реализовано на подменах, ожидает валидации». Это самостоятельный проверяемый результат разработки, который не требует закрытия отложенной F2.9. Задача и оба плана остаются в активных каталогах, дата окончательного завершения не проставляется; планы сохраняют утверждение и отмечают выполненные шаги. В completed документы переносятся вместе только после необходимой валидации и финальной синхронизации.

F2.9 обязательна до начала F5.6, а не до приёмки каркаса на подменах. Она проверяет условия, доступ, возможности модели и поведение при лимитах, включая возможность повторов будущей очередью. Перенос контрольной точки не разрешает реальные вызовы без отдельного согласования и не означает положительного ответа провайдера.

## Риски

- Внедрённая подмена может вернуть неверную форму, изменить вход или зависнуть. Нужны проверки формы, изолированных снимков, игнорирования отмены и поздних отказов без unhandled rejection.
- Несколько владельцев повторов создают лавину обращений. На этой стадии циклом управляет только ядро, а вызов F2.1 однопопыточный; будущая очередь должна сохранить общий предел задания.
- Неполная статистика может выглядеть как точный расход. Известные и неизвестные слагаемые показываются раздельно; сводка не даёт финансовой гарантии.
- Смена подключения или отзыв прав не проверяются самим циклом; нельзя выдавать его наличие за готовность сквозной авторизации или отмены заданий.
- Риск reasoning_content и применимость условий Go остаются в F2.9. Проверка на подменах не доказывает реальный инструментальный цикл и не снимает юридических вопросов.

## Допущения

Только подготовленная текстовая история user/assistant, без описаний и исполнения инструментов; один снимок на запуск; один владелец ограниченных повторов; никаких живых вызовов. Проверяются все исходы F2.1, лимиты и их границы, отмена при вызове и паузе, неизвестный usage, изоляция параллельных запусков, отсутствие утечек и побочных эффектов при импорте/создании. Сохраняются сборка, типы, линтер, платформенные границы и ESM; README отражает текущий объём.

## Открытые вопросы

Подход утверждён человеком с правками: раздельные шаги и попытки, автоповтор по умолчанию только server, отдельный rate_limit, новый промежуточный статус и контрольная точка F2.9 перед F5.6. Числа попыток шага, общего срока и паузы остаются плану реализации.

Ответственная граница таблицы — F2.4/роутер (уточнение 2026-11-22); строки согласованы человеком 2026-11-22 в [таблице публикации](../specs/agent-loop.md#публикация-исхода-и-молчание), локальная реализация выполнена F2.4 на подменах; реальная доставка остаётся F3.x. Обязательное правило активного режима уже согласовано. Подтверждение провайдера, реальные измерения и юридическое раскрытие остаются открытыми в F2.9; её результат обязателен до F5.6.
