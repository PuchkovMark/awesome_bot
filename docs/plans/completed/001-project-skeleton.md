## Подход и ключевые решения

### Исходное состояние и границы

В рабочем дереве отсутствуют исходники нового приложения, манифест зависимостей и конфигурация сборки. Создаётся самостоятельный скелет в корне репозитория. История старого бота и его архивы не используются как основа реализации и не изменяются.

Слои представлены каталогами исходников `core`, `channels`, `tools`, `storage` и `llm`. Их назначение документируется; минимальные пустые ESM-модули обозначают границы без введения контрактов или поведения последующих фич. Прикладная точка входа остаётся в F3.4.

### Среда и воспроизводимость

Базовая среда — Ubuntu 22.04.5 LTS (проверено 2026-11-21) и установленный Node.js 26 по сообщению пользователя. Прежние сведения об Ubuntu 18 устарели. Точная версия Node.js и npm фиксируется при реализации; используются одинаковые версии для установки, сборки и тестов. В оболочке агента при проверке команда `node` не найдена: перед выполнением команд требуется определить способ подключения уже установленного Node.js через `PATH` или менеджер версий.

Основной путь — локальные команды Node.js и npm. Docker остаётся необязательным запасным вариантом для изолированной среды при необходимости. При его использовании сохраняются права пользователя, а зависимости и результаты сборки остаются в пределах проекта или выделенных томов. Production-образ и развёртывание сюда не входят.

Используется один менеджер пакетов npm, lock-файл и установка через `npm ci`. Совместимые с Node.js 26 стабильные версии TypeScript, ESLint, typescript-eslint, Vitest и типов Node.js фиксируются при реализации вместе с lock-файлом. SDK VK, LLM и БД пока не устанавливаются. README описывает локальные npm-команды как основной путь разработки.

### TypeScript и ESM

Сборка выполняется TypeScript без бандлера: строгая проверка типов, `module` и `moduleResolution` — `NodeNext`, тип пакета — ESM. Исходники приложения отделены от результата сборки; тесты и конфигурация инструментов проходят проверку типов, но не попадают в выходные модули приложения. Выходной JavaScript проверяется загрузкой в Node.js, чтобы проверить реальную совместимость ESM помимо успешной компиляции. Выбор соответствует [документации TypeScript для Node.js](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options).

### Линтинг и запрет платформенных импортов

ESLint использует flat config и TypeScript-парсер. Отдельное локальное правило границ применяется ко всем вложенным исходникам `core` и `tools`. Запрещённые пакеты перечисляются в одном месте конфигурации: первоначально `vk-io`, при подключении очередной платформенной библиотеки список дополняется. Проверяются точное имя пакета и его подмодули; совпадение только по префиксу имени не запрещает посторонний пакет.

Правило разбирает статические импорты, импорты только типов, реэкспорты, TypeScript import-type, динамические импорты и вызовы `require` с известным именем модуля. Вычисляемая динамическая загрузка в защищённых слоях отклоняется, поскольку скрывает имя зависимости от статической проверки. Это ограничение способа проверки импортов, а не дополнительная матрица зависимостей слоёв. Новые запреты между остальными слоями не вводятся.

Использовать только стандартное `no-restricted-imports` недостаточно: [правило ESLint](https://eslint.org/docs/latest/rules/no-restricted-imports) охватывает статические импорты. Локальное правило позволяет одинаково проверять остальные формы. Оно контролирует прямые зависимости исходников; анализ транзитивного графа сторонних пакетов не входит в эту фичу. Независимость ядра сохраняется обязательным архитектурным правилом и при дальнейшем ревью.

Сборочная команда сначала выполняет линтинг, затем проверку типов и выпуск JavaScript. Поэтому нарушение границ блокирует сборку даже при корректных TypeScript-типах. Артефакты сборки и зависимости исключаются из Git и области линтинга. Некорректные примеры тестов не включаются в обычную компиляцию приложения.

### Проверка критериев приёмки

Vitest проверяет настоящую ESLint-конфигурацию через API ESLint на виртуальных исходниках с путями защищённых слоёв и адаптеров. Матрица включает допустимый нейтральный импорт, корень пакета и подмодуль, вложенные каталоги, импорт только типов, реэкспорт, динамический импорт и вычисляемую загрузку. Отдельный пример добавленного платформенного пакета подтверждает расширяемость списка без реализации второй платформы.

Интеграционная проверка на временной копии скелета подтверждает, что разрешённый проект собирается, а запрещённый импорт приводит к ненулевому коду команды сборки именно из-за линтера. Исходное дерево не изменяется. Проверки не загружают SDK и не требуют сети после установки зависимостей. Проверка загрузки выходного ESM-модуля выполняется без запуска приложения.

README описывает существующий набор возможностей, назначение слоёв и команды установки, линтинга, проверки типов, тестов и сборки. Сборка скелета не обозначается как запуск работающего бота.

## Альтернативы и причина выбора

- Бандлер и режим `bundler` добавляют преобразование модулей, которое серверному скелету пока не нужно. Выбран обычный выпуск JavaScript с проверкой правил Node.js.
- Только встроенное правило ограничения импортов проще, но оставляет динамическую загрузку за пределами проверки. Выбрано небольшое локальное правило с тестами реальной конфигурации.
- Полноценный анализатор графа зависимостей мог бы выявлять транзитивные зависимости, но требует дополнительных правил и инструментария. Для F1.1 выбран прямой запрет платформенных импортов, заданный архитектурой.
- Обязательная разработка через Docker не требуется: актуальный хост и установленный Node.js позволяют выбрать локальный запуск. Контейнер остаётся запасным вариантом.
- Прямое выполнение TypeScript средствами Node.js не заменяет обязательную строгую проверку типов и сборку в этой задаче; отдельный загрузчик TypeScript не нужен.

## Изменения спецификаций

В рамках этого плана спецификации и статусы фич не изменяются.

## Влияние на контракты и данные

Прикладных контрактов и моделей данных пока нет. Схема БД, сообщения, поведение бота, промпты и персонажи не меняются. Перенос данных, evals на реальной модели и ключи внешних сервисов не требуются.

## Риски

- Версии инструментов могут оказаться несовместимыми с Node.js 26. При реализации фиксируется проверенный набор; критерий — чистая установка и прохождение сборки и тестов в одной среде.
- При добавлении нового платформенного SDK необходимо дополнить список запретов; это отмечается в описании слоёв и проверяется ревью.
- AST-формы TypeScript могут отличаться от JavaScript. Тесты используют тот же парсер и конфигурацию, что и реальные исходники.
- Проверка только через Vitest может скрыть ошибки разрешения ESM. Дополнительно проверяется загрузка скомпилированного модуля самим Node.js.
- Оболочка агента может не наследовать настройки установленного Node.js. Перед реализацией проверяется его подключение; отсутствие команды в `PATH` не означает отсутствие установки на хосте.
