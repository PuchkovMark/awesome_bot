## Подход и ключевые решения

- Штатный сервис публикации сохраняет право выбора реакции, ограничения служебных уведомлений и проверки перед отправкой. Отправитель VK получает текст, исходную область, необязательный ID reply и сигнал отмены через платформенно-независимый порт. Доверенная проверка актуальности применяется после ожидания лимитера, непосредственно перед отправкой каждой части и каждым повтором. Она учитывает смену поколения и паузу с продолжением того же поколения. Вызов, уже начатый до отмены, может завершиться на стороне VK.
- Адаптер форматирует нейтральный текст для VK и затем делит его по границам абзацев и предложений. Если подходящей границы в пределах лимита нет, используются безопасные границы Unicode. Порядок и содержание форматированного текста сохраняются. Reply к исходному сообщению получает только первая часть длинного ответа. Служебное уведомление остаётся единичным reply с действующим периодом на чат. Индикатор набора использует `messages.setActivity` в области того же чата. Его отказ учитывается отдельно от результата сообщения. [Схема индикатора VK](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/messages/methods.json#L2575)
- Отправитель адресует `messages.send` одному `peer_id` сообщества, даже когда формат запроса поддерживает список адресатов. Кандидат для проверки — `peer_ids` с одним адресатом, поскольку публичная схема этой формы возвращает `peer_id` и `conversation_message_id`. Reply проверяется в пределах этого `peer_id`; кандидат для отправки — `forward` с локальным номером и `is_reply`. VK проверяется на совпадение адресата и локального ID. Время, автор, фактический текст и связь reply берутся из подтверждённого сообщения в этой же области. За основу берётся уже используемый в F3.1 `messages.getByConversationMessageId`. [Отправка VK](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/messages/methods.json#L2247) · [Форма результата VK](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/messages/objects.json#L1948) · [Параметры reply](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/messages/objects.json#L945)
- Приёмное обогащение, отправка, подтверждение доставки и индикатор используют один лимитер VK API для сообщества. Каждый фактический вызов проходит через этот лимитер. Запросы `a_check` идут по отдельному протоколу Bots Long Poll. Политика ограниченных повторов принадлежит адаптеру. Транспорт VK API делает одну попытку за вызов, чтобы скрытые повторы SDK не обходили срок и проверку актуальности. Технический ориентир — 20 запросов в секунду на сообщество. [Рабочий цикл `vk-io`](https://github.com/negezor/vk-io/blob/cc2bbd7/packages/vk-io/src/api/workers/sequential.ts)
- Для каждого логического сообщения выбирается отдельный случайный `random_id`; повтор части сохраняет то же значение. Повторы с экспоненциальной паузой разрешены в границах срока задания и для исходов, безопасных для повтора. Если VK мог принять сообщение, повтор отправки допустим только в пределах подтверждённой семантики дедупликации. При известном приёме сообщения повторяется только запрос подтверждения. Отказ и неизвестный исход останавливают отправку оставшихся частей.
- Подтверждённая часть передаётся доверенному сервису публикации сразу, до отправки следующей. Он проверяет исходную область и записывает фактическую часть в штатный журнал. Результат всей публикации учитывает число подтверждённых частей и статус остатка. При частичной доставке существующие записи остаются в журнале. Отдельные код и счётчик отражают частичный либо неизвестный исход без текста ответа и сырой ошибки. Для повторной постановки всего ответа основания по-прежнему определяет штатная политика публикации.

## Альтернативы и причина выбора

- Ответ VK на `peer_id` одиночным числом проще получить. В предыдущей проверке эта форма создала сообщение в беседе, но проба не получила из результата пригодное подтверждение локального ID. Форма с одним `peer_ids` и сверка по локальному номеру позволяют проверить адресата и получить поля, нужные журналу. Её поддержку на групповом ключе ещё нужно подтвердить. [Наблюдения в Test Bot](../../research/vk-lifecycle-capabilities.md#упоминание-ответ-сообществу-и-вложение) · [Две формы результата `messages.send`](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/messages/responses.json#L965)
- Передача частей одним итоговым результатом упрощает порт. Поочерёдное подтверждение позволяет записать уже доставленные части до таймаута, отказа или изменения подключения между отправками. Журнал остаётся в доверенном сервисе публикации.
- Reply у каждой части даёт ссылку на исходное сообщение при чтении отдельно. Выбран reply у первой части. Он связывает ответ с обращением и убирает повторяющиеся цитаты у продолжения.

## Влияние на контракты и данные

- Нейтральный `OutgoingMessage` сохраняет `chatId`, текст и необязательный `replyToMessageId`. Доверенный порт публикации расширяется подтверждением отдельной части и результатом полной либо неполной отправки. Совместимость действующих вызывающих путей и подмен проверяется отдельно. Платформенные поля, `random_id` и сырые ошибки остаются в адаптере.
- Каждая подтверждённая часть соответствует одной существующей записи журнала. Используются фактические ID, составной ID сообщества, текст, время UTC и подтверждённый ID исходного сообщения для связанной части. Служебное уведомление сохраняет свою отметку и исключение из контекста. Для такой записи достаточно существующей схемы SQLite.
- Сохраняются договорённости о роли, паузе F1.6b и допустимых реакциях F2.4. Для диагностики используются ограниченные статусы и счётчики. Ранее сохранённые трассы остаются читаемыми.

## Риски

- Публичная схема API 5.199 содержит `maxLength: 9000`, а проектный ориентир — около 4000 символов. Срез схемы сам по себе не устанавливает фактический лимит сервера или единицу измерения. Рабочая граница и Unicode проверяются до выбора значения, которое объявит адаптер. [Схема `messages.send`](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/messages/methods.json#L2247)
- После таймаута VK может принять часть позже. Одного `random_id` недостаточно для вывода о судьбе запроса. До проверки поведения VK при неоднозначном исходе он остаётся неизвестным. Между внешней доставкой и записью журнала остаётся риск прерывания.
- Отказ доступа к reply и отсутствие сведений о нём отличаются от успешной отправки. Для обычного ответа возможность отправки без reply определяется существующей политикой до первого запроса. Служебное уведомление требует подтверждённой возможности reply.

## Допущения

- Один экземпляр приёмника и отправителя для одного сообщества использует общий клиент и лимитер. Полная композиция и штатный запуск приложения относятся к F3.4.
- Локальная приёмка использует подмену VK и штатные роутер и SQLite. Проверка реальных форм VK проводится в согласованном тестовом сообществе на синтетических сообщениях. Ручная проверка ответов модели относится к F3.5.

## Подтверждённые формы и ограничения

Подтверждены `peer_ids` с одним адресатом, `forward.is_reply` и получение частей по локальному ID. Выбран проверенный предел 4000 байт UTF-8. Для отправки повторяется только явный отказ VK по частоте, для принятой части допускается повтор чтения подтверждения. При неоднозначном результате фиксируется `unknown`. В Test Bot индикатор набора вернул `10`. [Протокол](../../research/vk-outbound-capabilities.md)
