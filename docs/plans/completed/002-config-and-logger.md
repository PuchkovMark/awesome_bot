## Подход и ключевые решения

### Исходное состояние и границы

В проекте есть пустые ESM-модули пяти слоёв и проверки F1.1. Конфигурации приложения, логгера, SDK и прикладной точки входа нет. В F1.2 создаются независимые инфраструктурные компоненты конфигурации и логирования. Их импорт не читает `.env`, не меняет окружение и не пишет в вывод; работа начинается только при явном вызове. Ядро и инструменты не получают платформенных зависимостей.

Компоненты проверяются через вызываемые функции и тестовую композицию. Запуск бота и реальная интеграция с точкой входа остаются в F3.4. Необходимые для будущих компонентов секреты проверяются локально, без проверки действительности в VK или OPENCODE.

По прямому уточнению пользователя провайдер — OPENCODE, основная модель — `deepseek-v4.1-flash`. Прежнее предложение использовать Anthropic отменено. Для F1.2 предлагается ключ прямого API провайдера в `OPENCODE_API_KEY`; выбор конкретного endpoint и клиентской библиотеки относится к F2.1. SDK Anthropic не требуется. Наличие модели в опубликованном списке провайдера проверяется по [официальной документации OPENCODE](https://opencode.ai/docs/console/models/), но сетевой вызов модели в эту задачу не входит.

### Начальный набор конфигурации

| Переменная | Назначение | Обязательность и проверка | Секретность и значение по умолчанию |
| --- | --- | --- | --- |
| `VK_TOKEN` | Токен сообщества для будущего VK-адаптера | Обязательная непустая строка; пробелы по краям и переводы строк отклоняются | Секрет; значения по умолчанию нет |
| `OPENCODE_API_KEY` | Ключ OPENCODE для будущего клиента модели | Обязательная непустая строка; пробелы по краям и переводы строк отклоняются | Секрет; значения по умолчанию нет |
| `LLM_MODEL` | Идентификатор основной модели; в примере окружения — `deepseek-v4.1-flash` по выбору пользователя | Обязательная непустая строка без пробелов по краям и переводов строк; существование модели по сети не проверяется | Несекретный параметр, но автоматически в логи не выводится; значения по умолчанию нет |
| `LOG_LEVEL` | Минимальный уровень логирования | Одно из `debug`, `info`, `warn`, `error`, `fatal`, `silent`; регистр значим | Несекретный; `info`, только если переменная отсутствует |

Пустая или состоящая из пробелов строка не заменяется значением по умолчанию. Токены не проверяются по предполагаемому формату провайдера и не обрезаются молча. Прочие переменные системного окружения допускаются и не переносятся в объект конфигурации. Провайдер в текущем конфиге фиксируется как `opencode`; выбор среди нескольких провайдеров не реализуется заранее. Старый параметр `ANTHROPIC_API_KEY` не является заменой `OPENCODE_API_KEY`. Набор намеренно ограничен текущей задачей: параметры БД, второй модели, ролей, таймзон, сроков, лимитов и бюджетов добавляются в соответствующих фичах. Имена в таблице — предлагаемый контракт F1.2, а не перенос настроек старого бота.

### Загрузка и валидация

Поддержка `.env` использует `util.parseEnv` установленного Node.js 26, без отдельного dotenv-пакета. Парсер возвращает объект и позволяет объединять данные без изменения `process.env`; формат определяется [документацией Node.js](https://nodejs.org/api/environment_variables.html) и [API parseEnv](https://nodejs.org/api/util.html#utilparseenvcontent). Подстановки `${VAR}`, запуск команд и собственный расширенный синтаксис не добавляются.

Приоритет: явно переданное окружение процесса выше значений `.env`, затем применяются предусмотренные таблицей значения по умолчанию. Наличие переменной с пустым значением в окружении перекрывает файл и приводит к ошибке, а не к возврату к файловому значению. По умолчанию читается один `.env` из заданного рабочего каталога; отсутствие этого необязательного файла допускается, если окружение полно. Если вызывающий явно указал другой файл и он отсутствует, загрузка завершается ошибкой. Ошибка чтения существующего файла также не игнорируется.

Валидация возвращает типизированный неизменяемый конфиг либо отдельную ошибку с кодом причины и именами известных параметров. Имена неизвестных переменных, исходные значения, содержимое файла и исходные ошибки чтения не включаются в пользовательскую диагностику и `cause`. Для четырёх параметров достаточно явной проверки без дополнительной библиотеки схем. Некорректный конфиг не возвращается частично; будущая точка входа обязана вызвать загрузку до создания зависимых компонентов.

### Логирование и разделение данных

Вывод — структурированные JSON-строки в stdout через Pino. Подбирается совместимая стабильная версия, закрепляемая при реализации. Время записывается как UTC unix ms. Базовый уровень `info`; `silent` отключает вывод. Назначение файла, ротация, транспорт во внешние системы и глобальная обработка исключений процесса в эту фичу не входят.

Компонентам выдаётся ограниченный интерфейс логгера; экземпляр Pino не экспортируется. Он принимает коды событий и проверяемые поля, а не произвольные форматные строки, объекты запроса, конфиги или SDK-ответы. Начальные события — успешная загрузка конфигурации, ошибка конфигурации, ошибка компонента и отладочный текст. Для обычных событий используются фиксированные описания и поля: известные имена параметров, перечислимые коды причин и категорий ошибок. Неизвестные поля не выводятся. Типизация дополняется проверкой во время выполнения, чтобы приведение типов не позволяло обойти ограничения.

Исходные `Error.message`, `stack`, `cause`, вложенные объекты и пользовательские поля ошибки на обычных уровнях не сериализуются: они могут содержать текст сообщения человека и секреты. Ошибка классифицируется в ограниченный набор категорий, включая «неизвестная ошибка»; строка `error.name` не считается доверенной категорией без проверки. Ошибки конфигурации уже содержат только безопасные коды и известные имена параметров, поэтому могут быть записаны до создания полного логгера отдельным минимальным диагностическим вызовом без исходного окружения.

Отдельный метод отладочного текста всегда создаёт запись уровня `debug`. Он предназначен для текстов сообщений и диагностических подробностей ошибок; при более высоком пороге эти данные не попадают в вывод. Передаваемые подробности ошибки проходят контролируемое преобразование: допускаются только её текстовые диагностические поля, без произвольных объектов и вызова их пользовательских сериализаторов. Включение отладки не разрешает вывод секретов.

### Защита секретов и её границы

Логгер получает значения секретных параметров из конфигурации и убирает их точные вхождения из всех допускаемых строк, включая отладочный текст и диагностические подробности ошибок, до записи в Pino. Учитываются также секретные значения из обоих источников, перекрытые при объединении окружения и `.env`, если они доступны загрузчику. Это внутренний набор для очистки, который не входит в вывод и не передаётся бизнес-компонентам как метаданные. Для ошибки загрузки до получения набора секретов доступны только фиксированные безопасные диагностические поля.

Защита не сводится к списку путей Pino: произвольные объекты не принимаются, а чувствительные поля удаляются на входной границе. Встроенная [редакция полей Pino](https://github.com/pinojs/pino/blob/main/docs/redaction.md) может использоваться дополнительно для известных полей; она сама по себе не очищает секрет, вставленный в строку под другим именем. Пользовательские serializers и прямой доступ к Pino не выдаются.

Граница гарантии — известные приложению секреты, переданные через его конфигурацию или явно зарегистрированные при создании логгера, и предусмотренные поля событий. Любой новый источник секретов должен передать их в этот набор до логирования. Автоматическое распознавание неизвестного ключа внутри произвольного текста, а также декодирование base64/URL и иных преобразований не обещаются. Вывод конфигов, HTTP-заголовков и произвольных объектов запрещён контрактом логгера, даже если вызывающий рассчитывает на очистку.

### Проверка и документация

Тесты используют явные словари окружения, временные `.env` и перехватываемый поток вывода. Они не читают реальный файл пользователя, не зависят от его ключей и не меняют глобальный `process.env`. В тестах проверяются приоритет источников, пустые и некорректные значения, отсутствие/недоступность файла, отсутствие побочных эффектов импорта и безопасная диагностика.

Логи проверяются по фактически записанным JSON-строкам: уровни и `silent`, отсутствие человеческого текста на обычных уровнях даже внутри ошибок, отладочный текст только на `debug`, удаление известных секретов из строк и ошибок, отказ от неизвестных структурированных полей и отсутствие утечек перекрытых секретов. Тестовая композиция доказывает, что при ошибке конфигурации зависимые компоненты не создаются. Реальные SDK не подключаются. Существующие проверки F1.1, сборка, типы и линтинг остаются обязательными.

README и пример `.env` описывают четыре параметра, приоритет источников, уровни, безопасные методы логирования и ограничения очистки. Пример содержит заполнители вместо настоящих секретов. Результат F1.2 не обозначается как работающий бот.

## Альтернативы и причина выбора

- dotenv-пакет не нужен при выбранной среде: встроенный парсер Node.js поддерживает требуемый формат. Явное объединение словарей выбрано вместо глобальной загрузки в `process.env` ради изоляции компонентов и тестов.
- Библиотека схем полезна при большом конфиге; сейчас четыре параметра проверяются явно. Это не закрепляет запрет на библиотеку в будущих фичах.
- Обычный `console` и собственная реализация транспорта потребовали бы поддержки структуры записей и уровней. Выбран Pino за ограниченным интерфейсом; точная версия фиксируется после проверки совместимости.
- Один только список чувствительных ключей не защищает строковые ошибки и произвольные имена полей. Выбраны ограниченный набор событий, отдельный отладочный канал и очистка известных секретов.
- Свободная запись `Error` удобнее для диагностики, но может раскрыть текст человека на уровне `error`. Вместо этого обычные события содержат безопасную классификацию; подробности доступны только через отладочный метод.

## Влияние на контракты и данные

Появляются внутренние контракты конфигурации и логгера. Контракты сообщений/адаптеров F1.3, модель данных и БД не меняются. Конфиг и логгер не требуют долговечного состояния. Секреты остаются только в окружении и памяти процесса; в примеры и журналы они не записываются. Выбор OPENCODE и `deepseek-v4.1-flash` фиксирует целевое подключение; работающего LLM-клиента ещё нет, фактического переключения и вызовов не выполняется. Оценочный прогон реального поведения потребуется при подключении модели с доступным каркасом evals; обычные тесты используют подмены.

## Риски

- Полезность обычного отчёта об ошибке ограничена безопасными категориями. Подробнее диагностировать можно при явном включении `debug`; будущие события расширяются вместе с использующими их фичами.
- Очистка известных строк не распознаёт неизвестные или преобразованные секреты. Ограниченный интерфейс и обязательная регистрация новых секретов — часть контракта, а не обещание универсального фильтра.
- Поддержка `.env` следует синтаксису Node.js; ожидающие расширений dotenv пользователи должны увидеть это в README.
- Ошибки чтения и валидации возникают раньше полной конфигурации логгера. Минимальный диагностический путь обязан оставаться безопасным без набора секретов.

## Допущения

Провайдер OPENCODE и основная модель `deepseek-v4.1-flash` выбраны пользователем. Предлагаемые технические решения ожидают утверждения вместе с планом: четыре начальных параметра и их имена, прямой API с ключом `OPENCODE_API_KEY`, приоритет окружения над `.env`, `info` по умолчанию, Pino с JSON в stdout, явные вызовы без побочных эффектов импорта, ограниченный контракт логирования и отдельный отладочный метод. Они не утверждают открытые настройки поведения бота, ролей, лимитов или хранения.

## Открытые вопросы

Блокирующих вопросов нет. Выбор точной совместимой версии Pino и конкретных типов внутренних интерфейсов относится к плану реализации и проверке при установке. План не предусматривает запуск бота или работу с настоящими ключами.
