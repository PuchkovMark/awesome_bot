## Подход и ключевые решения

- Один стартовый набор хранит стабильные идентификаторы сценариев, ревизии, исходное синтетическое состояние, вход, наблюдаемые критерии и шаги для ручной проверки в VK. В него входят согласованные случаи F2.7 для текущего сообщения, имени, истории и цитаты, нейтральные контрольные случаи и ограниченная история с проверкой честности ответа. Изменение смысла сценария или критерия отражается в его ревизии. Сценарии будущих функций добавляются при подключении этих функций.
- Локальный запуск `npm run eval:local` готовит изолированную синтетическую беседу на сценарий и использует штатный путь от роутера через очередь и сборку контекста до подмены клиента. При проверке пользовательского ответа используется штатная политика публикации и подмена отправителя. Каждая подмена возвращает заданный результат, а проверки смотрят на фактический снимок запроса и наблюдаемый исход. Набор воспроизводит прохождение критерия, его нарушение и технический сбой. Для обычных тестов тот же каркас доступен с подменами.
- Автоматические критерии проверяют наблюдаемые признаки с однозначной трактовкой: наличие или отсутствие синтетического маркера, роль, исход и факт публикации. Смысловые критерии для реальной модели описываются в сценарии через конкретные факты и утверждения, которые оператор отмечает вручную. Например, в сценарии неполной истории фиксируется, утверждал ли бот, что видел весь разговор. Для повторов каждого сценария фиксируется отдельный результат. Число повторов и порог прохождения реальной оценки утверждаются перед F3.5.
- Локальный запуск пишет JSON-отчёт в явно указанный файл. Отчёт содержит версию формата, UTC-время, вид запуска, идентификатор и ревизию сценария, модель, точную версию промпта из использованного снимка при наличии и версию персонажа при её использовании. По каждому критерию сохраняется результат и краткое структурированное основание. Итоги различают прохождение, нарушение критерия и технический сбой. Полный контекст, исходные ошибки, секреты и данные реальных бесед в отчёт не входят. Отчёты хранятся локально под управлением оператора, который удаляет их по завершении сравнения. Путь выбирает оператор, результаты остаются вне отслеживаемых артефактов репозитория.
- Для F3.5 тот же набор задаёт шаги в личке или беседе тестового сообщества и поля для ручной записи результата. Отчёт ручной проверки содержит те же ключи сравнения и явно указывает VK как источник наблюдения. Сценарий, для которого ещё нельзя воспроизвести исходное состояние или наблюдать критерий, помечается как непроверенный с причиной. Проверка в VK проводится после подключения бота и разрешённой проверки провайдера. Локальная приёмка F2.8 завершается по результатам подмен и готовности сценариев к ручной проверке.

## Альтернативы и причина выбора

- Обычные тесты подходят для регрессий кода. Отдельный запуск нужен оператору для воспроизводимого сценарного отчёта, а общий набор связывает его с будущей проверкой через VK.
- Простая проверка текстовых маркеров даёт однозначный результат для точных условий. Для смысловых условий выбрана ручная оценка по проверяемым признакам, поскольку один и тот же факт может быть выражен разными словами.
- JSON-файл подходит для сравнения версий и чтения инструментами. Сохранение в рабочем SQLite связало бы экспериментальные прогоны со схемой и сроками хранения данных бота.

## Изменения спецификаций

После локальной приёмки уточнить в [evals](../../specs/evals.md) состав стартового набора, команду, форму отчёта и различия в источниках наблюдения. Ручная проверка в VK остаётся частью F3.5, её результаты будут фиксироваться после фактического прогона. Условия приёмки F2.7 определены её [планом реализации](../../impl-plans/completed/018-untrusted-context.md#4-оценка-модели-и-окончательная-синхронизация).

## Влияние на контракты и данные

Новые форматы относятся к синтетическим сценариям и внешнему файлу отчёта. Каркас использует существующие контракты маршрутизации, сборки контекста, клиента и публикации. У каждой локальной проверки своё временное состояние. Рабочие записи бота, настройки и промпты остаются вне этого прогона.

## Риски

- Успех локального прогона измеряет работу каркаса и наблюдаемые свойства штатного пути. В отчёте указан вид запуска, чтобы результаты подмен не учитывались при оценке качества модели.
- Ручной прогон зависит от воспроизводимости состояния беседы и доступности наблюдений в VK. Чек-лист указывает для каждого сценария, что подготовить, что увидеть в интерфейсе и какой исход отметить при недоступной проверке.
- Сравнение разных ревизий сценария может измерять разные условия. Отчёт связывает результат с ревизией сценария и версиями модели и контекста.

## Допущения

- Для технической приёмки достаточно синтетических локальных сценариев с предопределёнными ответами и ошибками. Вызовы реальной модели относятся к функциональной проверке через VK.
- Локальные отчёты содержат только синтетические метаданные и итоги критериев. Удаление по окончании сравнения выполняет оператор.

## Открытые вопросы

Команда `npm run eval:local`, локальный JSON-отчёт и ручная оценка смысловых критериев в VK утверждены. Модель реального прогона, число повторов, пороги и бюджет согласуются перед F3.5.
