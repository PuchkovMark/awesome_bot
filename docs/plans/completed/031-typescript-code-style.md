## Подход и ключевые решения

Короткие правила и воспроизводимый формат сначала проверяются на конфигурации приложения и её тестах. Относительные пути к локальным TypeScript-модулям пишутся без расширения. Сборка выпускает ESM с путями, которые Node.js разрешает при прямом запуске. Этот переход проверяется до распространения на проект.

Форматирование охватывает поддерживаемые исходники, тесты, скрипты и корневые конфигурации ESLint и Vitest. Изменения группируются по каталогам. Отдельное изменение сборщика контекста показывает применение правил именования и явный порядок операций. Заключительная проверка формата входит в штатную сборку.

## Альтернативы и причина выбора

Одновременное изменение сборки, форматирования и логики затрудняет поиск причины регрессии. Раздельные изменения позволяют проверить загрузку модулей, затем единый формат и отдельно поведение сборщика. Prettier отвечает за воспроизводимое оформление, действующие проверки ESLint и архитектурных границ сохраняют свои задачи.

## Влияние на спецификации, контракты и данные

При завершении обновить правила разработки и описание фактического выпуска ESM в архитектуре. Сохраняются внешние контракты, данные и содержимое выпущенных миграций.

## Риски и допущения

Проверка типов и Vitest могут пройти при ошибке в путях собранного JavaScript. Для приёмки требуется прямой запуск Node.js. Исполняемые скрипты MJS сохраняют полные относительные пути. До правок сборщика контекста фиксируется исходный замер [задачи 032](../../tasks/completed/032-context-preparation-latency.md).
