# Хранилище

SQLite через `better-sqlite3` 13.2.0, типы `@types/better-sqlite3` 9.6.0, полнотекстовый индекс FTS5. Драйвер и SQL изолированы внутри слоя хранения; последующая замена на Postgres требует реализации нейтрального интерфейса и собственных миграций. В F1.4 реализованы журнал, настройки и миграции; остальные перечисленные ниже сущности остаются будущими фичами.

## Модель данных

| Таблица | Поля |
| --- | --- |
| `messages` | Внутренний id, chatId, платформенный id сообщения, userId, имя автора, роль user/assistant, текст, id сообщения-родителя, время UTC |
| `chats` | chatId, название, индивидуальный системный промпт, режим ответа «всегда»/«по упоминанию или reply», таймзона (по умолчанию Europe/Moscow), включён ли бот, дата создания |
| `summaries` (F6.4) | chatId, начало и конец периода, уровень «кусок»/«день»/«скользящее», текст, диапазон id исходных сообщений |
| `memories` (F6.5) | chatId, необязательный userId, факт, источник, время обновления |

Идентификаторы, формат времени и изоляция запросов — в [архитектуре](architecture.md). Порядок создания настроек чата — там же.

## Ограничения и индексы

Физическая `messages` содержит `id INTEGER PRIMARY KEY AUTOINCREMENT`, `chat_id`, `platform_message_id`, `user_id`, `author_name`, `role`, `text`, nullable `reply_to_message_id`, `timestamp`. Основная таблица — STRICT; поля обязательны, кроме reply-id, роли ограничены `user/assistant`, время — неотрицательное безопасное целое UTC unix ms. Платформенные id строковые, без числового преобразования. Уникальность пары `(chat_id, platform_message_id)` обеспечивает дедупликацию на уровне БД; индекс `messages_chat_time` имеет порядок `(chat_id, timestamp, id)`.

Журнал не требует существующей строки `chats` или участника: запись входящего сообщения предшествует созданию настроек по [архитектуре](architecture.md#сквозная-обработка). Reply-id не требует наличия исходного сообщения. Входная граница проверяет непустые части составных id и совпадение платформы автора и чата; это не заменяет аутентификацию и права.

`messages_fts` использует внешнее содержимое `messages` и связь по внутреннему id. Триггеры поддерживают вставку, обновление и удаление; миграция строит индекс ранее существующих строк. Публичного изменения/удаления журнала и FTS-поиска в F1.4 нет. В F6.3 выдача поиска должна соединяться с журналом и фильтроваться по `chatId`; фильтрация шума и инструменты поиска ещё не реализованы.

## Миграции и хранение

Явный `openStorage(path)` из [модуля хранения](../../src/storage/index.ts) принимает абсолютный путь с уже существующим родительским каталогом либо явный `:memory:`. Путь обязателен, нет автоматического выбора файла и переменной `DB_PATH`. Импорт не загружает нативный драйвер, не открывает БД, не читает окружение и не выводит сообщения. Открытие и операции возвращают Promise, но SQLite внутри выполняется синхронно; это не неблокирующий ввод-вывод.

Миграции применяются автоматически при открытии; подключение этого открытия к запуску приложения остаётся F3.4. Набор встроен в ESM-выпуск и не требует дерева исходников или внешних SQL-файлов. `schema_migrations` хранит последовательные версии, имена и SHA-256 SQL. Подтверждённая история должна совпадать с известным префиксом: неизвестная версия, пропуск, изменённое имя или содержимое отклоняются. Непустая посторонняя БД без метаданных не меняется и не переносится автоматически.

Проверка истории, создание метаданных и весь недостающий набор выполняются одной транзакцией записи. При ошибке изменения этого открытия откатываются, соединение закрывается, готовое хранилище не возвращается. Версия 1 создаёт журнал и настройки, версия 2 — FTS и триггеры с построением индекса существующих сообщений. Режимы нескольких процессов и WAL отдельно не настраиваются.

Закрытие явно и повторно безопасно; последующие операции отклоняются с кодом `closed`. Публичные ошибки имеют фиксированные коды `invalid_input`, `unavailable`, `schema_incompatible`, `migration_failed`, `operation_failed`, `closed`, без исходного SQL, текста, пути, stack/cause драйвера. Сам слой хранения ничего не логирует; диагностика вызывающего компонента подчиняется [правилам логов](commands-and-limits.md#хранение-и-логи).

Срок хранения и очистка — в [командах и лимитах](commands-and-limits.md); они не реализованы одной схемой БД. Правила исключения шума из поиска при сохранении в журнале — в [контексте](context.md).

## Операции журнала

`messages.append` принимает нейтральную запись: `chatId`, `messageId`, `userId`, `authorName`, `role`, `text`, необязательный `replyToMessageId`, `timestamp`. Результат содержит `status: inserted | duplicate` и внутренний `id` сохранённой строки. Подавляется только конфликт уникальной пары; остальные нарушения — ошибки. Дубликат даже с изменённым текстом не заменяет строку и не индексируется повторно. Непустые имя и текст не требуются; строки сохраняются буквально, SQL параметризован. Дополнительные признаки событий и вложения F1.3 в эту схему не сериализуются.

Входящее сообщение записывается с ролью `user`, ответ — `assistant` с известным составным id аккаунта бота, фактическим id сообщения и временем. Одна запись соответствует одному платформенному сообщению. Для частей длинного ответа нужны собственные тексты и id; текущий результат адаптера F1.3 содержит только id, получение остальных данных относится к согласованной интеграции F3.2. Хранилище не дублирует полный текст для каждого id и не объявляет поток отправки готовым.

`messages.list(chatId, query)` требует область чата и положительный безопасный целочисленный `limit`; необязательные `from/to` задают UTC ms интервал `[from, to)`, при двух границах обязательно `from < to`. Выбирается последнее подходящее окно по `(timestamp, id)`, наружу возвращается по возрастанию этой пары. Результат ограничен и не объявляется полным журналом периода. Неограниченного, межчатового чтения и чтения только по внутреннему id нет; потолки инструментов относятся к F6.3.

## Настройки чатов

Физическая STRICT-таблица `chats` содержит первичный ключ `chat_id`, nullable `title` и `system_prompt`, `response_mode`, `timezone`, `enabled`, `created_at`. Режим — `always/mention`, включение — 0/1, время создания — UTC unix ms. Режим и включение не имеют SQL- или прикладного default; семантика роутера остаётся [архитектуре](architecture.md).

`chats.get(chatId)` возвращает настройки или `null`. `chats.create(chatId, input)` требует явных `responseMode`, `enabled`, `createdAt`; отсутствие названия/промпта означает `null`, таймзоны — `Europe/Moscow`. Таймзона проверяется через `Intl`. Результат содержит `status: created | existing` и настройки. Повторное создание возвращает сохранённую строку, не меняя данные и дату; некорректный ввод отклоняется и при существующем чате.

`chats.update(chatId, patch)` частично меняет только название, промпт, режим, включение и таймзону. Неуказанное поле сохраняется, явный `null` сбрасывает название или промпт; пустой patch, неизвестные поля, изменение id/даты и некорректные типы запрещены. Отсутствующая строка возвращает `null`, update не создаёт чат. Все операции настроек требуют область чата. Выбор начальной продуктовой политики остаётся интеграции и не выводится из возможности хранения.

## Новые сущности и связи

Это логические сущности; имена таблиц и не заданные поля предстоит выбрать в плане.

| Сущность | Данные и связи |
| --- | --- |
| Участник беседы | Связь человека и chatId, дата вступления, роль, статус, активность; модель закладывается сразу в F1.5 |
| Профиль | Принадлежит участнику конкретной беседы; модель закладывается сразу в F1.5 |
| Факт профиля | Принадлежит профилю; значение, источник и признак надёжности; видимость задаётся для каждого поля |
| Паспорт беседы | Принадлежит chatId; тема, правила, традиции, глоссарий, важные события |
| Персонаж | Имя, стиль, ограничения манеры, примеры реплик; используется библиотекой и конструктором, выбор связан с беседой или личным диалогом |
| Анкета | Относится к настройкам знакомства беседы; вопросы, типы ответов, обязательность и пропуск |
| Прохождение анкеты | Связано с анкетой и новичком в конкретной беседе; состояние и ответы, поддержка таймаутов, возобновления и отмены |

Между беседами общим остаётся только идентификатор человека. Данные участия, профилей и фактов, паспорта и прохождения не переносятся между беседами. Правила для локального профиля лички пока являются [допущением](../decisions.md#допущения-ожидающие-подтверждения). Продолжение анкеты в личке не отменяет принадлежность данных исходной беседе.

Правила прав и жизненного цикла задают [участники](participants.md), [профили](profiles.md), [знание о беседе](chat-knowledge.md), [персонажи](personas.md) и [знакомство](onboarding.md). Наличие библиотеки персонажей не разрешает переносить персональные данные между чатами.

## Бэкап и перенос старых данных

Веха F9.3 предусматривает бэкап БД. Необходимость миграции данных старого бота в F9.4 определяется по инвентаризации F0.3. Это ещё не выбранная процедура и не разрешение менять старую БД.

## Сквозные сущности и долговечное состояние

Логические сущности дополняют модель без выбора SQL-схемы:

| Сущность | Связи и содержимое |
| --- | --- |
| Трассировка ответа | Ответ и chatId; идентификаторы и размеры слоёв, версии промптов/персонажа, инструменты и сжатые результаты, токены и длительность; без полного текста контекста |
| Версии промптов и персонажей | Данные и номер версии, поддержка выбора и отката; также версии шаблонов приветствий |
| Версия текста согласия | Настраиваемый текст с номером версии; формулировку определяет человек |
| Запись согласия | Человек и конкретная беседа, связь с версией текста согласия |
| Состояние фоновой задачи | Состояние очереди и незавершённой работы, необходимое для восстановления после перезапуска |
| Состояние анкеты | Дополнение существующего прохождения: сохраняемый текущий шаг и ответы, достаточные для продолжения после перезапуска |
| Таймеры и незавершённые диалоги | Долговечное состояние приветствий и диалогов по [архитектурному правилу](architecture.md#состояние-переживает-перезапуск) |
| Счётчики лимитов и расхода | Привязка к беседе и периоду; лимиты запросов/ответов и расход токенов, которые не сбрасываются потерей процесса |

Для состояний, счётчиков и персональных данных сохраняется область беседы. Обычные инструменты не получают межчатовый доступ. Доступ владельца к сводкам трассировок и расходов нуждается в отдельном согласовании по [security](security.md).

Источники версий, право публикации/отката, состояния задач, правила повторного выполнения и атомарность изменений предстоит определить в плане. Версионирование не превращает пользовательский текст в доверенные инструкции.

Сроки хранения, удаление, согласия, скрытие при выходе и бэкапы подчиняются [privacy](privacy.md). Прежний вопрос «что входит в удаление» теперь уточняется требованием удалить все данные человека в беседе; открытым остаётся способ обработки совместных и производных данных и копий. Требование хранения трассировок короче сообщений не задаёт конкретных чисел.
