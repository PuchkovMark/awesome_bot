Доставку тестовых сообщений в этот диалог ранее наблюдали в [проверке F3.2](#отправка-reply-и-подтверждение). Закрытую личку и первое сообщение в новом диалоге в этой проверке не воспроизводили. Для закрытой лички владелец выбрал отложенное уведомление с отменой при восстановлении права отправки в беседу. ## Формы ответа и код ограничения

Публичная схема описывает локальный ID в ответе `messages.send` для списка адресатов. В ней также перечислены `forward.is_reply` и `messages.setActivity`. Форму с одним адресатом, связь reply и поля после доставки нужно проверить в действующем VK. [Отправка](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/messages/methods.json#L2247) · [Поля ответа](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/messages/objects.json#L1948)

Схема задаёт `maxLength: 9000` для `message` и отдельный код `914` для превышения длины. Фактическую рабочую границу уточнит проверка с замером Unicode code points, единиц UTF-16 и байтов UTF-8. [Параметры `messages.send`](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/messages/methods.json#L2247) · [Коды VK](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/errors.json)

На локальной HTTP-подмене `APIRequest.make()` из `vk-io@4.10.1` сделал один запрос и вернул `error_code: 6` вызывающему коду. Следующий явный вызов получил успешный ответ. Это проверяет поведение одиночной попытки при ошибке частоты; доступ к живому VK не использовался для этой проверки.

## Отправка, reply и подтверждение

После согласования выполнены десять запросов `messages.send` и по одному `messages.setActivity` в личке и Test Bot. `peer_ids` с одним адресатом вернул массив с одной записью для ожидаемого `peer_id` и положительным `conversation_message_id` в обеих областях. Глобальный `message_id` был положительным в личке. В Test Bot он не был положительным, но в интерфейсе доставленный ответ отображался. `forward.is_reply` с локальным номером связал оба ответа с исходниками. Прочитанные по локальному номеру записи подтвердили область, автора сообщества, текст, время и reply. У вложенного родителя `peer_id` присутствовал в личке и отсутствовал в беседе.

Повтор запроса ответа в Test Bot с тем же `random_id` вернул тот же `conversation_message_id`. В проверенной области найдена одна копия ответа. Проверялся один близкий по времени повтор успешной отправки. Поведение при потере ответа и срок дедупликации отдельно не подтверждены.

22 ноября 2026 года для F3.6 сверили описание `random_id` в SDK VK. Оно определяет назначение параметра для защиты от повторной отправки. Продолжительность защиты в описании метода не указана. При неизвестном исходе штатный запуск F3.6 ожидает проверки фактической записи в VK. [SDK VK, метод messages.send](https://github.com/VKCOM/vk-php-sdk/blob/master/src/VK/Actions/Messages.php#L3749-L3760)

`messages.setActivity` с `type=typing` вернул успешный результат в личке. В Test Bot запрос вернул `10`. Этот результат описывает одну попытку с текущими настройками беседы. Из него нельзя вывести постоянный запрет индикатора.

## Длина и сохранность Unicode

| Проба в Test Bot | Наблюдение |
| --- | --- |
| ASCII 4000 и 4096 | Обе отправки приняты, текст получен целиком |
| ASCII 4097 | VK отклонил запрос с кодом `914` |
| Кириллица 4096 кодовых точек, 8178 байт UTF-8 с маркером | Отправка принята, текст получен целиком |
| Эмодзи, 4096 единиц UTF-16 и 8178 байт UTF-8 | Отправка принята, при чтении получен укороченный текст в 4010 байт. Конечный маркер отсутствовал |
| Смешанный текст, 4096 кодовых точек и 8179 байт UTF-8 | Отправка принята, при чтении получен укороченный текст в 5408 байт. Конечный маркер отсутствовал |
| Смешанный текст с эмодзи и другими символами вне BMP, ровно 4000 байт UTF-8 | Отправка принята, текст и конечный маркер совпали целиком |

Рабочая граница адаптера — 4000 байт UTF-8 на часть. Это консервативное ограничение по проверенным образцам. Из испытаний нельзя вывести универсальную единицу счёта или порог преобразований на сервере VK. Для журнала подтверждение получает фактический текст VK, а изменение отправленного текста учитывается как неполный исход.

## Проверка собранного клиента

Собранный клиент запросил сервер Long Poll и прочитал ранее доставленные контрольные сообщения. Обработчик отправки получил сохранённую форму ответа на `messages.send` через подмену и подтвердил уже доставленный reply реальным чтением по `conversation_message_id`. Текст контрольного образца в 4000 байт также совпал. Эта проверка использовала фактические квитанции и чтение VK в рамках прежних отправок.
