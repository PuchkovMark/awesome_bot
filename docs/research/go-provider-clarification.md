## Письмо для отправки

Тема: Допустимость OpenCode Go для разговорного бота сообщества VK

Здравствуйте!

Разрабатываю бота для личных сообщений и групповых бесед VK и хочу до запуска уточнить допустимость использования OpenCode Go.

Бот будет отвечать участникам на обычные вопросы, помогать со сведениями и историей текущей беседы, использовать ограниченные инструменты приложения. Это разговорный помощник сообщества, а не coding agent. При отдельно включённом активном режиме возможны самостоятельные ответы по ограниченному списку поводов. Обработчик работает на сервере и обращается к API автоматически, в том числе когда владелец не находится онлайн. Запросы инициируют разные участники; API-ключ хранится на сервере и участникам не выдаётся.

Рассматривается модель deepseek-v4.1-flash через Go Chat Completions. Клиент честно идентифицируется собственным User-Agent и передаёт стабильный x-opencode-session для каждого подключения беседы без исходного chatId. Трафик не будет маскироваться под программирование. Рабочие переписки пока не отправлялись; реальные вызовы модели для этого проекта ещё не запускались. Окончательные пределы нагрузки не определены.

Прошу письменно уточнить:

1. Разрешён ли описанный разговорный сценарий по подписке Go, учитывая требование типичного coding-agent трафика?
2. Допустимо ли обслуживание участников сообщества владельцем одного серверного приложения с учётом ограничений Terms of Use на собственное внутреннее использование, работу в интересах третьих лиц, автоматическое получение Output и автоответчики? Какие дополнительные условия или договорённости необходимы?
3. Какой тип аккаунта и ключа допустим для такого серверного приложения, какие ограничения нагрузки и одновременных обращений необходимо соблюдать? Если Go не подходит, какой ваш вариант доступа разрешает именно этот сценарий и на каких условиях? Это запрос информации, а не согласие на смену тарифа или покупку.
4. Кто обрабатывает тексты при этом маршруте и модели, используются ли они для обучения, каковы сроки хранения и исключения, зависят ли гарантии от периодического продления соглашений? Где найти актуальные условия для раскрытия участникам передачи текстов внешнему провайдеру?

Дополнительно прошу направить технические вопросы соответствующей команде:

- Требуется ли через ваш Go-шлюз возвращать reasoning_content при продолжении диалога с результатами инструментов для deepseek-v4.1-flash?
- Можно ли для этой модели через Go явно отключить thinking, каким документированным параметром и с какими ограничениями для инструментов?

Если ответ зависит от нагрузки или организационных обстоятельств, пожалуйста, перечислите, какие сведения нужно предоставить. Прошу указать применимые документы и условия, а при необходимости отдельного разрешения — порядок его получения.

Спасибо!

## Что зафиксировать после ответа

Дату отправки и ответа, канал и идентификатор обращения без персональных данных аккаунта, разрешённый сценарий, условия и ограничения, ссылки на документы и нерешённые вопросы. Сам факт ответа не означает разрешение: нужно проверить, относится ли он к описанному сценарию, а не только к доступности API.

Ответ и необходимые выдержки добавляются в [исследование](go-model-validation.md) с удалением персональных данных. Даже положительный ответ не закрывает натурные проверки модели и юридические формулировки согласия. Ключи, переписки, профили, платёжные сведения и доступ к аккаунту в запрос не включаются.
