## Проблема или цель

После F1.3 общие контракты определены, но журнал сообщений и настройки чатов ещё не сохраняются. Будущим компонентам нужны долговечные данные, подавление повторной доставки и доступ к истории строго в области текущего чата.

Цель F1.4 — подготовить хранилище SQLite через `better-sqlite3` и версионируемые миграции для журнала и настроек по действующей спецификации. Фича не запускает бота и не определяет продуктовые политики будущих компонентов.

## Ожидаемое поведение

При явной инициализации хранилища создаётся новая БД либо применяется недостающая часть миграций к существующей. Повторная инициализация не теряет данные и не применяет уже выполненные миграции заново. Импорт модуля сам по себе не открывает и не изменяет БД.

Слой хранения принимает записи входящих сообщений и ответов бота, сохраняет предусмотренные спецификацией поля и позволяет получать историю конкретного чата. Вызывающий компонент различает новую запись и повтор. Одинаковые платформенные id сообщений в разных чатах и платформах не конфликтуют.

Настройки каждого чата сохраняются независимо и доступны после закрытия и повторного открытия БД. Создание начальных настроек не перезаписывает изменения. Будущая сквозная обработка использует этот слой для журналирования до решения об ответе; сам роутер сюда не входит.

## Критерии приёмки

- Миграции версионируются и автоматически применяются при инициализации хранилища, которую затем будет вызывать запуск приложения. Проверены пустая БД, повторная инициализация, применение последующей миграции к уже созданной БД и сохранность существующих данных. Ошибка миграции явно сообщается вызывающему компоненту, успешная готовность не объявляется при неуспехе.
- Журнал хранит внутренний id, составной `chatId`, строковый платформенный id сообщения, составной `userId`, имя автора, роль `user/assistant`, текст, необязательный id сообщения-родителя и время UTC unix ms. Соответствие нейтральным контрактам F1.3 и представление автора ответа бота уточняются в плане без зависимости от SDK.
- На уровне БД обеспечена уникальность пары `(chatId, платформенный id сообщения)`. Повторная запись не создаёт вторую строку и не подменяет исходное сообщение. Вызывающий компонент получает различимый результат повтора; конкретный API выбирается в плане.
- Тесты подтверждают дедупликацию в одном чате и независимую запись одинакового платформенного id в разных чатах, в том числе с разными платформенными префиксами. Повторы распознаются и после повторного открытия БД.
- Операции истории требуют текущий `chatId`. Тесты с данными нескольких чатов подтверждают, что чтение истории одного чата не возвращает сообщения другого; порядок и границы выборок определяются в плане и проверяются тестами. Запросы выполняются без VK и LLM.
- Схема содержит индекс по `(chatId, время)` и предусмотренную спецификацией FTS5-таблицу по тексту, синхронизируемую с журналом. Проверена согласованность индекса с поддерживаемыми операциями записи; продуктовые поиск, фильтрация шума и инструменты истории остаются F6.3.
- Настройки чата охватывают `chatId`, название, индивидуальный системный промпт, режим ответа, таймзону, признак включения бота и дату создания. Таймзона по умолчанию — `Europe/Moscow` по спецификации; время создания хранится в UTC unix ms. Спорные начальные значения режима ответа и включения не выбираются молча.
- Создание и изменение настроек одного чата не затрагивают другой. Повторное создание начальных настроек сохраняет уже изменённые значения; после закрытия и повторного открытия той же файловой БД настройки и сообщения сохраняются.
- Проверки используют отдельные временные БД, не обращаются к старой или рабочей БД и очищают свои ресурсы. README объясняет инициализацию хранилища и запуск проверок. Совместимость выбранных зависимостей с используемым Node.js проверяется при планировании и реализации.
- Проходят линтинг, проверка типов, сборка и существующие тесты F1.1–F1.3; импорт модулей сохраняет отсутствие побочных эффектов. Секреты и тексты журнала не попадают в обычные диагностические сообщения по [правилам логов](../../specs/commands-and-limits.md#хранение-и-логи).

## Что явно не входит

- Роутер, очередь, агентный цикл, подключение БД к запуску реального бота и вызовы VK/OPENCODE.
- Схема участников и профилей F1.5, роли и авторизация F1.6, версии промптов и персонажей F1.7.
- Саммари, память, паспорт беседы, анкеты, трассировки, фоновые задачи и счётчики будущих фич. Требование долговечности сохраняется для них при их реализации, но не расширяет эту задачу до всех сущностей проекта.
- Хранение и дедупликация служебных событий участия: их политика не определена F1.3 и требует отдельного согласования.
- Исполняемые инструменты поиска, FTS-запросы для модели, оценочный сценарий «что было вчера?» и фильтрация шума F6.3.
- Команды очистки, фоновое удаление по сроку, выгрузка и удаление персональных данных, бэкапы, перенос старых данных и переход на Postgres.
- Самовольный выбор режима ответа, политики включения, сроков хранения или иных открытых продуктовых решений.
- Изменение старого бота, его БД, архивов и несвязанных рабочих файлов.

## Открытые вопросы

Блокирующих вопросов для рассмотрения задачи нет. До реализации план должен определить:

- Контракты операций журнала и настроек, порядок и границы выборок, представление автора ответа бота и связь id отправленных частей с записями журнала.
- Способ задания пути к новой БД, жизненный цикл подключения, порядок применения миграций и обработку их ошибок; конкретные имена и типы полей без изменения заданных гарантий.
- Совместимость версии `better-sqlite3` и FTS5 с Node.js 26 и воспроизводимость установки.
- Начальные значения настроек, которые ещё не определены требованиями. Выбор режима ответа и включения нельзя вывести из механизма хранения: если план требует значения по умолчанию, необходимо согласование с человеком до реализации.

Эти вопросы не являются выбранным решением. Политики служебных событий, персональных данных и будущих сущностей не заполняются догадками в рамках F1.4.
