## Проблема или цель

В [сборщике контекста](../../../src/core/context/builder.ts) чтение сообщения и проверка отмены записаны в одной строке, а цикл подбора длины цитаты объединяет вычисление середины, изменение цитаты и проверку бюджета. При ревью трудно увидеть, какие данные уже прочитаны и на каком шаге работа может остановиться. Разработчику нужен единый способ оформить TypeScript и пример, по которому можно проверить читаемость новой правки.

## Ожидаемое поведение

Разработчик находит краткие правила через корневой AGENTS.md. Из них понятно, как запустить форматирование и проверку, как именовать идентификаторы и величины с единицами и как показывать последовательность чтения, проверки и побочного действия. Единый формат охватывает поддерживаемый код в src, tests и scripts, а также корневые конфигурации ESLint и Vitest. Правила вводятся по каталогам. Сборщик контекста и его тесты служат примером улучшения читаемости; работы с этими файлами согласуются с замерами [задачи 032](../032-context-preparation-latency.md).

Относительные импорты локальных TypeScript-модулей записываются с путями `./` и `../` без расширения, например `import type { Storage } from '../storage/index';`. То же правило действует для импорта значений. При выпуске ESM сборка автоматически указывает расширение `.js` у относительных путей в JavaScript.

## Критерии приёмки

- Из установленного по lock-файлу окружения документированная команда одинаково форматирует исходник и тест. Повторный запуск даёт пустую разницу. Команда проверки обнаруживает заведомое отклонение в выбранном файле, возвращает ненулевой код и сохраняет файл без изменений.
- После применения формата по каталогам одна команда проверки охватывает весь указанный код, включая уже существующие файлы. Повторное форматирование всего охвата даёт пустую разницу. Обычная проверка проекта выявляет новые отклонения. Изменения импортов и сборки проверяются отдельно от механического форматирования.
- В правилах есть пример из проекта до и после правки. На нём видно, как отличать ID записи журнала от ID сообщения платформы, указывать единицы времени и отделять проверку после асинхронного чтения от следующего действия.
- В образцовом модуле можно проследить выбор текущего сообщения, доступной цитаты и истории, проверку бюджета и отмену. Механические изменения оформления и смысловой рефакторинг доступны для раздельного ревью.
- Проверка типов и Vitest разрешают относительные пути без расширения для импорта типа и функции. После штатной сборки проверка запускает Node.js напрямую и вызывает функцию из собранного модуля: исходный путь вида `./helper` разрешается в `dist` как `./helper.js`. Проверки границ слоёв распознают новую запись пути и по-прежнему отклоняют запрещённый импорт.
- Штатная сборка и тесты проходят. Существующие проверки подтверждают прежние состав и порядок контекста, соблюдение бюджета, отмену и недоступность просроченных источников. Проверки платформенных импортов и границ чтения контекста продолжают выполняться при сборке.

## Что явно не входит

Выпущенные миграции сохраняются в исходном виде. Генерируемый dist, зависимости, lock-файл и проектные документы исключены из прохода форматтера. Ручная переработка логики каждого модуля, изменение публичных контрактов и поведения бота выходят за границы задачи.
